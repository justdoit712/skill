# 定向查找 Skill 实施方案

## 1. 目标与已确认约束

用户输入一句具体需求，程序搜索相关 Skill、读取实际内容、评估需求匹配程度和说明质量，返回可比较的短名单，由用户选择。

示例需求：

> 找能够生成高质量 Prompt 的 Skill。

本功能采用以下确定规则：

1. **直接输入需求，不要求选择目录大类。**
2. **指定需求时跳过目录规则。** 目录的分类范围、来源排除、关键词排除、六项收录判据、人工屏蔽和冷冻名单均不作为本次查找的过滤条件。
3. **结果按本次需求评估。** 例如 Prompt 工程相关 Skill 可以正常进入搜索和比较，无须修改目录的 AI 开发排除配置。
4. **输出独立查找报告。** 不将结果自动写入目录，不改变推荐、候选、收藏或冷冻状态。
5. **保持轻量。** 复用当前 Python、GitHub HTTP 请求和模型调用能力，不新增运行依赖；本次只实现本地查找入口与报告。

本功能中的“高质量”指基于实际材料作出的适配和说明质量判断。未执行的技能不标记为已经通过功能实测，不能仅根据模型打分、仓库星数或名称宣称效果优越。

## 2. 使用方式

新增根目录入口 `find_skill.py`。以下命令为实施后的目标用法，目前尚未实现：

```powershell
# 输入需求，默认最多返回 5 个优先查看的 Skill
.\.venv\Scripts\python.exe find_skill.py "生成高质量 Prompt"

# 调整结果数量与评估范围
.\.venv\Scripts\python.exe find_skill.py "根据模糊需求生成结构完整的 Prompt，并优化已有提示词" --limit 3 --max-evaluations 20

# 调整本次模型用量停止阈值
.\.venv\Scripts\python.exe find_skill.py "生成高质量 Prompt" --max-tokens 200000
```

在 PyCharm 中直接运行 `find_skill.py`，未传需求参数时，在交互终端显示：

```text
你想找什么 Skill？
> 生成高质量 Prompt
```

需求不能为空。非交互环境没有需求参数时直接报告用法错误，不挂起等待输入。

参数定义：

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `topic` | 必填，或交互输入 | 用户原始需求，完整保留到报告 |
| `--limit` | 5 | 短名单最多展示多少个；不是模型调用次数 |
| `--max-evaluations` | 20 | 本次最多评估多少个技能文件 |
| `--max-tokens` | 200000 | 查询规划与技能评估合计的模型用量停止阈值 |

参数集中定义一次，不增加第二套配置文件。校验正整数，并要求 `limit <= max_evaluations`。有合理候选也不保证凑足指定数量。

## 3. 执行流程

```text
输入需求
  ↓
检查参数、模型连接配置与凭据
  ↓
生成本次搜索词和判断标准
  ↓
GitHub 搜索 → 仓库去重 → 定位真实 SKILL.md
  ↓
按相关线索安排读取顺序 → 抓取原文 → 文件级去重
  ↓
基于本次需求逐项评估，核对证据
  ↓
对已评估结果排序，生成短名单和备选说明
  ↓
保存 report.json、report.md，输出文件路径
```

### 3.1 需求理解与查询规划

使用一次有界模型调用，将用户需求整理为本次查找计划：

```json
{
  "intent": "寻找能够根据用户需求生成或改进提示词的 Skill",
  "queries": [
    "prompt generator",
    "prompt optimizer",
    "prompt engineering skill",
    "提示词生成",
    "提示词优化"
  ],
  "criteria": [
    {
      "id": "generate_prompt",
      "kind": "required",
      "description": "明确支持将需求转化为提示词"
    },
    {
      "id": "clarify_input",
      "kind": "quality_signal",
      "description": "说明如何识别信息缺口或澄清需求"
    },
    {
      "id": "structure_output",
      "kind": "quality_signal",
      "description": "说明目标、上下文、约束和输出格式的组织方法"
    },
    {
      "id": "improve_prompt",
      "kind": "quality_signal",
      "description": "提供提示词检查、优化或迭代步骤"
    }
  ]
}
```

上面是数据结构示例，不是对已经找到的技能的评价。

约束：

- 查询最多 8 条，覆盖中英文、同义表述和直接需求。
- 只有用户明确提出的能力可以设为 `required`；质量观察项不能擅自变成硬门槛。
- 不默认指定某种模型、某个平台或编程语言。
- 标准在本次运行开始时固定，所有候选使用相同标准。
- 查询规划结果必须校验类型、长度、重复项和标准 ID。无有效计划时报告规划失败，停止后续调用。
- 模型只输出自然语言搜索短语；程序负责构造 GitHub 查询，不执行模型返回的命令或代码。

### 3.2 搜索与发现

仅复用当前已经支持的 GitHub 搜索渠道。

- 调用 `github_search()` 执行本次计划中的查询。
- 主查询围绕搜索短语和 `"SKILL.md" in:readme` 构造；少量查询可以使用短语加 `"agent skill"` 扩展发现，最终仍必须找到真实技能文件。
- 如果使用现有 `build_query_string()`，必须显式传入 `exclude_terms=()`，避免它的默认目录排除词进入定向查询。
- 不调用会自动注入目录种子和全量领域词表的 `discover()` 总入口，不加载 `sources.json`、`searches.json` 的目录策略。
- 单条查询最多取 20 个仓库候选；按查询顺序轮转合并并去重，最多展开 20 个不同仓库。计数与实际截断情况写入报告。
- 复用仓库文件树展开能力，筛选文件名精确等于 `SKILL.md` 的路径。多个 Skill 的合集按文件分别处理，仓库首页不能替代技能文件。
- 仓库展开失败或返回不完整树时记录失败/不完整信息，不能声称该仓库没有技能或已经遍历完毕。

搜索结果受查询、索引覆盖、返回页数和数量上限影响；报告呈现本次检查范围，不使用“全网最佳”这样的结论。

### 3.3 候选安排与原文读取

**先排读取顺序，最终以文件内容确认。** 仓库名称、描述、技能路径与查询词只用于发现和优先级，不作为质量结论。

- 仓库去重键为 `owner/repo`；技能去重键为 `owner/repo:path`。
- 相关路径优先，但保留部分通用命名路径的读取机会，避免 `SKILL.md` 所在目录没有需求关键词时被直接排除。
- 跨仓库轮转读取，避免第一个大型合集占满所有名额。
- 每次最多读取 80 个技能文件、每个仓库最多读取 10 个技能文件。
- 使用 GitHub 原始文本地址，原文内容完整读取后计算 `content_fingerprint`。HTML 页面、404、空文本、超过单文件 64 KiB 上限而截断的材料不进入正式模型评估。
- 根据完整材料中的明确线索安排最多 20 个技能的评估；无法从名称和路径确认的条目不能据此判成不匹配。因限额未评估的记录为未评估。
- 每个技能可按需读取最多 2 个同仓库、由 `SKILL.md` 明确引用的说明文件；与主文件合计最多 96 KiB。保持每段材料自己的路径、内容指纹和行号。未读取的引用只记录其存在，不能据此宣称功能已经核实。
- 抓取到的同一份材料直接用于评估和证据核对，不在中途重新抓取后继续使用旧指纹。

原文仅作为材料读取，不安装或执行上游技能。结果保留必要证据片段与内容指纹，不保存一份技能包镜像。

### 3.4 需求匹配与说明质量评估

为定向查找编写独立 Prompt 与结果解析器，复用现有底层 `call_model()`。不调用目录的 `evaluate()`、`parse_evaluation()` 或 `decide()`，它们依赖目录六项检查和固定分类。

每个候选一次评估同时回答：

1. 是否直接满足用户需求？
2. 各项能力有哪些原文依据？哪些只是未说明？
3. 使用步骤、输入输出、示例和依赖是否足够清楚？
4. 用户如何尝试它？有哪些限制或无法确认的部分？

结果结构：

```json
{
  "match": "strong",
  "summary_zh": "基于已读材料的简述",
  "criteria_results": [
    {
      "criterion_id": "generate_prompt",
      "status": "supported",
      "explanation": "为什么认为它支持该需求",
      "evidence": [
        {
          "source_path": "skills/example/SKILL.md",
          "start_line": 12,
          "end_line": 14,
          "quote": "对应材料中的原文片段"
        }
      ]
    }
  ],
  "documentation": "clear",
  "usage_zh": "从技能说明中归纳的使用方式",
  "dependencies": [],
  "limitations": [],
  "why_consider": "适合优先查看它的理由"
}
```

枚举与解释：

- `match`：`strong / partial / none`。
- 能力状态：`supported / unsupported / unknown`；未说明不等于不支持。
- `documentation`：`clear / partial / insufficient`。

代码强制约束：

- 结果必须覆盖本次计划中定义的标准 ID，不接受模型临时增加新的硬标准。
- `supported` 必须有已读材料的证据。程序核对文件、行号和引文；不存在或不匹配的证据降为 `unknown`，并重新计算短名单资格。
- 所有必需能力都有有效支持证据，才允许 `strong`。模型的自报匹配程度不能越过这个条件。
- 输出只允许文本、规定的枚举和有界数组；拒绝非对象 JSON 和错误类型，HTML/Markdown 输出正确转义。
- 技能 ID、链接、作者/仓库、检查时间、材料指纹由程序填写，不采用模型编造的链接和身份信息。
- 上游材料仅是评估对象，其中要求修改规则、读取凭据或执行命令的文字不作为程序指令。

### 3.5 排序与结果数量

在本次评估范围结束或预算停止后，对有效结果统一排序，避免找到前几个就直接宣称它们最优。

排序依据依次为：

1. 经证据校验的需求匹配程度。
2. 有证据支持的质量观察项覆盖程度。
3. 使用说明的清晰程度。
4. 相同条件下按稳定 ID 排序，保持结果可重复。

短名单最多 `limit` 个，从 `strong` 且说明不为 `insufficient` 的候选中选取。`partial` 的相关技能单列为“备选及差距”，不能用来填满强匹配数量。未找到足够条目时如实说明。

仓库星数不作为质量分数。来源只报告可确认的仓库和作者信息，不自动将某个 GitHub 仓库认定为官方。

## 4. 目录规则的隔离方式

隔离通过调用边界实现，不通过临时清空全局配置或篡改规则实现。

| 现有能力 | 新入口的处理 |
| --- | --- |
| `github_search()`、仓库文件树读取 | 复用基础网络能力 |
| `Candidate`、去重、内容指纹 | 复用数据与工具函数 |
| `fetch_text()` | 复用读取能力，调用前构造原文 URL，调用后检查截断和内容类型特征 |
| `call_model()`、`resolve_api_key()`、`UsageTotals` | 复用模型传输、凭据与用量统计 |
| `load_all_config()`、`prescreen()`、目录 `evaluate()`、`decide()` | 不调用 |
| 分类、领域搜索词、来源排除、黑名单、冷冻名单 | 不作为定向查找输入 |
| 本地候选池、周账本、目录索引 | 不读写，不改变状态 |

仅加载 `config/model.local.json`，不存在时加载 `model.example.json`，再按现有方式解析环境变量凭据。只取连接、认证、模型和必要的请求设置；本次上限使用定向查找自己的运行参数，不沿用目录的周额度或 100M 默认预算。示例配置未填真实连接参数时，预检明确报错。

## 5. 用量、失败与结束行为

- 查询规划和候选评估的模型用量都计入本次报告。
- 对本次使用的模型配置副本设置 `max_attempts=1`，避免底层自动重试隐去单次请求的用量；不改写原模型配置文件。
- 每次调用前检查剩余停止条件；每次调用结束立即累计用量并保存已完成结果。
- `--max-tokens` 是按返回用量执行的停止阈值，不承诺服务商账单的硬上限；最后一次请求可能使累计用量超过阈值。模型输出长度另行限制，查询规划最多 1200 个输出 Token，单技能评估最多 2500 个。
- 模型请求超时、结果不明，或响应缺少可用用量时，记录未知用量并停止后续模型请求，保留此前有效结果。不能把未知用量当成免费继续调用。
- 模型返回结构无效但用量已知时，计费记录保留，该条记为评估失败；连续 3 次评估失败结束本次查找。
- GitHub 的临时错误使用现有有界重试；仓库或文件读取失败记入搜索覆盖信息。个别失败不清空已有结果。
- 用户中断时保存已完成结果、用量和停止原因，不伪装成正常完成。

报告状态区分正常完成、候选不足、评估数量上限、Token 停止阈值、搜索失败、模型失败、用量未知和用户中断。短名单是否足够与流程是否报错分别记录。

## 6. 输出与保存

每次写入独立目录：

```text
data/local/find-skills/<时间戳-随机后缀>/
  report.json
  report.md
```

该路径已被现有 `data/local/` 忽略规则覆盖，不需要修改 `.gitignore`。运行目录唯一，不共用目录账本或候选池，也不增加跨任务缓存。

`report.json` 包含：原始需求、查找计划、有效运行参数、运行状态、搜索/读取/评估计数、失败与未评估原因、全部已评估结果、短名单、备选、Token 用量和格式版本。

`report.md` 面向选择使用，展示：

```text
查找需求：生成高质量 Prompt
本次实际检查范围与用量

优先查看
1. 技能名称与原始链接
   能做什么
   与本次需求匹配的证据
   使用方式与依赖
   主要限制或未确认项

相关备选及差距
未找到足够条目/提前停止的原因
```

文件采用临时文件后替换的方式保存。JSON 是本次运行记录，Markdown 由它生成；原始材料引用标注抓取时间、路径和指纹，不能将 HEAD 链接当作不可变版本链接。只有实际解析到提交版本时才展示固定版本链接。

## 8. 测试与验收

自动测试使用临时目录、假 GitHub 请求和假模型响应，业务逻辑调用真正的新入口，不在测试里复制一份过滤或排序实现。

必须覆盖：

1. **跳过目录规则**：目录策略配置不存在，或把 Prompt 工程及测试仓库列为目录排除项，新入口仍能找到并评估它；目录屏蔽/冷冻状态不拦截定向结果。
2. **无目录副作用**：运行前后正式索引、候选池、账本、人工配置内容保持一致。
3. **查询生成**：保留原需求、生成有界有效查询、不引入目录默认排除词、不把质量观察项升级成必需条件。
4. **真实文件**：仓库首页不能作为 Skill；`SKILL.md` 精确匹配；重复仓库和文件不重复评估；展开截断记录为不完整。
5. **读取边界**：原始文本 URL 正确，HTML、404、空文本、截断内容不能得到强匹配结论；行号对应实际读到的同一份材料。
6. **需求匹配**：明确生成 Prompt 的技能可以匹配；仅列出 Prompt 文章链接或泛泛提及 Prompt 的技能不能因此获得强匹配。
7. **证据校验**：伪造文件、越界行号、引文不匹配、缺少必需能力证据，都不能进入强匹配短名单。
8. **限额语义**：`limit=5` 只影响展示；最多评估 `max_evaluations` 个；不够 5 个时不凑数；查询规划也计入 Token。
9. **失败与中断**：未知用量后不再请求模型；已知用量的无效输出被计入；中断保存部分结果；全部搜索失败区别于没有匹配项。
10. **报告**：链接与身份来自程序，依赖不臆测，排序稳定，用户输入和上游文本在输出中正确转义，不泄露凭据。

完成实现后执行：

```powershell
.\.venv\Scripts\python.exe -m unittest tests.test_skill_finder tests.test_find_evaluate tests.test_discover
.\.venv\Scripts\python.exe -m unittest discover -s tests
```

真实运行验收使用本次明确提出的需求：

```powershell
.\.venv\Scripts\python.exe find_skill.py "生成高质量 Prompt" --limit 5 --max-evaluations 20 --max-tokens 200000
```

检查实际找到的链接、报告证据与用量；结果必须让用户能够比较“这个 Skill 如何帮助我生成 Prompt、说明是否充分、有哪些限制”。没有足够可靠候选时，给出真实结果和覆盖范围，不预先承诺一定找到 5 个。
