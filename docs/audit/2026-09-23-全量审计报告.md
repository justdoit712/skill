## 2. P0 缺陷（阻断级）

### P0-1 阶段一任意一次抓取失败即 `NameError` 崩溃

- **位置**：`src/catalog/sync_reserve.py:241` 使用 `UPSTREAM_GONE`；导入处 `:15` 只有 `from src.infra.http import fetch_text`。
- **触发**：`prepare()` 抓取循环中任意 `fetched.ok == False`（404/410、网络错误、限流、超时）。
- **后果**：`NameError` 抛出 → `phase_reserve()` 整体失败 → **账本与队列都不落盘，本轮零评估零产物**。因队列排序键确定（`queue.py:128-137`），重跑必然先命中同一条 → 单条死链即可永久阻塞每周流水线。`--dry-run` 同样受影响（也调用 `prepare`）。
- **复现**（单候选 + 404 假抓取）：

  ```python
  phase_reserve(..., discover_fn=lambda *a, **k: ([cand], []),
                fetch_fn=lambda url, **k: FetchResult(url=url, ok=False, status=404,
                                                      reason_code="UPSTREAM_GONE", error="HTTP 404"))
  # → NameError: name 'UPSTREAM_GONE' is not defined
  # → budget.json / queue.json 均未写出
  ```
- **旁证**：全库"未定义名"静态扫描仅此 1 处；293 项测试全绿，因为 `sync_reserve` 的抓取失败分支从未被执行（覆盖率实测该模块 86.9%，该分支未命中）。
- **修复**：改用 `from src.infra.http import REASON_UPSTREAM_GONE`（或补导入），并补一条抓取失败回归用例。
- **置信度**：【实测】

### P0-2 CI 会把真实 `LLM_API_KEY` 发往 `api.example.com`

- **位置**：`src/catalog/config.py:31-32`、`config/model.example.json:6-7`、`.gitignore:6`、`.github/workflows/sync-skills.yml:123-130`。
- **链条**：`config/model.local.json` 被 `.gitignore` 排除 → CI 检出后不存在 → `load_all_config` **回退加载 `model.example.json`**（`endpoint=https://api.example.com/v1/chat/completions`、`model=example-model-name`）→ `precheck()` 只校验非空 → **返回 `[]` 放行** → `call_model` 从环境变量取到真实密钥，作为 `Authorization: Bearer` 发出。
- **后果**：密钥被发往非模型供应商域名（IANA 保留的 example.com），且付费评估 100% 失败。
- **复刻**（临时目录只放已提交的配置文件）：

  ```
  endpoint = https://api.example.com/v1/chat/completions
  model    = example-model-name
  precheck = []（视为就绪）
  密钥来源 = 环境变量 LLM_API_KEY
  ```
- **文档自证**：`../src分层重构实施方案.md:259` 已写明"示例占位连接值不能作为就绪配置进入请求"，未实现。
- **修复**：`model.local.json` 缺失即判为预检失败；或由 CI 步骤从 Secrets 生成该文件。
- **置信度**：【实测】（"密钥确实离开本机"为合理推断，未发起真实请求）

### P0-3 定时同步永不部署（step id 引用错误）

- **位置**：`.github/workflows/sync-skills.yml:52-54` 声明 `outputs.dry_run: ${{ steps.run.outputs.dry_run }}`、`week: ${{ steps.run.outputs.week }}`；`:177` 为 `if: needs.sync.outputs.dry_run == 'false'`。
- **实测**：sync job 实际 step id 只有 `args`（写 `args`/`week`）与 `reserve`（写 `dry_run`）。`steps.run` 不存在 → 两个 job output 均为**空串** → `'' == 'false'` 恒假 → **deploy job 永远被跳过**。
- **后果**：定时运行提交数据但永不发布；只有改 `config/overrides.json|snoozed.json` 走 `sync-config-deploy.yml` 才会部署（因而发布的可能是与 `main` 不一致的版本）。
- **为何没被测出**：`tests/test_workflows.py:107-110` 只断言 `needs`/`uses`，不解析 step id。
- **修复**：`steps.run.outputs.dry_run` → `steps.reserve.outputs.dry_run`；`week` → `steps.args.outputs.week`（或统一加 `id: run`）。建议同时新增一条断言：**每个被引用的 step id 必须真实存在**。
- **置信度**：【实测】（静态引用）／【推断】（依赖 Actions 对不存在 step id 求值为空串的平台语义；未在真实 Actions 上观察过跳过）
