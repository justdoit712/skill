## 2. O-01：同步后的第一次取消无效

### 触发步骤

1. 在网页将 Skill A 标记为已收录。本地 `stagedAdds[A]` 存入 `localStorage`。
2. 导出变更包，用 `tools/manage_owned.py --apply-changes` 合入仓库，离线同步页面数据。
3. 刷新网页。新的公共名单已经含 A，但浏览器仍加载旧的 `stagedAdds[A]`。
4. 在“已收录”列表点击“取消已收录”。

`unmarkOwned()` 先发现 `stagedAdds[A]`，只将其删除并返回，没有创建 `stagedDeletes[A]`。此时基线仍有 A，所以 A 依旧处于已收录状态。最小复现得到 `stillOwned=true`，生成的变更包为 `changes=[]`。

### 根因和位置

- [owned-state.js](../../public/js/owned-state.js) 的 `populateOwnedBaseline()` 只重建基线，没有对账已暂存操作。
- 同文件的 `unmarkOwned()` 在删除 `stagedAdds` 后无条件返回，没有考虑基线已含这个 ID。
- [app.js](../../public/js/app.js) 的 `boot()` 依次加载新基线和旧本地缓存，没有后续对账步骤。

### 修复方法

将浏览器状态表示为“基线 + 每个 ID 的未同步目标状态”。加载新基线及本地操作后，逐项对账：

1. 暂存新增的目标内容与新基线相同：判为已同步，移除对应暂存新增。
2. 暂存删除且新基线已不存在：判为已同步，移除对应暂存删除。
3. 新基线与原 `before` 不一致，且尚未达到目标状态：保留为冲突并提示用户，不静默清除。
4. 对账后再保存浏览器状态、刷新待同步数量和列表。

为兼容旧缓存，`unmarkOwned()` 还应处理“双重存在”的情况：删除 `stagedAdds[A]` 后若 `baseline[A]` 存在，应继续登记删除，而不是直接返回。删除补丁的 `before` 必须来自新基线。

### 验收

新增行为测试：标记 A → 保存暂存 → 新页面基线包含 A → 加载缓存 → 取消 A；断言 A 不再被 `isOwned()` 判为已收录，变更包有一条 `before=A, after=null`。同时测试重复刷新不会反复出现“待同步新增”，以及服务器记录与暂存内容不同的冲突提示。

## 3. O-02：多标签页会覆盖未同步操作

### 触发步骤

1. 同一个站点打开标签页甲和乙，两页都在空名单时加载。
2. 甲标记 A，保存 `stagedAdds={A}`。
3. 乙标记 B，保存 `stagedAdds={B}`。
4. 甲或乙刷新。

当前 `saveOwnedStagedStorage()` 将所在标签页的完整 `stagedAdds`、`stagedDeletes` 对象直接写到同一个 `localStorage` 键。实测最终只剩 B；甲的 A 没有进入变更包。`saveOwnedPrivateStorage()` 同样整体覆盖私人详情，存在相同风险。页面没有监听 `storage` 事件。

### 根因和位置

- [owned-state.js](../../public/js/owned-state.js) 的 `saveOwnedStagedStorage()` 和 `saveOwnedPrivateStorage()` 使用单键整体覆盖。
- [app.js](../../public/js/app.js) 没有跨标签页更新或冲突提示。

### 修复方法

推荐将暂存操作和私人详情迁移到 IndexedDB，以 `skill_id` 为键分别保存；每次修改使用事务读取并写入当前 ID，避免互不相关的 A、B 相互覆盖。通过 `BroadcastChannel` 或 `storage` 事件通知其他标签页重新读取并刷新页面。

对**同一个 ID** 的并发修改，记录修订号或更新时间；发现另一标签页已改动时提示冲突，不能简单采用最后一次写入。迁移时先读取旧 `localStorage` 键，成功写入新存储后再移除旧键。存储不可用或事务失败时要在页面提示“未保存”，不能吞掉异常后显示成功。

若暂时不引入 IndexedDB，至少需要让页面检测其他标签页的修改并阻止旧标签页继续静默写入。单纯增加 `storage` 监听，而仍然整体覆盖旧对象，不能完全解决交错写入。

### 验收

双标签页行为测试：甲新增 A、乙新增 B，任一页刷新和导出都应包含 A、B；两页编辑同一 ID 时应出现冲突提示或明确的合并结果。私人详情执行同样测试。另验证旧存储键迁移一次且不丢现有未同步变更。

## 4. O-03：取消已收录后错误展示原排除项

### 触发步骤

主索引存在状态为 `excluded` 的 Skill A，已收录公共数据在 `owned_entries` 保存其 `original_partition=excluded`。在“已收录”中取消 A。

最小复现中，`partitionEntries()` 把 A 放入 `activeCandidates`。相同路径也会误处理 `pending`、`processing_failure` 等非展示状态。`isExcluded()` 只检查人工屏蔽状态，不能替代条目原来的自动排除结论。

### 根因和位置

- [catalog-state.js](../../public/js/catalog-state.js) 的 `populateBaseline()` 将 `owned_entries` 合并到 `allEntries`。
- 同文件的 `partitionEntries()` 只显式检查 `recommended`；其他所有值都进入 `activeCandidates`。

### 修复方法

分区必须使用允许名单：

- 原分区 `recommended` → 推荐区。
- 原分区 `candidate` → 候选区。
- 原分区 `manual` 且当前仍有效收藏 → 收藏区；已取消收藏时按原自动结论处理，不能猜成候选。
- `excluded`、`pending`、`processing_failure`、未知值 → 不进推荐或候选；仍可从主索引或已收录管理信息中追溯。

页面中“取消已收录”的反馈也应依实际结果区分“已恢复展示”和“仍受原状态限制”。不要对 `owned_entries` 缺失原分区的条目默认赋值 `candidate`；需要结合原条目状态确定，实在无法判断则保持隐藏。

### 验收

分别构造推荐、候选、收藏、自动排除、待处理、处理失败和未知状态的已收录条目。取消后仅符合展示资格的条目进入相应分区；其余不出现。补一条页面端到端断言，防止纯状态测试绕过数据投影。

## 5. O-04：运行期解析错误导致查找报告不完整

### 触发步骤

定向查找的模型规划请求返回了有效用量但无效 JSON。`parse_query_plan()` 抛出 `ValueError`。

当前 `execute_find_skill()` 的运行期 `except ValueError: raise` 将异常直接传出，跳过 `finalize_run()`。最小复现中 `report.json` 已记录 2 Token，但 `status` 仍是 `running`，没有 `report.md`。CLI 最后把错误解释为参数或配置错误，无法从报告看出一次已发出的模型请求究竟如何结束。

### 根因和位置

[run.py](../../src/finder/run.py) 的预运行校验已经在 `try` 之前完成；运行期 `ValueError` 可能来自规划解析、搜索/展开适配器或其他数据处理。统一重抛把这些运行错误与启动参数错误混为一类。单项评估解析目前在 `_evaluate_candidate()` 内自行处理，不属于这个复现路径。

### 修复方法

保留 **运行前** 配置、名单、参数校验的抛错行为；移除运行期的 `except ValueError: raise` 特例，让运行期错误进入失败记录与统一收尾。根据发生阶段设置 `plan_failed`、`evaluation_error` 或现有兼容的错误码，不把内部异常全文写入公共投影。确保已记录的请求用量、已完成的部分评估和错误阶段一并保存。

运行期异常后的本地 `report.json` 不应保持 `running`。公共快照是否更新仍遵循现有规则：零有效结果的失败保留上一次有效快照。

### 验收

分别让规划解析、搜索/展开适配器抛 `ValueError`，验证 CLI 失败码、本地 JSON 的终态、Markdown 报告、用量与错误阶段。再验证非法命令参数和损坏名单依旧在请求前失败，模型调用次数为零。

## 6. O-05：页面的 Actions 自动合并提示不真实

### 触发步骤

打开“已收录”同步弹窗，说明写着可把 `owned-patch.json` 提交到仓库，由 Actions 自动合并。实际 [sync-config-deploy.yml](../../.github/workflows/sync-config-deploy.yml) 只监听 `config/owned-skills.json` 等配置文件，执行 `tools/run_local.py --sync-config`。它没有读取或合并变更包，也不监听 `owned-patch.json`。单独提交变更包不会改变已收录名单，甚至可能不会触发该工作流。

### 根因和位置

[modals.js](../../public/js/modals.js) 的说明超出了当前工作流支持的能力。

### 修复方法

第一版直接修正文案，给出可实际完成的路径：下载 `owned-patch.json` → 在仓库本地执行 `python tools/manage_owned.py --apply-changes <文件路径>` → 检查 `config/owned-skills.json` 与生成的目录文件 → 提交并推送配置。页面按钮只复制本地命令，不承诺 GitHub 网页或 Actions 自动合并。运行说明同步修改。

若以后确实需要网页端自动合并，另行实现受控的变更包提交入口、格式及冲突校验、Actions 触发与失败报告，再恢复相应文案。不能让现有配置同步工作流盲目应用仓库中任意变更包。

### 验收

用页面下载的真实变更包执行本地工具，在临时仓库副本确认名单与页面产物更新；核对弹窗中的命令、文件名、工作流触发路径和运行说明一致。若只提交变更包文件，文档应明确其不会自动生效。

## 7. 建议修复顺序

1. 修 O-01，再修 O-03：先保证“标记 → 同步 → 取消 → 恢复”的基本闭环正确。
2. 修 O-04：保证付费请求的用量和终态可追溯。
3. 修 O-02：处理多标签页和私人详情的数据丢失风险。
4. 修 O-05：同时更新页面文案与运行说明。
5. 跑完整 Python、前端测试，再用临时仓库副本走一次离线全流程和浏览器双标签页冒烟。

当前已有测试全绿并不能替代这些回归。新增测试应围绕上述真实操作顺序，而不只是验证单次函数调用。
