# 分层重构实现与验收核对

> 本文及关联 observations JSON 是修复前基线，原始观察保留。后续代码修复和验证结果见 [修复验收记录](./2026-09-23-分层重构修复验收.md)。

日期：2026-09-23。代码基准：`098d754da4ef7ff056291a9226f8e3aff6db73fe`。

依据：历史《分层与轻量化评估》《分层重构实施方案》（已归档至 Git，见提交 f2fc5bc 的 docs/ 目录）；长期约束见 [架构约定](../架构约定.md)。本文是当前代码对原方案的核对，不执行方案中的重构、提交、发布或真实模型验收。

## 结论

**尚未完整实现，不能按原方案宣布全量验收通过。** 四包迁移、前端模块化、统一条目更新和部分 finder 行为修复已经落地；存储协调、材料集合身份、请求事实、报告契约以及真实入口验收仍有明确缺口。

本次重新执行 Python 测试 **302 项通过**、Node 测试 **7 项通过**；三个 CLI 在正常配置下的 `--help` 均成功。新增离线探针调用真实生产编排、解析和核验函数，以假模型/网络结果替代外部接口，得到 15 组行为观察（包含正常成功对照）及静态调用/函数跨度统计。探针显式禁止 requests 网络调用，运行数据全部在系统临时目录。本次不读取本地模型凭据、不发真实模型请求、不运行真实采集、不验证远端发布、不进行浏览器交互验收。

证据：[可重跑探针](../evidence/refactor_acceptance_probes.py)、[本次观察结果](../evidence/refactor-acceptance-observations.json)。探针是诊断记录，不是“保留缺陷才通过”的回归测试；修复时应把对应行为转成预期正确结果的生产入口测试。

标注：**实测**表示本次执行生产函数得到结果；**读码**表示检查生产调用链；**证据不足**表示当前测试或本次范围不足以验收，不等于断言功能一定错误。

## 一、已落实的部分

- `catalog`、`finder`、`infra`、`shared` 四包已存在；现有 AST 检查覆盖跨业务和反向入口依赖，并在本次测试中通过。
- `catalog/local.py:243` 和 `catalog/sync_evaluate.py:241` 实际调用 `update_entry()`，并非只有孤立 helper。
- finder 候选尝试数与成功数分离；失败消耗尝试名额，规划单独计入请求；未知用量停止后续调用，强制单次模型传输。现有 T01/T02 用例通过，但不涵盖下文所有 F1 要求。
- finder 实际调用精确路径、行号范围与完整引文核验；使用深拷贝，不再沿用旧版首尾子串宽松匹配。解析前置类型转换仍存在绕过，见 R05。
- 查询先搜集再轮转；精确 `SKILL.md` basename、HTML 拦截和相关/通用路径交替已有实现及测试。不能把旧审计中“完全没有 HTML 拦截”继续当作当前 finder 的事实。
- 缺少 required 的规划会报错；正常排序、短名单/备选区分已有行为测试。
- 两阶段材料缓存缺失后重新抓取时，已有指纹不匹配跳过评估的检查与测试（`sync_evaluate.py:161`）；不等同于完整材料集合身份已实现。

- workflow 的输出已引用 `steps.reserve` 和 `steps.args`，旧报告所述 `steps.run` 错误已修正；本次未运行 GitHub Actions。

## 二、必须补齐的缺口

### R01：统一存储协调器没有接入生产入口（高）

要求：方案 §6.1、T19/T20；所有目录采集和维护使用同一锁保护读改写，完成结果及页面可离线恢复。

**读码**：`catalog/store.py` 定义 `mutate_catalog()` 和 `recover_catalog_projections()`，但在整个 `src` 中没有找到它们的具名调用，只有定义/导出。静态扫描不覆盖动态调用；结合实际入口检查，`local.py:253`、`sync_evaluate.py:270`、`enrich.py:236`、`index.py:406` 仍调用旧 `write_catalog()`。后者使用 `index.py:308` 的 `_write_json()` 直接 `write_text()`。

影响：store 的锁、原子写和恢复测试不能证明真实采集/维护被保护；原写入仍有半文件及旧内存覆盖风险。此处是调用链结论，本次没有制造真实并发覆盖。

补齐：让各实际入口使用同一个读改写协调路径；为真实入口增加锁冲突和主记录/页面写入故障注入，恢复模型调用数必须为 0。

### R02：材料集合身份未落地，快照接口本身不兼容（高）

要求：方案 §4.2、T18；主/引用文件组成同一集合，保存各自指纹、来源、读取失败与版本事实。

**读码**：`MaterialBundle`、`validate_document()` 在 `src` 无具名调用。`finder/search.py:256` 仍返回 `dict[str, str]`，只更新主文件指纹；引用 URL 使用 `HEAD`，失败引用没有进入材料 manifest。

**实测**：把合法 `DocumentSnapshot` 传入 `verify_evidence_snippet()`，在 `finder/evidence.py:36` 抛 `AttributeError`：读取了不存在的 `.content`，数据类实际字段是 `.text`。当前字典字符串路径不触发此错误，但说明新快照契约尚未打通。

补齐：接通快照与集合身份，保留旧 ID 兼容；加入“只改变引用文档”“主文档固定 revision、引用不同 revision”“引用失败”的真实材料读取测试。

### R03：未知用量的有效结果被丢弃，中断请求记账不完整（高）

要求：F1、T01/T16；有效但缺 usage 的当前结果可解析保留，然后停止；中断时记录已开始但结果未知的调用。

**实测**：正常对照运行得 1 条有效结果；相同评估只删除 usage，输出 `stopped/usage_unknown`，但 `evaluated_count=0`。原因是 `finder/run.py:519` 在解析当前返回内容之前直接收尾。

**实测**：规划返回成功后，在候选模型函数内抛 `KeyboardInterrupt`；假接口进入两次，报告 `evaluation_attempts=1`，但 `usage.requests=1`、`unknown_usage_requests=0`，只记录规划请求。

**实测**：`UsageTotals.add(ModelCallResult(attempts=0))` 反而记录 1 次请求与 1 次未知用量（`shared/usage.py:25`）。这与中断漏记是不同方向的问题，不能通过统一强制计 1 来解决。

补齐：区分未进入传输、已开始未返回、已收到结果；在请求前持久化开始事实，收尾时结算未知状态；先保留有效结果再因未知用量停机。

### R04：展开/材料全部失败被标成正常无匹配（高）

要求：F3、T04；全部展开失败应为 `error/expansion_failed`，全部材料失败应为 `error/material_failed`。

**实测**：模拟全部展开失败，以及全部候选材料返回 HTTP 429；两者都得到 `completed/candidates_exhausted`，而非错误。实际分支分别位于 `finder/run.py:425`、`:498`。本次通过 `execute_find_skill()` 复现，未另跑该场景 CLI 子进程。

影响：运行失败与没有匹配混淆，可能按正常空结果替换旧公共结果。后一个影响由公共发布条件读码判断。

补齐：保存逐项失败原因和 `coverage_incomplete`，区分正常为空、部分失败、全部基础设施失败，并验证退出码。

### R05：严格证据核验被解析器的类型转换削弱（高）

要求：F2/F6、T03/T21；先校验字段类型、标准 ID、枚举和长度，不把非法值转成合法值。

**实测**：模型返回 `start_line=true/end_line=true`；`parse_skill_evaluation()` 在 `finder/evaluation.py:213` 用 `int()` 转为 `1`，之后生产核验器接受，最终仍为 `strong`。直接测试核验 helper 拒绝 bool 无法发现这个串联问题。

**实测**：简介长度 1,201（方案上限 1,200）仍被接受。**读码**：解析器将多种字段 `str()` 化；不按 F2 严格拒绝超限证据/说明，对额外标准 ID 忽略，对遗漏结果补 unknown，而非严格结构校验。

补齐：测试必须走“模型原始 JSON → 解析 → 核验 → 排名”；覆盖 bool/float 行号、对象冒充文本、超限、重复/遗漏/额外标准 ID。

### R06：公共报告仍中途写出、异常被吞，脱敏不完整（高）

要求：方案 §6.2、T11/T13；公共投影仅在统一收尾发布，失败可诊断，不公开本机路径/连接细节。

**读码**：`finder/run.py:265` 的中途保存调用 `update_public_snapshot()`，并 `except Exception: pass`。`report.py:288` 对有成功评估的未识别状态也允许发布，因此 `running` 快照可能写出。公共写入无约定的短锁；JSON 原子替换不能替代并发发布协议。

**实测**：`sanitize_report_for_public()` 原样保留 `stop_reason='OSError: C:\\private\\report.json'`。查询 error 也直接投影。`run.py` 会把异常文本拼入 stop_reason，因此白名单字段本身并不保证其内容安全。

**读码**：`write_local_report()` 的 Markdown 使用直接 `write_text()`；`finalize_run()` 派生写出失败会抛异常，没有独立诊断返回协议。本次未对每个保存边界做故障注入，不宣称所有恢复路径均已复现。

补齐：区分本地诊断与公开错误 code/message；只在收尾发布公共快照；派生失败保留 JSON 并明确报告，可独立重建。

### R07：配置契约不完整，示例 endpoint 仍可通过加载（高/中）

要求：F5、T07/T12；拒绝小数、错误类型配置和占位连接，help 不依赖配置正确。

**实测**：`_parse_int_val(1.9)` 返回 1；`find-skill.json` 为 JSON 数组 `[]` 时静默得到 `{}`；示例 endpoint `https://api.example.com/v1/chat/completions` 被 `load_finder_model_config()` 接受；损坏查找配置下 `main(['--help'])` 返回 2。

位置：`finder/config.py:35/:62/:82`、`finder/run.py:631`。目录配置也保留 example 回退和非空预检（`catalog/config.py:52/:83`）。本次没有向示例域名发送任何请求，不把配置放行表述成已发生凭据泄露。

补齐：统一入口校验，显式拒绝示例占位值与错误配置类型，help 先解析；保留正确的显式参数和配置优先级。

### R08：HTTP 恰好达到读取上限被误判截断（中）

要求：§4.1、T05；恰好等于上限且 EOF 的完整文档可用。

**实测**：4 字节响应、上限 4，`infra/http.py:60` 的 `_read_capped()` 返回 `truncated=True`。业务层可能因此跳过完整材料。

补齐：读取到能区分 EOF 与实际超限的边界，并覆盖单块/多块与上限前后各 1 字节。

### R09：网络请求重复实现，账本读取仍有副作用（中）

要求：P2/P3、评估 §12.4/§13；共享通信能力，区分读取和周切换。

**读码**：`infra/github.search_repositories()` 没有生产具名调用；`catalog/discovery.py:103` 与 `finder/search.py:38` 仍各自执行仓库搜索，后者没有有界重试循环。`BudgetLedger.load()` 仍执行归档移动/删除（`catalog/budget.py:86`）；本地通过 `_save_record()` 写私有接口（`local.py:577/:637`）。

补齐：共享传输实现，保留各业务策略；将周切换作为显式写操作纳入锁；提供明确评估记录操作。

### R10：大编排和维护职责只部分迁移（中）

要求：P3/P4；候选处理与运行控制分开，去除依赖大量外层状态的 save/publish 闭包。

**读码/AST**：`local._collect()` 338 行，仍有 `save()`、`publish()` 闭包；`phase_evaluate()` 265 行；`execute_find_skill()` 466 行。行数不是单独判错依据，问题在于方案明确要求拆出的逐候选处理、运行快照、保存协调仍交织。

`maintenance.py` 只是调用 `index.sync_config_to_catalog()` 和 `enrich.enrich_catalog()`，实际文件级用例未移出；`FinderRunState` 没有实例化，状态仍散落在 report 和局部变量中。各包 `__init__.py` 有大量集中重导出，与“保持简单”的要求有偏差。

补齐：先处理实际状态边界，避免为减少行数机械拆函数；删除不用的抽象或接入必要实现。

### R11：报告 schema、覆盖信息及前端兼容验收不完整（中）

要求：F3、评估 §14、T13；事实 JSON 有 schema，未知版本可见报错，不把未知计数伪装成 0。

**实测**：正常生产 finder 本地 report 没有 `schema_version`，只有公共投影硬编码该字段。**读码**：生产报告没有完整的 `coverage_incomplete`/逐项失败清单；前端 `find-view.js` 不检查 schema，缺 usage 显示 0，缺尝试数从成功数量推算。

补齐：固定事实报告版本与投影契约；新旧样例通过实际渲染测试，未知版本显式提示。现有前端状态测试多为字符串存在断言，未证明 DOM 行为。

### R12：仍有阶段一抓取失败崩溃（高）

**读码**：`catalog/sync_reserve.py:241` 使用 `UPSTREAM_GONE`，模块无该名称定义或导入。抓取失败进入该行会抛 `NameError`。本次没有重做该分支的完整入口复现，结论来自当前作用域核查，不冒充实测。

补齐：使用 HTTP 层原因码并测试 404、429、网络失败，区分暂时不可用与上游移除。

## 四、为什么测试全绿仍不能验收

1. `tests/test_store.py` 验证的是 store helper，未证明真实写入入口调用它；`test_materials.py` 同样只验证快照/集合自身。
2. `tests/test_entry_state.py:259` 所谓 local/pipeline 一致性，是相同参数调用 `update_entry()` 两次再比较，没有分别经过两个入口。
3. `tests/test_summary_structure.py:122` 起的部分继承测试在测试体内重写规则，不能代替生产状态机回归。
4. `tests/test_finder_projection.py:374` 起的前端验证是源码字符串检查，不能证明运行时渲染、新旧 schema 或交互正确。
5. 证据 bool 类型测试若只调用 verifier，会绕过生产 parser 的 int 转换。T23 手写结论也不能证明模型语义判断。

这些问题不意味着所有测试无价值；302 项通过证明现有断言成立，本次 15 组观察说明验收还需要串联生产入口和错误分支。
