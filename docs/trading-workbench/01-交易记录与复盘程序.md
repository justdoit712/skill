# 交易记录与复盘程序：产品与实现规范

版本：0.1.0（设计基线）  
日期：2026-10-09  
状态：待实现。本文描述新程序，不代表当前 Skill 目录仓库已具备这些能力。

关联文档：[标的研究程序](02-标的研究程序.md) · [共享数据存储与访问规范](03-共享数据存储与访问规范.md)

## 1. 产品目标

用尽量少的操作保存真实交易经过，让用户能够回答：当时为什么买、原本准备怎么做、实际怎样执行、结果如何、以后需要验证什么改进。

用户主要在手机同花顺中操作 A 股。第一版在 Windows PC 上运行；用户自行将手机截图传到电脑，再导入程序。手机不是本程序的运行端，不建设手机网页、远程连接或自动同步。

程序负责记录、校验、核算和展示；Codex、Antigravity 等 agent harness 负责交互、截图理解和分析。用户从 harness 聊天界面发起 AI 工作，程序通过 MCP 提供工具，结果保存到本地。

### 1.1 已确认的使用原则

1. 允许只有一张截图和一句思路，先保存，不要求填完整表格。
2. AI 默认整理思路、检查矛盾和缺失信息，不主动执行独立标的研究。
3. 每轮最多追问一个关键问题；用户不回答也不影响保存。
4. 原图先保存；标的、方向、成交状态、时间、价格和数量等关键字段确认后才进入正式账本。
5. 复盘分别评价判断依据与实际执行，不用盈亏直接判定交易质量。
6. 交易原话、研究报告、AI 推断分别保存，后补分析不得伪装成下单前已有判断。
7. 导入研究报告只是增加参考资料；只有用户明确采用的观点才成为交易理由。

### 1.2 第一版范围

| 包含 | 后续阶段 |
| --- | --- |
| A 股普通股票的买入、卖出记录 | 加密合约、资金费、杠杆及强平核算 |
| PC 手动导入图片、输入文字思路 | 手机端、语音录入与自动转写 |
| AI 提取草稿、人工确认成交 | 自动读取券商账户、实盘下单 |
| 分批交易、费用、交易档案、基本绩效 | 全券商交割单自动适配 |
| 单笔复盘、用户主动发起的周期复盘 | 定时运行、主动推送 |
| 本地保存、检索、备份、交换资料 | 多设备实时同步 |

基金、可转债、期权等不能仅因代码相似就进入普通股票核算。截图包含不支持的资产时可以作为日记附件保存，核算状态标为不支持。美股及所谓“美股合约”的具体产品类型留到扩展阶段确认。

## 2. 与标的研究程序的边界

| 用户动作或问题 | 本程序负责 | 交给研究程序 |
| --- | --- | --- |
| “我因为突破买了，帮我记录。” | 保存原话、识别交易、整理理由 | 无 |
| “我说跌回平台就走，但后来没走。” | 对照计划与执行，记录偏离 | 无 |
| “截图能证明放量吗？” | 标记证据不足，提出待验证点 | 经用户要求，获取数据验证 |
| “这只股票现在还能不能继续关注？” | 保存问题或关联新报告 | 当前机会研究 |
| “当时的依据是否充分？” | 形成复盘结论，约束为当时信息 | 必要时辅助核验证据 |
| “过去类似操作常犯什么问题？” | 基于历史记录生成执行经验 | 将经验作为个人提醒引用 |

本程序不维护第二套行情、新闻或基本面研究管线。发现研究需求时，生成包含标的、交易周期、待验证问题、时间边界及资料引用的交接包，由用户主动交给研究程序。共享资料可读不等于自动发起研究。

## 3. 使用入口与界面

PC 应提供最小本地界面，建议使用仅绑定 `127.0.0.1` 的本地网页。具体 UI 框架不属于已经确定的需求。界面应能独立完成保存和确认，不依赖 AI 在线。

### 3.1 页面

| 页面 | 必须具备的内容 |
| --- | --- |
| 收件箱 | 图片导入、原图预览、提取状态、重复提示、失败重试 |
| 待确认记录 | 原图与字段并排、字段证据、人工修改、成交/委托区分、确认按钮 |
| 交易列表 | 按账户、标的、时间、状态、标签过滤，展示资料完整度 |
| 交易详情 | 操作时间线、成交、费用、原话、计划、报告关联、修订历史 |
| 复盘 | 单笔或周期报告，判断与执行分栏，未知项、证据和后续假设 |
| 数据管理 | 知识库路径、备份、导入导出、完整性检查、版本信息 |

AI 分析从 harness 发起。程序界面可以显示分析运行状态和已有报告，但第一版不嵌入 Codex/Antigravity 聊天界面，也不由按钮后台启动 harness。

### 3.2 最短使用路径

1. 用户将手机截图复制到 PC。
2. 在程序导入图片，或在 harness 中指定一张本地图片，由 MCP 导入。
3. 原图归档，产生 `capture`；若用户附带一句话，立即生成 `journal_note`。
4. harness 读取图片，提交结构化提取结果。程序生成或更新提取草稿。
5. 用户在程序待确认页查看原图与字段，修正并确认。
6. 程序原子创建 `execution`，关联相应 `trade_episode`，刷新账务投影。
7. 用户后续导入加仓、减仓、卖出图，重复同一流程。
8. 用户在 harness 中要求复盘；AI 调用程序计算与取证工具，保存报告。

用户还没确认成交时，可以进行日记整理和思路讨论，但不能把提取草稿计入已实现盈亏。

## 4. 截图导入与识别

### 4.1 支持的图片语义

| 图片类型 | 处理方式 |
| --- | --- |
| 委托提交、委托列表 | 保存订单意图，标记未确认成交 |
| 部分成交或已成交 | 提取实际成交信息；区分本次成交和累计成交 |
| 成交明细、交割明细 | 作为成交与费用的证据 |
| 持仓页面 | 保存持仓快照，不反推不存在的历史成交 |
| K 线、新闻、聊天笔记 | 保存研究或思路证据，不生成成交 |
| 混合页面 | 逐条拆分候选记录，各自确认；共享同一原图引用 |

不得根据“委托成功”“订单已提交”创建已成交记录。撤单不等于平仓；部分成交后的撤单不抹除已发生的成交。

### 4.2 提取字段

每个候选字段均包含值、证据引用、来源类型和不确定原因。可用置信度辅助排序，但置信度高不能跳过人工确认。

| 字段 | 要求 |
| --- | --- |
| 账户 | 关联本地账户 ID，不要求保存完整券商账号 |
| 标的 | 交易所＋证券代码；不能仅凭名称自动确定 |
| 方向 | `BUY` / `SELL`，识别不清为未知 |
| 状态 | 委托、部分成交、成交、撤单、未知 |
| 发生时间 | 保存截图真实精度；只有日期时不得虚构秒级时间 |
| 价格、数量 | 区分委托与成交；正数、格式及资产适配校验 |
| 成交/委托编号 | 有则保存；缺失为 null |
| 费用 | 保存明确披露的金额；未显示不等于零 |
| 币种 | A 股首版为 CNY，仍显式保存 |
| 图片区域 | 页/区域/原文片段，可定位回原图 |

### 4.3 去重与纠错

- 同字节图片通过 SHA-256 去重，但保留每次导入动作的审计信息。
- 不同截图可能覆盖同一成交，因此图片不同不代表成交不同。
- 优先使用账户＋券商实际成交编号识别重复；订单编号不能替代成交编号。
- 缺乏可靠编号时，时间、标的、方向、价格、数量仅构成重复候选，交由用户处理。
- 同一个委托的累计成交截图不能逐次累加为新成交。需要明细或用户明确确认增量。
- 已确认数据纠错创建新修订并记录原因；不直接覆盖原记录。更正导致持仓负数或后续卖出无成本时，整次更正失败并解释依赖。

## 5. 思路、计划与交易归组

### 5.1 三种不同内容

1. `journal_note`：用户原话和补充，不改写成更“专业”的说法。
2. `trade_plan`：从原话提出的候选计划，以及用户明确确认的计划。
3. `research_report`：外部研究参考，不自动转换成个人计划。

AI 整理文本可以作为独立生成版本，与原话并列。比如“跌回平台就走”可以提取为退出条件原文，但不能自动补成某个价格。

追问优先级：阻碍入账的事实缺失 > 影响交易归组的歧义 > 判断失效条件 > 其他复盘信息。每次只问一个关键问题。待确认记录缺关键事实时留在待确认状态，其他日记内容正常保存。

### 5.2 交易档案 `trade_episode`

一份档案表示用户认定的一次完整交易过程，不等同于一张截图或一笔成交。

- 首版一份档案对应一个账户、一个标的、一种方向（A 股普通多头）。
- 可以包含多次买入和卖出，归零后关闭。
- 首版同一账户、同一标的最多一个已确认持仓中的档案，避免同时维护多套成本归属。
- 归零后再次买入默认新建档案，不自动合并为上次交易。
- AI 可以建议关联，用户确认成交时同时确认归组。
- 同一成交只能属于一个有效档案，跨档案拆分成交属于后续能力。
- 历史持仓补录使用显式的期初持仓事件，注明来源、数量、成本和证据完整度。

档案状态为 `DRAFT`、`OPEN`、`CLOSED`、`ARCHIVED`。历史完整性、费用完整性和核算可用性是独立字段，不通过一个状态混在一起表示。

## 6. 账务与指标

### 6.1 第一版核算口径

采用档案内移动加权平均成本，使用 Decimal，遵循共享存储规范的精度和舍入约定。此口径用于个人复盘，不承诺与每家券商显示的摊薄成本完全一致。

- 买入：增加数量与成本；已确认买入费用计入净成本。
- 卖出：按卖出前平均成本结转；净已实现盈亏＝卖出收入－结转成本－卖出费用。
- 部分卖出：仅确认已卖出数量的盈亏，剩余持仓继续保留。
- 未知费用：可以显示毛盈亏或明确的部分费用口径，完整净盈亏为 null。
- 没有可确认成本的历史卖出：保留事实，核算标记不完整，不能把成本当零。
- 只有日期且买卖顺序影响核算：要求用户确认当日事件顺序，否则不输出确定成本。
- 分红、送转、拆股等公司行动首版不自动核算；遇到影响数量或成本的事件，标记账务待调整，不能继续宣称结果完整。

### 6.2 指标定义

| 指标 | 口径与前提 |
| --- | --- |
| 毛/净已实现盈亏 | 按卖出事件发生日期归集，费用完整度单列 |
| 完整交易盈亏 | 档案所有有效成交及费用累计，关闭时确定 |
| 胜率 | 费用和历史完整的已关闭档案中，净盈利档案数 / 有效档案总数；保本计入分母 |
| 平均盈亏比 | 平均盈利 / 平均亏损绝对值；缺一侧时为 null |
| Profit Factor | 总盈利 / 总亏损绝对值；无亏损时显示“不适用/无亏损样本”，不写 Infinity |
| 期望值 | 有效档案净盈亏总和 / 有效档案数，同时报告币种和样本数 |
| 持有时间 | 根据可用时间精度计算；仅日期时标为日级近似 |
| R 倍数 | 首版仅对具有入场前已确认风险金额、简单开仓且无追加买入的完整档案计算；其他情形 null |
| MAE/MFE | 需要匹配持仓期间与周期的行情数据；首版允许缺失，不从成交图推导 |
| 账户净值回撤 | 首版不提供完整账户回撤；缺净值、未平仓估值和出入金数据时不得用已实现盈亏曲线冒充 |

周期复盘同时展示两张不同口径的表：按卖出日期统计的期间已实现盈亏，以及按最终关闭日期统计的完整交易表现。前者不包含其他期间的卖出事件，后者可能包含以前期间的部分退出。两者不得相加。

每份指标快照必须记录核算版本、输入记录修订、统计时区、时间区间、排除记录及原因。前端与 AI 都引用同一程序生成的 `metric_snapshot`，不各自重新算账。

## 7. 复盘流程与报告

### 7.1 单笔复盘

1. 选择档案，锁定本次输入修订和时间边界。
2. 获取原话、事前计划、实际成交、当时已有研究及指标快照。
3. 区分当时可获得的信息和后来补充的信息。
4. 评价判断依据：事实是否有来源、假设是否明确、反证条件是否可执行。
5. 评价执行：与原计划对照，列出遵守、偏离、事后改变和无法判断的项目。
6. 分别说明结果与过程；正常执行后的亏损也可能属于计划内结果。
7. 提出少量具体的待验证改进假设，保存报告。

不得只凭连续亏损或频繁交易判定报复性交易。行为标签必须关联操作证据或用户原话，使用“可能模式”，资料不足时为未知。

### 7.2 周期复盘

第一版由用户主动指定日期区间。按交易周期、用户确认的策略标签、退出原因、执行偏离汇总。报告样本数、缺失率和排除条件；不因几个样本就宣布某策略失效。

若发现需要重新研究市场或标的，生成待验证问题；是否移交由用户决定。本程序不自动修改筛选条件或执行交易。

### 7.3 输出结构

`review_report` 至少包含：

- 本次复盘范围、输入版本、数据覆盖和局限。
- 交易结果，引用程序生成的指标快照。
- 判断依据评价，每项附证据和未知项。
- 执行评价，每项附原计划与实际操作。
- 可能行为模式、替代解释、待用户澄清的问题。
- 改进假设及后续观察条件。
- 作者 harness、模型（能够确定时）、Skill 版本、生成时间。

报告保存不等于用户认可。复盘提炼出的 `lesson_rule` 默认为 `PROPOSED`；用户接受后才成为正式个人执行提醒。报告与规则不得倒写历史计划。

## 8. MCP 与 Skill 的职责

两个 harness 通过同一套协议访问本地知识库。下列工具是目标接口，不是当前已安装的工具。通用参数、返回值、并发和错误遵循共享规范。

| 工具 | 作用 | 允许产生的修改 |
| --- | --- | --- |
| `journal_import_capture` | 复制原图、登记 capture | 附件及导入记录 |
| `journal_submit_extraction` | 提交/修订提取结果 | 待确认草稿 |
| `journal_append_note` | 保存用户原话或 AI 整理稿 | 新笔记或新修订，保留作者类型 |
| `journal_get_episode` | 读取完整档案和精确引用 | 无 |
| `journal_list_pending` | 列出待确认记录 | 无 |
| `journal_compute_metrics` | 按明确口径计算 | 新指标快照 |
| `journal_save_review` | 保存有证据引用的复盘 | 复盘报告新版本 |
| `journal_propose_lesson` | 提出个人执行经验 | `PROPOSED` 规则 |
| `journal_export_handoff` | 导出研究问题/复盘资料 | 交换包，不更改业务事实 |

成交确认、事实纠错确认、规则采纳、报告与交易关联由程序本地 UI 的确认流程完成。第一版不给通用 AI 工具提供可绕过确认的“直接成交入账”能力。AI 说“用户已确认”不能代替程序收到的确认事件。

交易复盘 Skill 的内容包括：触发场景、取证顺序、追问规则、报告结构、未知项处理、何时移交研究。Skill 不保存数据库、不重新实现盈亏公式、不把聊天历史作为唯一记忆。

## 9. 失败与恢复

| 情况 | 必须行为 |
| --- | --- |
| harness 未连接或暂时不可用 | 正常导入、浏览和人工录入；AI 工作保留为待处理 |
| 识别结果缺字段或格式无效 | 保存原图，返回字段级错误，不部分入账 |
| 模型分析中断 | 运行状态标记中断/失败，已有事实不受影响 |
| 报告保存超时、结果不明 | 用幂等键查询是否已保存，再决定重试 |
| 事实修改后旧报告仍存在 | 保留旧报告，标记输入已变化；重算生成新版本 |
| 多个 harness 同时改草稿 | 一个成功，另一个得到版本冲突并重新读取 |
| 导入包版本不兼容 | 拒绝导入并提示版本，不猜测转换 |

## 10. 验收场景

1. 导入一张委托成功图，系统保存原图及待确认草稿，但账本数量和盈亏不变。
2. 导入真实成交图，AI 提取后用户修改一个字段并确认；成交、作者、修订和原图关联均可追溯。
3. 同一图片导入两次不重复创建成交；同一成交的两张不同截图触发重复核查。
4. 用户只说“突破了先买点”，原话立即保存；AI 最多追问一个问题，未答仍可保存日记。
5. 分批买卖正确结转成本；缺费用时完整净盈亏为空，不显示为已核实净利润。
6. 上周部分卖出、本周卖完：事件盈亏和关闭档案统计按各自口径显示，无重复相加。
