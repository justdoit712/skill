# 共享数据存储与访问规范

版本：0.2.0（补充上游 Skill 适配存储）

协议目标版本：`schema_version = "1.0.0"`

日期：2026-10-10

状态：待实现。本规范是两个程序共同遵循的数据契约，不代表数据库或 MCP 已经部署。

关联文档：[交易记录与复盘程序](01-交易记录与复盘程序.md) · [标的研究程序](02-标的研究程序.md)

## 1. 范围、优先级和基本原则

本规范定义数据的归属、存放、身份、字段、版本、关联、查询、修改、交换、备份与恢复。两个程序和不同 harness 必须依据同一规范实现，不能各自创造同名字段的不同含义。

发生冲突时：用户已确认的产品要求优先；字段和协议问题以本文为准；业务流程分别以两个程序文档为准。实施中需要改变本契约时，同步更新三份文档和版本，不能只改一个程序。

核心原则：

1. 本地数据库是结构化事实的权威来源，原始附件按内容哈希保存。
2. Markdown、搜索索引、统计缓存和前端状态是可重建的派生物。
3. 已保存内容保留修订，引用精确版本，不随“最新版本”漂移。
4. 用户原话、用户确认事实、AI 推断、外部来源分别表达。
5. agent 通过受约束工具读写，不直接执行任意 SQL 或改数据库文件。
6. 不因共享存储而自动共享业务决定：读到报告不等于已关联，关联不等于采纳。
7. 本地保存与模型推理位置分离；使用云端 harness 时，本次提供给模型的内容仍可能发送到云端。

## 2. 物理目录与权威来源

知识库路径由用户配置，示例为 `D:\TradingKnowledge`。这是示例路径，创建时必须由程序实际配置解析。第一版放在 Windows 本机磁盘，不将运行中的 SQLite 放在网络共享或同步盘目录。

```text
<knowledge_root>/
  config/
    workspace.json
    upstream-skills.json
  db/
    knowledge.sqlite3
  objects/
    sha256/<前两位>/<完整哈希>
  exports/
    markdown/
    packages/
  cache/
    previews/
    search/
    adapters/<run_id>/
  staging/
  logs/
  backups/
```

| 位置 | 权威性 | 说明 |
| --- | --- | --- |
| `db/knowledge.sqlite3` | 权威 | 记录、修订、关联、审计、幂等与附件元数据 |
| `objects/` | 权威 | 原图、来源原文、结构化行情附件等不可变字节 |
| `config/workspace.json` | 工作区配置 | 工作区 ID、schema 版本、时区，不保存模型密钥 |
| `exports/markdown/` | 派生 | 方便查看报告；修改文件不会自动修改数据库 |
| `exports/packages/` | 交换产物 | 显式导入导出包，不是第二个在线数据库 |
| `cache/` | 派生 | 缩略图、全文索引等，可删除重建 |
| `staging/` | 临时 | 未完成的导入与文件落盘，不向正常查询暴露 |
| `logs/` | 诊断 | 不代替业务审计，不默认输出完整交易内容或密钥 |
| `backups/` | 恢复副本 | 数据库一致快照＋引用附件＋校验清单 |

程序代码、Skill 和 MCP 配置可保存在各自项目；私人知识库不放入当前开源 Skill 目录的 `data/`、`public/` 或 Git 跟踪范围。

## 3. 部署与访问模型

两个业务程序共享一个版本化的数据访问库（下称 Storage Gateway），所有数据库写入均通过该库。该名称表示统一实现边界，不要求首版额外部署常驻远程服务。

- PC UI 调用本地业务服务，业务服务调用 Storage Gateway。
- MCP 可以运行在独立的本地 STDIO 进程中，调用同一业务服务与 Gateway。
- 两个 harness 可以各自启动 MCP 进程，SQLite 事务负责本机并发串行化。
- 程序关闭 UI 不影响 harness 通过 MCP 读取本地库。
- 不同程序不得携带互不兼容的 Gateway 版本直接打开同一数据库。
- 配置握手返回 `workspace_id`、schema 版本、协议版本、可用工具和功能能力。

建议一个本地 MCP server 包同时暴露 `knowledge_*`、`journal_*`、`research_*` 命名空间。两个业务程序仍独立，共享的是协议和数据组件。未来拆分多个 server 不改变字段契约。

### 3.1 已有交易 Skill 的兼容数据

记录复盘程序优先复用 `trader-memory-core`、`weekly-performance-digest`、`trade-performance-coach`。这些组件的原生 YAML/JSON 不取代统一数据契约，也不能与 SQLite 成为两套同时接受事实修改的账本。

适配规则：

1. **固定组件版本**：`config/upstream-skills.json` 登记 component_id、仓库 URL、skill_path、实际 commit、Skill/脚本文件哈希、许可证核验结果、入口、adapter_version 和支持能力。未核验项明确标记 unknown；不能只写 HEAD 后声称可重现。
2. **生成运行输入**：从本地精确修订导出上游所需结构，临时工作目录位于 `cache/adapters/<run_id>/`。每个运行独立，不让两个 harness 写同一份 thesis 文件。
3. **保留映射证据**：输入清单包含原记录引用、上游 thesis_id 与本地 episode_id 映射、时间与币种转换、未提供字段、排除项和适配器版本。无法无损表达时应返回不兼容，不能静默丢失费用、追加买入或期初持仓。
4. **持久保存运行材料**：需要追溯的实际输入、映射清单和原始输出，均作为不可变附件进入 objects 并由 analysis_run 引用。临时缓存可清理，不能把唯一的映射证据放在缓存中。
5. **限制上游写入**：上游脚本只能写运行专属兼容目录；其输出经业务服务校验后才通过 Gateway 保存。禁止上游状态文件直接反向同步覆盖已确认成交。
6. **区分意图和事实**：如果复用上游状态命令，它产生的是待校验的状态变化建议，不能替代本地 UI 的成交确认。原生“开仓”命令不构成本地账本的授权事件。
7. **统一正式统计**：相同指标只能有一个正式核算实现。复用上游函数时，将其封装为本地有版本的 calculator；需要适配币种或成本时记录差异。上游原始统计可用于兼容对比，不直接覆盖正式 metric_snapshot。

上游组件源码建议放在新程序项目的依赖或 vendor 目录，知识库只存版本清单和实际运行材料。未来升级组件，先验证兼容再更新清单；已有运行仍引用旧版本。共享检索不要求另一个业务程序理解上游内部 YAML。

## 4. 记录归属与写入权限

| 记录类型 `kind` | 负责创建与维护的业务 | 其他业务的权利 |
| --- | --- | --- |
| `account` | journal | 读取必要字段 |
| `instrument` | shared | 两程序调用统一注册/校验 |
| `attachment` | shared | 通过导入接口创建及引用 |
| `capture`、`execution` | journal | research 只读 |
| `journal_note`、`trade_plan`、`trade_episode` | journal | research 只读 |
| `research_task`、`source_snapshot`、`research_report` | research | journal 只读或主动关联 |
| `review_report`、`lesson_rule` | journal | research 读取已接受规则及明确授权的资料 |
| `report_link` | journal 的用户确认流程 | research 只读 |
| `analysis_run` | 本次执行对应业务 | 另一业务只读 |
| `metric_snapshot` | 依指标命名空间确定 | 其他业务引用，不覆盖 |

`metric_snapshot.namespace = "journal.accounting"` 由 journal 核算服务写；`"research.features"` 由 research 计算服务写。两者指标名不能混用。

权限由实际工具处理器和调用通道决定，不能由 AI 在 JSON 中声明 `owner=journal` 就获得权限。MCP 默认只能创建交易草稿，不能确认成交。用户确认只能来自本地 UI 的确认操作及对应服务校验。

## 5. 标识、版本和公共封装

### 5.1 ID 与引用

- 工作区使用 UUID，记录使用带类型前缀的 UUID，如 `exe_<uuid>`、`rpt_<uuid>`。
- ID 全局唯一，不采用“代码＋日期”作为唯一键。
- `revision` 从 1 递增，同一记录类型不变。
- 所有结论、指标、计划采用和报告关联引用 `{record_id, revision}`。
- 列表查询可以取最新版本；证据链不能只存 `latest`。
- 外部导入保留原 ID；遇到相同 ID、相同 revision、不同内容，拒绝覆盖并返回冲突。

### 5.2 公共记录封装

每个记录修订包含以下字段，`payload` 根据 kind 应用不同 JSON Schema。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `schema_version` | string | 本记录 payload 所遵循的契约版本 |
| `record_id` | string | 稳定记录 ID |
| `kind` | enum | 第 4 节中的记录类型 |
| `owner` | enum | `shared` / `journal` / `research`，由服务填充 |
| `revision` | integer | 当前修订号 |
| `created_at` | datetime | 首次写入时间，不因业务时间回填而改变 |
| `updated_at` | datetime | 本修订保存时间 |
| `actor` | object | 来源通道、harness、模型、Skill 版本等 |
| `status` | string | 按记录类型约束的状态 |
| `supersedes_revision` | integer/null | 前一修订；首版为 null |
| `change_reason` | string/null | 已确认事实修订时必填 |
| `payload` | object | 该类型的业务内容 |
| `evidence_refs` | array | 精确证据引用与定位 |
| `content_sha256` | string | 规范化记录内容哈希，由服务计算 |

哈希输入为除 `content_sha256` 外的完整封装，使用 UTF-8、对象键按字典序、无无意义空白的规范 JSON；数组保持原顺序，拒绝 NaN/Infinity。协议中数值型金额使用字符串避免浮点序列化差异。

`actor.type` 为 `user`、`agent`、`system` 或 `import`。`harness` 和 `model` 允许 null；无法确认具体模型时不得猜测。harness 自报的模型标为 `model_identity_source="reported"`，与程序可核实身份区分。

### 5.3 时间、金额和缺失值

- 系统时间使用 UTC RFC 3339，例如 `2026-10-09T02:03:04Z`。
- 业务发生时间用 `occurred_at`；只有日期时 `occurred_at=null`、`occurred_on="2026-10-09"`、`time_precision="day"`，另存 `timezone="Asia/Shanghai"`。
- 时间精度：`second` / `minute` / `day` / `unknown`。不得为排序虚构时间。
- 记录业务时点、外部发布时间、采集时间、数据库写入时间各自独立。
- 金额、价格、数量、比率在协议中均为十进制字符串，币种使用显式代码。
- 普通股票数量为正整数字符串；其他资产精度由将来的资产规范决定。
- 成交价格保存来源精度；内部 Decimal 运算至少 28 位有效数字，不使用二进制 float。
- 首版 CNY 展示金额保留 2 位小数，舍入 `ROUND_HALF_UP`；中间成本运算不反复舍入，清仓时释放全部剩余成本并消除舍入残差。
- 券商已报告费用金额原样保存，不再估算覆盖；税费表不在首版写死。
- 0 表示明确为零，null 表示未知，空数组表示已知没有条目。缺失字段不能被默认填零。
- JSON 原生整数只用于 revision、计数等离散值，不用于金融数值。
- 时间区间统一使用起点包含、终点不包含的 `[start, end)`，同时存统计时区。UI 选择“10 月 1 日至 10 月 7 日”时转换为当地 10 月 1 日零点至 10 月 8 日零点，避免相邻周重复计数。
- `as_of` 表示信息截止时点，与期间终点不同；是否满足历史信息可得性还需来源证据，不能仅比较日期字符串。

## 6. 核心实体字段

以下为 1.0.0 必需语义。实施时必须提供对应 JSON Schema；顶层及已定义 payload 禁止未知字段，扩展数据统一放入具命名空间的 `extensions`，不能静默接受拼写错误。

### 6.1 账户与标的

`account.payload`：`display_name`、`broker_name`（可空）、`base_currency`、`masked_identifier`（可空）、`timezone`。不得要求原始账号或密码才能记账。

`instrument.payload`：`symbol`、`exchange`、`market`、`asset_type`、`currency`、`display_name`、`aliases`。首版 `market="CN"`、`asset_type="equity"`。交易所代码按配置的受控枚举如 `XSHG`、`XSHE`、`XBSE`，不以证券名称作唯一键。

同一标的的自然键为 `(market, exchange, symbol, asset_type)`。币种、名称等修订不会产生第二个标的身份；检测到资产性质变化需人工核验。

### 6.2 附件与截图

`attachment.payload`：`object_sha256`、`relative_path`、`media_type`、`byte_size`、`original_name`、`origin`、`retention_class`。

- 哈希对应原始字节；缩略图/OCR 文本不是原文件。
- 相同字节可共享对象文件，不同业务引用仍保留。
- MCP 返回受控附件内容或资源，不把任意本机路径作为可读取能力。

`capture.payload`：`attachment_refs`、`capture_type`、`account_ref`、`candidates`、`duplicate_candidates`。

`capture.status`：`IMPORTED`、`EXTRACTED`、`PENDING_CONFIRMATION`、`PARTIALLY_CONFIRMED`、`CONFIRMED`、`REJECTED`。图片多行成交分别有稳定 `candidate_id`，每个 candidate 保存确认后的 execution 引用，避免重跑时重复创建。

字段候选统一形式：`value`、`source_kind`、`evidence_refs`、`uncertainty`。`source_kind` 为 `ocr`、`user_input`、`agent_inference` 或 `import`；模型推断与图中实际文字不能合并。

### 6.3 已确认成交与期初持仓

`execution.payload` 必需字段：

| 字段 | 说明 |
| --- | --- |
| `event_type` | `FILL` / `OPENING_BALANCE` |
| `account_ref`、`instrument_ref`、`episode_ref` | 精确引用 |
| `side` | FILL 为 BUY/SELL；期初持仓为 BUY，但明确不是实际新增成交 |
| `quantity`、`price`、`currency` | 期初成本未知时 price 可空，并阻断完整核算 |
| `occurred_at`、`occurred_on`、`time_precision`、`timezone` | 按第 5.3 节 |
| `event_sequence` | 同精度时间内经用户确认的顺序；不影响计算时可空 |
| `broker_execution_id`、`broker_order_id` | 可空；两者不可混用 |
| `fees` | `status`、`items`、`total`；见下文 |
| `confirmed_by`、`confirmed_at` | 服务根据 UI 确认填入，不能由 agent 伪造 |
| `source_candidate_ref` | capture ID、revision、candidate_id |

`execution.status` 为 `CONFIRMED` 或 `VOIDED`，草稿只在 capture 中。`VOIDED` 以新修订表示；既有报告仍能读取原版本。

`fees.status` 为 `COMPLETE` / `PARTIAL` / `UNKNOWN`。只有 COMPLETE 才能认定 `total` 是全部费用；明确无费用时 `items=[]`、`total="0.00"`。PARTIAL 保存已知项目但 `total=null`，UNKNOWN 为 `items=[]`、`total=null`。项目包含类型、金额、币种、是否券商原文及证据；避免总费用与分项重复相加。

### 6.4 原话、计划与档案

`journal_note.payload`：`episode_ref`（可空）、`text_original`、`text_role`、`recorded_for_time`、`input_mode`、`derived_from_refs`。`text_role` 为 `user_original` 或 `agent_summary`；两者不共用同一条原话记录。用户修改原话仍需新修订。

`trade_plan.payload`：`episode_ref`、`horizon`、`entry_reason`、`invalidation_condition`、`exit_intent`、`initial_risk_amount`、`adopted_claims`、`confirmed_at`。未知条件为 null。状态为 `PROPOSED` / `CONFIRMED` / `SUPERSEDED`，是否事前计划通过真实确认时间与成交时间比较，不能手填一个布尔值伪装事前信息。

`adopted_claims` 每项包含研究报告精确引用、claim ID、用户确认采用的原文或表达、确认时间；不自动复制整份报告为计划。

`trade_episode.payload`：`account_ref`、`instrument_ref`、`title`、`horizon`、`strategy_tags`、`data_completeness`。成交归属以 execution 的 episode_ref 为权威，档案里不再保存第二份可独立修改的成交数组。数量及开闭状态由核算服务派生并受业务事务约束。

### 6.5 研究任务与来源

`research_task.payload`：`instrument_ref`、`question`、`horizon`、`mode`、`as_of`、`user_thesis`、`provided_refs`、`personal_context_refs`、`data_requirements`。周期由 `kind`、`user_text`、可空 `intended_days` 组成；不能只存一个含义不清的“短期”。

`source_snapshot.payload`：

- `source_type`：market_data / filing / news / user_document / webpage。
- `provider`、`url`（本地材料可空）、`title`。
- `published_at`、`available_at`、`retrieved_at`、`data_as_of`，未知为 null。
- `attachment_refs`、`excerpt`、`capture_completeness`（full / excerpt / metadata_only）。
- 行情适用字段：`instrument_ref`、`interval`、`price_adjustment`、`units`、`session_timezone`。
- `historical_availability`：verified / unverified / unavailable，并附证据。

外部原文变化创建新快照，不覆盖旧快照。来源快照的时间和版本是研究结论可追溯的基础。

### 6.6 报告、经验与运行

`research_report.payload`：`task_ref`、`run_ref`、`instrument_ref`、`horizon`、`as_of`、`input_refs`、`coverage`、`claims`、`invalidation_conditions`、`personal_reminders`、`body_markdown`。

`claims` 每项有 `claim_id`、`type`（fact / inference / hypothesis）、`text`、`evidence_refs`、`limitations`。报告状态 `COMPLETE` / `PARTIAL` / `WITHDRAWN`；撤回仍保留历史。

`review_report.payload`：`episode_refs`、`period`、`run_ref`、`metric_refs`、`input_refs`、`judgment_findings`、`execution_findings`、`behavior_hypotheses`、`improvement_hypotheses`、`unknowns`、`body_markdown`。

`lesson_rule.payload`：`text`、`scope`、`supporting_refs`、`sample_size`、`limitations`、`accepted_at`、`accepted_by`。状态 `PROPOSED` / `ACCEPTED` / `RETIRED`。默认研究提醒只采用 ACCEPTED；该状态不等于规则已统计证明有效。

`analysis_run.payload`：`purpose`、`task_ref`、`harness`、`model`、`model_identity_source`、`skill_version`、`tool_contract_version`、`input_refs`、`started_at`、`ended_at`、`output_refs`、`error`。状态 `STARTED` / `SUCCEEDED` / `PARTIAL` / `FAILED` / `INTERRUPTED`。用量不可取得时为 null，不把未知写成零。

调用上游 Skill 或适配脚本的运行还须保存 `upstream_components`（组件 ID、实际 commit、入口文件哈希、adapter_version）和 `adapter_artifact_refs`（实际兼容输入、映射清单、原始输出的附件引用）。没有调用则使用空数组。harness 使用的入口 Skill 版本与底层上游组件版本分别记录，不能用同一个 skill_version 混指两者。

`metric_snapshot.payload`：`namespace`、`calculator_version`、`input_refs`、`input_fingerprint`、`period`、`timezone`、`basis`、`values`、`excluded_refs`、`coverage`。快照不可原地修正，重新计算创建新记录。

### 6.7 主动报告关联

`report_link.payload`：`episode_ref`、`report_ref`、`relation`、`linked_by`、`linked_at`。`relation` 为 `reference_research` 或 `review_of`；研究报告关联仅作为参考。确认采用观点使用 trade_plan 的 adopted_claims，不能用 report_link 替代。

关联的是具体报告版本。新的报告版本出现后，原关联不自动升级；用户可新增关联。

## 8. SQLite 结构与索引

采用通用记录＋不可变修订保存规范化 JSON，减少两个程序各自设计不同表结构的风险。金额计算仍在 Python Decimal 层完成，禁止 SQL 中转换为 REAL 后计算。

| 表 | 关键列及约束 |
| --- | --- |
| `workspace_meta` | 唯一 workspace_id、schema_version、migration_version |
| `records` | record_id 主键、kind、owner、created_at、latest_revision、archived_at |
| `record_revisions` | (record_id, revision) 联合主键、envelope_json、content_sha256、created_at；JSON 合法校验 |
| `record_edges` | from_id/from_revision、to_id/to_revision、relation、locator；两端修订外键 |
| `object_files` | object_sha256 主键、relative_path 唯一、byte_size、media_type、created_at |
| `record_objects` | record_id/revision、object_sha256、role；外键约束 |
| `idempotency` | (workspace_id, operation, idempotency_key) 唯一、request_hash、result_json、committed_at |
| `audit_events` | event_id、time、actor_json、operation、record_id、before_revision、after_revision、reason |
| `confirmation_events` | confirmation_id、local_user、capture_revision、candidate_id、input_hash、execution_ref、confirmed_at |
| `execution_index` | execution_id 主键、latest_revision、账户/标的/档案 ID、时间、有效状态、broker_execution_id |
| `report_index` | report_id、revision、kind、instrument_id、horizon、as_of、harness |
| `search_index` | 记录 ID、revision、允许检索的正文和标签 |

`records.latest_revision` 与 `record_revisions` 在同一事务中更新；记录类型和 owner 不允许更新。`record_edges` 与 `record_objects` 从经验证的 envelope 构造，不能作为第二份可独立编辑的业务事实。

execution_index/report_index/search_index 是投影，可从权威修订重建；正常写入时同步更新，索引重建期间不能绕过权威版本校验。对有效的非空 `(account_id, broker_execution_id)` 建唯一约束，但必须先确认该券商编号作用域；若编号仅日内唯一，唯一键增加交易日并将 scope 记录在账户适配配置中。

记录引用未来可能回指旧版档案，这是正常的创建时上下文。查询一个档案的当前全部成交时，以稳定 episode ID 查询有效成交最新修订，不只读取当年档案创建版本。

## 9. 修改、确认与事务

### 9.1 通用写操作

1. 校验工作区、schema、工具权限和输入类型。
2. 验证所有精确引用存在，读取预期修订。
3. 对附件先完成内容哈希、临时写入和对象原子落盘。
4. 开始短数据库写事务，校验幂等键和 `expected_revision`。
5. 校验业务不变量、写新修订、关系、索引、审计和幂等结果。
6. 提交后返回新的精确引用；派生 Markdown 可在提交后生成。

SQLite 使用外键约束和 WAL 模式；每个连接启用 `foreign_keys=ON`，初始 `busy_timeout=5000ms`。写事务采用明确的短写锁策略，例如 `BEGIN IMMEDIATE`。重试有上限，耗尽返回 `STORAGE_BUSY`，不无限等待。

下载、模型推理、人工确认等待和图片处理不在写事务内进行。数据库文件不得由 AI 或另一套脚本直接改写。

### 9.2 确认成交的原子操作

UI 提交待确认 candidate 的 revision、人工修订字段、归组和本次确认 ID。服务验证确认事件对应当前内容哈希，原子完成：

- 创建 execution，或对已确认事实创建更正修订。
- 更新 capture 对应 candidate 的确认状态。
- 更新档案与持仓核算投影。
- 写 confirmation_events、审计及幂等结果。

任一步失败全部回滚。AI 提交 `confirmed_by` 文本不触发此流程。相同确认 ID 重试返回原成交引用。

### 9.3 文件与数据库一致性

对象文件以“同盘 staging 写入 → 校验 → 原子替换/放置”的方式先落盘，数据库随后登记。崩溃最多留下未引用对象，不应生成引用不存在对象的正式记录。

未引用对象由完整性检查列出，不能在首次发现时自动删除。备份期间停止清理。报告 Markdown 导出失败不回滚已经成功保存的报告，标记导出待重建。

### 9.4 并发与修订冲突

更新操作必须提供 `expected_revision`，否则拒绝；服务分配新 revision，agent 不自行指定新版本。两个 harness 同时修改时，后提交者得到 `REVISION_CONFLICT` 和当前版本，不执行静默覆盖。

不同分析运行的报告可以各自新建记录。对同一事实的更正要重放其后相关交易，导致无效持仓的更正不得部分生效。

### 9.5 幂等

所有变更工具必填 `idempotency_key`。相同操作、相同 key、相同规范化请求体返回原结果；相同 key、不同请求体返回 `IDEMPOTENCY_CONFLICT`。

请求哈希不包含传输层重试时间等易变元数据，包含业务字段、精确引用和 expected_revision。响应超时后先查询幂等结果，不能换 key 盲目重复写入。

## 10. 查询、MCP 返回值与错误

### 10.1 通用只读工具

| 工具 | 最小参数 | 返回 |
| --- | --- | --- |
| `knowledge_info` | 无 | 工作区、协议/schema 版本、能力 |
| `knowledge_search` | query、kind、filters、limit、cursor | 命中摘要、精确引用、下一游标 |
| `knowledge_get` | record_id、revision（可选） | 完整封装及引用；省略时明确返回已解析的最新 revision |
| `knowledge_get_attachment` | attachment_ref、representation | 原图/受控预览/文本，不能传任意路径读取 |
| `knowledge_get_operation` | operation、idempotency_key | 已提交结果或未找到 |
| `knowledge_find_dependents` | record_ref | 依赖旧记录的报告与指标 |

分页默认 20、最大 100；长附件按类型返回资源或分段，不默认将整个知识库灌入一次模型上下文。全文检索不自动等于语义相似；向量检索以后作为可重建索引添加。

### 10.2 通用变更参数与分析运行

业务变更工具统一接收 `schema_version`、`idempotency_key`、`payload`；更新现有记录时还需 `record_id` 和 `expected_revision`。创建时由服务分配 ID，响应必须返回准确 revision。工具名决定业务操作，不能在 payload 中自行指定任意 SQL、owner 或目标文件路径。

`knowledge_begin_run` 接收 `purpose`（research/review/extraction）、可空 `task_ref`、`input_refs` 和实际可取得的执行端元数据，返回新的 analysis_run 引用。`knowledge_finish_run` 接收 run_ref、expected_revision、结束状态、output_refs 和可空 error，更新该运行的结束信息。服务按 purpose 分配 owner，并核对输出类型。

调用顺序为开始运行、读取/追加输入、保存输出、结束运行。输出报告可以引用 run 的开始修订；run 的结束修订再引用输出，避免要求两个对象在创建前就互相存在。正式报告的 input_refs 必须记录其实际使用的全部输入，不能仅依赖运行开始时的初始清单。

进程异常退出后仍为 STARTED 的运行，经核实不再执行后标记 INTERRUPTED；不得仅因 UI 关闭就中断另一个活跃 harness 的工作。第一版使用进程/会话存活检查或用户主动结束，不引入未经实现的自动任务调度。

### 10.3 返回封装

```json
{
  "ok": true,
  "protocol_version": "1.0.0",
  "workspace_id": "<uuid>",
  "data": {
    "record_ref": {"record_id": "rpt_<uuid>", "revision": 1}
  },
  "warnings": [],
  "error": null
}
```

失败时 `ok=false`、`data=null`、error 含 `code`、`message`、`field_errors`、`retryable`、可空 `current_revision`。不将异常堆栈、密钥或完整私人路径作为默认错误输出。

### 10.4 错误代码

| code | 语义 |
| --- | --- |
| `VALIDATION_FAILED` | 类型、枚举、数值、时间或业务约束错误 |
| `UNSUPPORTED_SCHEMA` | schema 不兼容 |
| `NOT_FOUND` | 记录或精确版本不存在 |
| `MISSING_DEPENDENCY` | 保存/导入需要的关联记录缺失 |
| `REVISION_CONFLICT` | 乐观锁冲突 |
| `IDEMPOTENCY_CONFLICT` | 同 key 请求内容不一致 |
| `CONFIRMATION_REQUIRED` | 尚未经过本地用户确认 |
| `DUPLICATE_CANDIDATE` | 疑似重复需处理 |
| `STORAGE_BUSY` | 写锁等待超时 |
| `OBJECT_HASH_MISMATCH` | 附件损坏或交换包不一致 |
| `INSUFFICIENT_DATA` | 缺资料不能完成请求计算 |
| `UNSUPPORTED_ASSET` | 不支持该资产核算/研究适配 |
| `PERMISSION_DENIED` | 工具越过业务写入边界 |

错误不触发自动放宽 schema、不把缺失值补零、不绕过用户确认。

### 10.5 输入与展示边界

- 图片、网页、研究报告和导入笔记都作为业务资料处理；其中出现的“执行命令”“忽略规则”等文字不能成为工具权限或系统指令。
- UI 渲染 Markdown 时禁用原始 HTML 和脚本，链接只允许明确的受支持协议；本地附件经受控查看接口打开。
- 数据库使用参数化查询；过滤字段和排序键采用白名单。
- 原始文件名仅作展示，实际对象路径由服务根据哈希生成；导入路径必须解析为明确文件，不能按目录隐式遍历用户磁盘。
- 首版建议单张图片不超过 25 MiB、解码不超过 40 百万像素、单交换包解压总量不超过 1 GiB。将限额作为可查看的配置，超限明确拒绝，不截断原始证据后继续入账。
- 诊断日志记录操作 ID、错误代码和引用，不默认复制完整账户记录、截图或登录信息。

## 11. 证据、输入快照与过期判断

报告提交必须包含 input_refs，其中每个引用锁定确切修订；metric_snapshot 还需核算版本。服务验证报告中使用的证据属于声明输入或显式追加的来源。

证据引用的 locator 支持 `json_pointer`、`text_quote`、`line`、`page`、`image_bbox`；图片坐标必须声明像素或归一化坐标，并对应原图尺寸。没有定位能力时可引用完整附件，但标记粗粒度。

报告过期是根据输入最新版本与报告 input_refs 比较得到的展示状态，不修改历史报告内容。用户可以查看旧版、选择重跑或继续引用旧版。

个人知识的长期保留依赖记录和附件，不依赖 harness 的会话标题、上下文窗口或模型记忆功能。

## 12. 手动关联与交换包

### 12.1 共用同一本地库

用户在程序中选择已有报告版本并确认，创建 report_link。无需先导出再导入同一个文件。此操作依然属于手动关联，不由后台自动建立。

### 12.2 跨工作区或离线交换

交换格式使用 ZIP，包含：

```text
manifest.json
records/<record_id>/<revision>.json
objects/<sha256>
readable/<report>.md
```

manifest 必须包含 `package_version`、`package_id`、`source_workspace_id`、`exported_at`、`root_refs`、全部记录和对象的路径/大小/SHA-256、依赖清单及导出范围。

- 导出精确修订及其必需依赖；不自动打包整个账户历史。
- 第一版不支持“去掉必需证据后仍宣称完整”的包；用户可选择减少 root_refs，或者导出明确标记不完整、仅供阅读的 Markdown。
- 导入前预览来源、包含数据、重复项、冲突和缺依赖。
- 校验 ZIP 路径无绝对路径、`..`、符号链接等逃逸，校验解压大小上限及文件哈希。
- 相同 ID/版本/哈希跳过；内容冲突拒绝整个结构化导入，不覆盖。
- 原作者与原系统时间保留，另加本地 import 审计，不伪装为当前用户新写的内容。
- 先暂存并校验附件，再以单次数据库事务登记记录及依赖；失败不得留下部分有效记录。
- 导入不自动建立交易关联，不创建采纳观点或确认成交。

## 13. 备份、恢复与完整性

### 13.1 备份

使用 SQLite 一致性备份接口，不直接复制正在运行的 `.sqlite3` 文件来假定完整。备份流程：

1. 获取备份操作锁，阻止对象清理与 schema 迁移。
2. 通过 SQLite backup API 生成一致数据库快照。
3. 从快照读取引用对象集合，复制对应不可变对象。
4. 输出 manifest，记录工作区、版本、记录数量、对象数量、大小、哈希和完成时间。
5. 校验数据库和所有引用对象后标记备份成功，最后释放锁。

普通新写入可继续，但本次备份仅包含快照时点已引用的对象。不包含临时文件、缓存、harness 密钥或模型登录凭据。

### 13.2 恢复

先恢复到新的空目录并验证，停止两个程序及全部 MCP 写入后，才切换知识库路径。不得在正在使用的库上逐文件覆盖恢复。

校验包括 SQLite integrity_check、外键、对象哈希、引用存在性、最新修订一致性和账务重算。恢复测试要证明在无 AI 会话的情况下仍能读到交易、原图、报告及证据。

### 13.3 删除与归档

第一版默认归档，不硬删除已被报告引用的证据。用户确需永久删除时，由单独维护流程展示受影响记录并执行，不借普通 AI 工具悄悄删除。缓存删除不涉及权威资料。

## 14. Schema 升级与兼容

- 程序启动先握手检查 schema 和功能能力，旧程序不能静默修改新版库。
- patch 用于不改变字段语义的修复；minor 用于可协商的新可选字段/能力；major 用于破坏性变更。
- 因采用严格字段校验，旧客户端遇到新字段需由 Gateway 投影成其支持版本，或明确拒绝，不应声称所有 minor 自动兼容。
- 迁移前备份、停止写入并获取全局迁移锁；失败整体回滚或恢复，不留下半迁移状态。
- 旧 revision 保留原 schema；新版本读取通过明确适配器转换视图，不改写历史哈希。
- 两个程序、MCP、Skill 的版本分别记录。Skill 升级不等于数据库升级。

## 15. 数据级验收案例

### 15.1 核算案例

同一档案买入 100 股，单价 10，完整买入费用 5；再买入 100 股，单价 12，完整费用 5。总成本 2210，数量 200，平均成本 11.05。

随后卖出 100 股，单价 13，完整卖出费用 5：结转成本 1105，净已实现盈亏 190；剩余数量 100、成本 1105。再卖出 100 股，单价 11，完整费用 5：本次净盈亏 -10，完整档案净盈亏 180，剩余成本归零。

上述第一笔卖出与第二笔卖出跨周时，周事件盈亏分别为 190 和 -10，第二周关闭档案统计为 180。禁止将第二周的 -10 与 180 相加。

### 15.2 其他必须通过的约束

1. UNKNOWN 费用不被转换成 0，净指标不冒充完整值。
2. 重复确认、工具超时重试不创建第二笔成交或第二份报告。
3. 两个 harness 基于同一旧修订提交修改，只有一个成功。
4. 新报告引用原计划旧版本，计划后来变化不会静默改变该报告输入。
5. 执行事实更正产生审计，相关缓存失效，旧报告仍可追溯。
6. 相同标的跨账户不混算；不同币种指标不直接相加。
7. 导入恶意路径、哈希错误、引用缺失或 schema 不兼容的包全部拒绝。
8. 文件落盘后数据库提交前中断，只产生可诊断孤立对象，不出现半条成交。
9. Markdown 导出失败可重建，不丢数据库中的报告。
10. 从一致性备份恢复后，两个程序读取相同记录和版本，指标可复算。
11. 同时调用上游技能使用不同 run 目录；其 YAML 输出不会覆盖正式交易记录，清理缓存不丢实际运行证据。
12. 上游适配不能把 CNY 当成 USD、把未知风险或费用写成零；不兼容样本有明确错误或排除记录。

这些案例应合入未来项目对应的数据、账务和集成测试领域，避免为每轮设计新建碎片化测试文件。

## 16. 首版实施清单

1. 发布公共字段、各 kind JSON Schema、错误枚举和示例。
2. 实现 Storage Gateway、schema 检查、修订、关系、幂等、事务和对象导入。
3. 实现只读查询、附件读取、全文检索和备份恢复。
4. 由 journal 实现成交确认及账务不变量；由 research 实现来源和报告校验。
5. 封装 MCP 工具，对两个 harness 分别验证连接、图片读取和结果落盘。
6. 实现手动关联、交换包和依赖校验。
7. 按第 15 节验证一致性，再扩展资产与新数据源。

本文不要求首版建设向量数据库、云端知识库、跨设备同步或自动多模型调度。未来新增这些能力时，权威记录、精确版本和业务归属保持不变。
