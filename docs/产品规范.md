# Skills 导航目录产品规范

更新时间：2026-09-23

本文定义产品范围、业务规则与验收要求。当前用法与已知限制见 [运行说明](运行说明.md)，架构约束见 [架构约定](架构约定.md)，本轮实现与验证边界见 [修复验收记录](audit/2026-09-23-分层重构修复验收.md)。规范描述目标行为，实现状态由运行说明单独标注。

## 1. 产品定位

Skills 导航目录是公开的 AI Agent Skills 发现与比较工具。用户通过静态网页了解技能用途、中文简介、分类、评估依据和更新记录，再通过原始链接访问上游。

- 保存技能索引、简述、分类、评估依据、版本标识和更新记录。
- 运行时可读取上游 README、SKILL.md 及必要参考材料，用于识别与评估。
- 不下载、镜像、安装、启用或执行完整技能包，不提供聊天助手或技能运行服务。
- 主目录收录范围见第 3 节；针对具体需求的独立查找见第 12 节。
- 收录不等于经过功能实测或安全审计，来源身份与评估结论分别展示。

## 2. 运行模式

| 模式 | 目标与限额 | 数据边界 |
| --- | --- | --- |
| 目录周同步 | GitHub Actions 定时或手动触发；新增与重评每周合计最多 50 个，首次同样适用 | 共享周账本、队列和主目录，按发布链路生成站点 |
| 本地目录采集 | 默认新增 50 个推荐，允许评估更多候选；单次输入和输出合计最多 100M Token | 独立本地账本与候选池，更新目录；不自动提交或发布 |
| 定向查找 | 按具体需求生成短名单；受本次评估数与 Token 阈值约束 | 独立运行记录和前端查找报告，不修改主目录及其策略 |

本地采集达到目标、Token 阈值或候选用完时停止，不为凑数降低门槛。网络错误及临时 HTTP 错误允许首次失败后最多重连 5 次，共 6 次请求；重跑不重置已记录的尝试次数。未知用量按输入字节数、最大输出和消息余量预留估算预算，并与实际 Token 分列。重连次数用尽或最终响应仍缺用量时停止。

Token 阈值在每次响应后检查，最后一次请求可能超过阈值，不等于服务商账单的硬上限。相同材料、规则和模型配置版本的已完成评估可复用；结果不明的调用不能默认为免费重试。各模式的配置、启动方式和报告路径见运行说明。

## 3. 收录领域及边界

### 3.1 用途分类

| 主分类 | 收录内容 |
| --- | --- |
| 编程开发 | 前后端、重构、调试、测试、代码审查 |
| 文档办公 | Word、PDF、Excel、PPT 等 |
| 内容创作 | 文章、图片、视频、音频 |
| 产品与设计 | 需求分析、界面设计、原型 |
| 自动化 | 浏览器操作、文件处理、工具集成、工作流 |
| 云服务与运维 | 部署、CI/CD、基础设施 |
| 安全 | 漏洞检测、代码安全、审计 |
| 金融与投资 | 宏观、股票、期货、大宗商品及研究和策略辅助 |
| 心理健康 | 情绪记录、压力管理、心理健康信息理解 |
| 身体健康 | 睡眠、运动、饮食及身体健康信息理解 |

科研、通用数据分析、AI 开发不作为独立收录方向；直接服务上述用途的技能仍可纳入。例如股票数据分析归入金融，不因包含数据处理就排除。

支持一个主分类和多个用途标签。来源可信度、用途分类、适用平台分别记录。

### 3.2 金融与投资

不能仅按交易市场限定信息范围，需关注国内外事件及跨市场关联：

- 公司、行业、财报、公告和股票行情研究。
- 国内外宏观经济、货币与财政政策。
- 地缘政治、军事动向及经济影响，例如中东局势与石油供给。
- 期货、大宗商品、能源、黄金和白银。
- 利率、汇率及其与股票和商品市场的关联。
- 新闻采集、事实核验、事件跟踪和风险提醒。
- 选股、技术分析、回测、模拟交易、仓位和风险分析。

排除实盘自动下单类技能。地缘政治与军事信息在这里用于投资研究，不扩展为无关的军事用途目录。市场适用范围以上游材料为准，不默认只覆盖 A 股或某个交易市场。

### 3.3 心理健康与身体健康

覆盖日常管理和健康信息理解：

- 情绪、压力、睡眠、运动、饮食、习惯养成。
- 医学资料查询、体检指标解释、症状信息整理和就医准备。

不收录面向专业临床诊断、治疗决策的技能。金融与健康类评估规则需要专门设计，不能把盈利或疗效宣传当成质量证据，也不能把被收录解释为专业认证。

## 4. 来源与条目识别

### 4.1 来源层级

1. 核实归属的团队官方仓库作为基础。
2. 可信社区清单提供发现线索，追溯到原作者仓库。
3. GitHub 搜索主动发现符合领域的新技能，搜索规则与排除规则可配置、可逐步改进。

来源由 config/sources.json 配置；官方身份必须核验到具体团队与仓库，不能仅凭名称授予。

GitHub 是托管平台，不是所有技能的发布方。官方、社区、聚合清单必须区分，条目数量以当前索引为准。

官方开发团队列表不能代表全部领域来源。金融、心理健康、身体健康必须有独立的社区发现入口，不因缺少官方团队技能而放弃搜索或用开发技能充数。

### 4.2 识别粒度

- 优先识别有真实 SKILL.md 和任务说明的独立技能。
- 合集仓库尽量展开到具体技能，保留直达目录或说明文件的链接。
- 普通仓库、空模板、插件容器或整个合集不能直接计为一个独立技能。
- 多个来源指向同一技能时去重，保留全部发现依据。
- 不把上游 README 内出现的任意 GitHub 链接自动当作技能。
- DSH 插件无论由哪条渠道发现均排除。
- 不以某个 Agent 平台作为收录门槛。纯说明型技能和带辅助脚本的技能均可收录，只要满足用途和筛选要求；特殊工具、运行环境和依赖须明确标注。SKILL.md 能被读取不代表其依赖的工具在所有环境都可用。
- 不直接继承外部聚合的“可信”或“推荐”状态，聚合结果只作为发现线索。

### 4.3 来源覆盖与搜索配置

金融、心理健康、身体健康需有各自的发现入口，不能以开发类仓库代替全部领域覆盖。每个领域配置中英文查询和同义词；词语命中只用于发现，最终按实际材料识别用途。合集必须展开到技能文件后分别筛选。

config/sources.json 保存来源 ID、URL、来源类型、领域、发现方式和核验状态；config/searches.json 保存按领域的查询与排除条件。GitHub 查询需处理认证、返回页数和限流，不把部分结果称为完整搜索。

每轮报告按领域的发现、预筛、评估、推荐和覆盖缺口。没有合格条目的领域显示缺口，不伪造覆盖；可持续补充来源与查询，不以每类已存在推荐项作为采集前提。

## 5. 候选区与推荐区

### 5.1 流程

发现 → 去重 → 领域与类型预筛 → 待评估队列 → AI 简述、分类与评估 → 候选或推荐。

不符合领域、非技能、DSH 插件等应在调用 AI 前尽可能排除。超过每周额度的条目排队，不能仅因未轮到评估就判为低质量。

### 5.2 推荐原则

- 内容优先，Star、使用量、维护记录是参考信号，不设置统一硬门槛。
- 任务明确，步骤、依赖或示例足以支持对用途的理解。
- 来源可追溯，介绍和实际内容相符。
- 没有明显可疑行为或与收录范围冲突的功能。
- 官方技能也需识别用途、匹配领域，不无条件推荐。
- 信息不足、判断不确定或模型调用失败的条目不强行推荐。
- 展示推荐理由、主要限制、证据链接和未经实测状态，不用不透明分数替代说明。
- 已推荐技能的内容变化后，保留推荐状态并醒目标记“内容已变化，待复核”；展示原评估对应的版本及评估时间，不把旧结论视为对新版本的验证。复核通过后更新评估依据并清除标记，复核不通过则降级至候选区；确认不符合收录范围的条目移出活跃目录并保留状态变更记录。
- 等待额度或模型调用失败时保持待复核标记，不自动生成通过结论。
- 人工收藏（`config/overrides.json` 的 `manual_picks`）条目为例外：内容变化只在页面提示，不标记待复核、不自动重评、不自动降级，由用户自行决定是否移出收藏。

采用下述可测试的门槛规则，不使用未经校准的百分制“质量分”。规则根据样本维护版本；AI 辅助评估不等于功能测试或安全审计。

每次评估输出 `scope_match`、`purpose_clarity`、`instruction_completeness`、`evidence_traceability`、`dependency_transparency`、`risk_review`，每项为 `pass/fail/unknown`，附对应链接、文件位置或简短依据，另含 `domain_checks`、`reason_codes`、`rules_version` 和 `source_fingerprint`。纯文本技能明确无外部依赖也可通过依赖检查。

- 推荐阈值（普通查找，规则 1.1.0）：上述各项均为 `pass`，相关领域检查全部通过，并通过实际价值、可执行性、结果验证三项质量检查。通过项的引文须与原文完整连续行及行号匹配。拟推荐项由当前配置模型另发独立请求重新评估，不提供初评结论；两轮均通过且主分类一致才推荐。分歧或证据不足留在候选，网络/解析失败不当作质量判定。
- 质量标准按技能形态适配，不用篇幅、Star 或作者知名度替代判断；引用匹配不等于语义证明，两轮模型评估不等于功能实测。每个实际请求分别记录 Token，初评后预算耗尽或用量缺失时保存初评，下次仅继续复核。
- 候选：属于范围内但存在 `unknown`、说明不完整或尚需核验，注明原因；不得用模型自报置信度替代证据。
- 排除：明确不属于范围、非 Skill、DSH、实盘下单、临床决策、凭据外传等硬性拒绝项。普通说明质量不足不等于恶意。
- 网络、解析和模型错误属于处理失败，不当作质量判定；已有推荐按待复核规则处理。

金融专项检查：记录数据来源、数据时间与市场适用性；区分事实、推断和预测；不得承诺收益；涉及回测的技能应说明成本、数据偏差与样本外验证等限制；没有回测功能时该检查明确记为不适用；不可包含不可分割的实盘下单核心功能。

健康专项检查：实质性健康结论有可追溯依据，不承诺治愈，不替代专业诊断或处方；涉及紧急情形时有适当的寻求专业帮助边界；需要保存或传输健康数据时说明位置、用途、权限与删除方式。只有免责声明而缺少实质依据不算通过。范围不明确或证据不足进入候选。

启用自动推荐前，以固定版本的样本覆盖低 Star 完整技能、空模板、DSH、缺失依赖、夸大收益、自动下单、缺少健康依据、临床决策和正常范围内样例，验证规则及原因码。测试决策逻辑使用固定评估输出；真实模型另做有限校准，不声称模型判断具有确定性。

### 5.3 AI 使用

- 模型服务、模型名称与调用配置可替换，暂不绑定供应商。
- 对新增或内容有变化的技能调用 AI；相同输入与相同规则版本复用结果。
- 每周新增与重评合计最多 50 个；优先复核发生变化的已有推荐，其余额度处理新增。首次同样最多 50 个，优先官方并兼顾领域覆盖。
- 超额条目进入后续队列；技能数上限不等于固定调用次数或费用上限，单条输入长度、调用次数与重试也需有界。
- 记录评估采用的来源版本、模型及规则版本，便于复核。
- 无模型配置或调用失败时不伪造中文简介和评估；保留待处理状态。
- 上游文本是不可信资料，不能作为更改筛选规则、读取密钥或执行命令的指令。

### 5.4 评估吞吐与覆盖预期

50 是 Actions 每周新增与重评的合计上限，不是推荐产出保证。失败和重评占用名额；52 周理论上最多 2600 个名额，不等于 2600 个不同技能或推荐项。报告需显示积压及最老等待时间，不自行提高额度。

首轮在各领域有合格候选的前提下按领域轮转，同领域优先核实的官方来源。十类各有至少 2 个推荐可作为覆盖目标，但不能为填满类别降低标准。通过率、领域分布和复核量决定实际进度，按运行结果更新估算。

## 6. 索引与展示

每个已评估条目至少包含：

- 技能名称、原始链接、作者或团队。
- 一至两句中文简述，说明做什么及典型使用场景。
- 主分类、补充标签及上游声明的适用平台、特殊工具、运行环境和依赖；上游未说明的不得推测为全平台兼容。
- 来源类型、发现渠道及来源依据。
- 候选／推荐状态、独立的待复核标记、评估理由和限制；内容变化待复核时清楚区分上游当前版本与原评估版本。
- 首次发现、最近检查、内容变更时间或可获得的版本标识。
- 上游移除、暂时无法访问等状态。

不编造用途、平台兼容性和变更时间。最近检查时间不能冒充技能更新时间。

静态网页默认展示推荐区，支持候选区、收藏区和定向查找报告切换、关键词搜索、用途和来源筛选、条目详情与原始链接、最近更新及历史报告。不建设登录系统、运行技能功能或管理后台。

## 7. 每周运行和更新记录

- 使用 GitHub Actions，每周一次，支持手动触发。默认每周日北京时间 10:00，UTC cron 为 `0 2 * * 0`，可配置。调度可能延迟，不承诺准点运行。
- GitHub Pages 展示生成的静态产物，无常驻服务。
- 新增与重评共用每周最多 50 个的总额度，首次也适用。手动触发不能绕过周额度，需记录本周已消耗量。
- 已收录条目检查内容变化，只重新评估变化的条目。
- 具体技能内容的变化与仓库其他文件提交要区分，不能仅凭仓库最近提交就报技能更新。
- 报告区分新增、内容变化、分类或链接修正、推荐状态变化、上游移除及采集失败。
- 网络失败时保留上次有效数据，不做批量删除或虚假下架。
- 公共索引和网页使用同一数据来源，避免重复维护。
- API 密钥、认证头和含凭据的请求信息不进入日志、仓库或网页。
- 同步和部署任务需明确串联，确保每周生成结果确实发布，不能仅假定自动提交必然触发另一个任务。

### 7.1 站点与部署边界

- 项目仓库为 justdoit712/skill，目标站点为 https://justdoit712.github.io/skill/；实际发布状态以 Pages 环境和部署验证为准。
- 网页相对资源、数据请求、canonical、sitemap、robots 和 README 链接应正确支持 /skill/ 子路径。不在站点中硬编码无关域名。
- 当前不使用自定义域名，public/ 不生成 CNAME；需要自定义域名时须明确配置所有权与部署目标。
- 只修改本项目有权管理的仓库、部署和域名设置，不修改第三方基础设施。
- 仓库中的 vercel.json 与 .vercelignore 是否使用，需根据本项目实际部署绑定确认；不能仅凭文件存在判断线上状态，也不能未核验即删除部署配置。

### 7.2 同步、持久化、生成和部署的完整链路

采用同一次顶层 workflow 中显式依赖的处理与部署步骤，不靠机器人提交触发第二次 `push`。GitHub 说明 `GITHUB_TOKEN` 触发的普通 push 不会启动新 workflow：[官方说明](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/trigger-a-workflow)。

1. **检出与预检**：同步入口完整检出用户仓库目标分支，包含 `src/`、`config/`、`data/` 和 `public/`。校验配置、密钥存在性、仓库写权限及数据结构。未准备好不调用付费模型。
2. **发现与预筛**：更新候选队列和上游指纹，不把待处理条目直接推荐；读取当前周的持久额度。
3. **预留额度**：在模型调用前，把本批名额预留写入 `data/state/` 并成功 commit/push；失败则停止付费调用。详情见 7.3。
4. **评估和生成**：处理本批条目，更新唯一索引 `data/catalog.json`、队列 `data/queue.json`、额度及运行记录 `data/state/`、更新报告 `data/reports/`。由这些数据在本 job 生成 `public/data/`、报告页面与构建清单。模型失败也要记录，不抹除上次有效条目。
5. **验证与提交**：验证索引、链接、分类、额度和页面结构；明确提交范围为 `data/catalog.json`、`data/queue.json`、`data/state/`、`data/reports/` 及生成的 `public/` 内容。自动任务不改代码、规则、README 或密钥；提交前审核状态和差异，禁止无差别 `git add .`。代码和配置由开发提交。
6. **发布同一产物**：数据与页面提交成功后，从同一工作区上传已经生成的 `public/` Pages artifact，携带此次数据提交 SHA 和索引摘要。部署 job 通过 `needs` 或可复用 workflow 显式接收该产物；不重新检出另一版本的 `public/`，不在缺少数据和生成器的环境构建。
7. **部署验证**：记录部署结果与 artifact 对应 SHA，验证 `/skill/` 下的数据和页面。提交成功而部署失败时可仅重试部署该产物，不再次评估技能；产物过期则完整检出指定 SHA 后仅生成页面再发布，不调用模型。

`.github/workflows/sync-skills.yml` 作为顶层入口；`.github/workflows/deploy-pages.yml` 作为显式调用的 `workflow_call` 发布流程。人工代码 push 或仅发布请求走同一顶层入口的“仅构建／发布”分支，读取持久索引，不消耗 AI 额度。避免两个独立部署入口发布不同版本。

写数据与部署的顶层运行共用固定 concurrency group，`cancel-in-progress: false`；被调用的部署 workflow 不再申请同一锁，以免相互阻塞。额度仍以仓库状态为准，不能把 Actions 排队当作账本。遇到用户同时 push，使用正常非强制提交；push 冲突时停止后续付费调用并重新加载状态，不能覆盖他人的提交。

仅写数据步骤使用 `contents: write`，部署步骤使用 `pages: write` 与 `id-token: write`，其余最小读取权限。Fork 投稿及 PR 测试不获取模型密钥、不执行上游技能，正式带密钥流程只运行用户可信默认分支的代码。

### 7.3 周额度与失败恢复

- 以 `Asia/Shanghai` 的周一 00:00 起算一周，使用带年份的 ISO 周标识，例如 `2026-W38`；定时、手动和重跑共享账本，不提供“绕过额度”输入。
- `data/state/budget.json` 记录周标识、上限 50、已预留名额及对应评估 ID。评估 ID 包含技能稳定 ID、内容指纹、规则版本与模型配置版本；不同目标版本的重评也消耗名额。
- `data/state/evaluations/` 记录预留、调用尝试、完成／失败状态及输出摘要；记录无密钥、无个人健康或交易账户信息。
- 先持久化本批预留再调用模型，批处理异常或 runner 被终止也不释放已预留名额，以保守方式防止再次获得 50 个。已完成 ID 复用结果，未知是否成功的调用标为待恢复，不静默免费重跑。
- 设计默认每个名额最多 2 次调用尝试，首次与重试都在调用前持久化尝试计数；失败／超时后仍占本周名额。手动重跑不重置尝试计数。失败任务可下周重新排队并占新周名额。
- 网络请求、来源检查不占 AI 名额。`dry_run` 只验证配置、读取和计算计划，不调用模型、不写账本、不提交、不部署。若要付费试跑，必须走正式额度预留流程。
- 验证包括：新 runner 读回账本、同周两次手动运行、并发触发、预留后崩溃、模型超时、push 失败、周边界和跨年周标识；总预留不得超过 50。

### 7.4 配置、密钥及依赖边界

| 文件／位置 | 保存内容 |
| --- | --- |
| `config/sources.json`、`searches.json`、`taxonomy.json`、`rules.json`、`overrides.json` | 无密钥的来源、查询、分类、规则和人工覆盖，全部可提交 |
| `config/model.example.json` | 不含凭据的接口、模型名、超时、token 上限和重试配置示例 |
| GitHub Secrets／运行时环境变量 | `LLM_API_KEY` 等模型凭据；GitHub 访问使用最小权限的运行时 token |
| `.env.example` | 仅变量名和占位符，可提交 |
| `.env`、`.env.*`（`.env.example` 除外）、`config/*.local.json` | 本地私密配置，由实际 `.gitignore` 规则排除，不只是注释 |

凭据只从运行时环境或被忽略的本地配置读取，不与可提交配置混存。发现已提交的真实凭据时先撤销或轮换；忽略规则不能撤回已提交内容，不自动重写 Git 历史。

运行依赖为 requests（HTTP）和 PyYAML（安全解析元数据）；JSON、时间与静态产物生成使用标准库。开发测试依赖单独管理，依赖版本通过环境安装和检查后确定，不引入不需要的常驻服务或调度框架。

### 7.5 README、投稿模板与公开产物

- README 由维护者编辑，介绍产品、入口和文档；全量技能数据及每周结果写入索引、报告和页面，不由采集任务改写 README。
- 投稿模板分类与 config/taxonomy.json 的十个主分类一致，其余用途通过标签表达。
- 必填技能名称、具体 SKILL.md 或技能目录链接、原始作者/仓库、来源类型、用途、主分类、依据和依赖说明；许可未知时明确记录，披露金融、健康或交易执行能力。
- 投稿只创建待检查记录，不直接进入推荐区或证明官方身份。公开文案与实际状态一致。

## 8. 页面与内容边界

页面只提供技能浏览、搜索、筛选、详情、原始链接、人工配置草稿和运行报告。不包含无关聊天演示、项目推广、站群导航、二维码广告或技能包下载入口。

展示数量从页面数据计算，不硬编码宣传数字。主导航统一使用 public/index.html，不维护重复的技能列表页面。页面资源必须位于发布目录内；robots、sitemap 和 canonical 使用本站地址。上游文本和模型输出作为数据处理，正确转义文本并校验链接来源。

代码适用根目录 LICENSE，文字、分类、简述及评估等内容适用 LICENSE-CONTENT.md。外部技能仍适用各自原始许可，条目应记录可确认的来源和许可信息。引用或复用外部内容时保留其适用的署名与许可。

## 9. 验收标准

1. 来源、查询、领域、排除规则和人工配置可维护，条目定位到独立技能，去重保留来源依据。
2. 推荐、候选、收藏互斥；推荐依据可追溯，不把低 Star、新发布或未轮到评估等同于低质量。
3. 内容变化后的待复核、历史评估版本与人工收藏例外符合第 5 节，失败不生成通过结论。
4. 主目录遵守第 3 节范围，金融和健康专项检查有效，定向查找使用第 12 节独立契约。
5. 条目包含中文简介、分类、明确声明的依赖及版本时间，不编造用途和平台兼容性。
6. Actions 首次、定时、手动和重跑共享每周 50 个名额；本地与定向运行使用各自限额及账本。
7. 请求前记账、失败保留有效数据、结果未知时保守恢复；不会因页面缺失自动重新付费评估。
8. 索引、报告与页面来自对应快照，同步和发布使用同一产物，发布失败可独立重试。
9. 不执行上游技能，不镜像技能包，不泄露凭据；页面链接、署名和许可信息正确。
10. 边界行为以离线业务测试验证；真实网络/模型验收单独记录范围和限制，不用测试数量代替功能验收。

## 10. 配置与人工维护

### 10.1 配置职责

### 10.2 配置变更与运行前检查

变更评估语义时维护规则/模型配置版本，并明确历史结果的兼容方式。新增字段与旧缓存缺字段、明确空值分别处理，不能批量改 ID 导致无意重评。

## 12. 定向查找特定需求 Skill

本节合并独立查找方案中的有效产品约束，与目录业务分别适用。技术修复、读取上限和版本契约见 [架构约定](架构约定.md)；命令、配置默认值与当前限制见 [运行说明](运行说明.md) 第 10 节。

### 12.1 目标与隔离边界

用户输入具体需求，程序搜索 Skill、读取实际材料、比较需求匹配程度与说明质量，生成可供用户选择的短名单。例如“生成高质量 Prompt”，不要求先选择目录大类。

- 本次查找跳过主目录分类、来源排除、关键词排除、六项收录判据、人工屏蔽和冷冻规则；本节优先于仅针对主目录的领域限制。
- 不加载目录种子或全量领域搜索配置，不临时清空或篡改目录全局策略实现隔离。
- 不修改主目录条目、候选池、队列、周额度账本及人工配置，不自动安装或执行技能。
- 使用现有 Python、GitHub HTTP 与模型传输能力，不新增运行依赖或跨任务缓存。
- 查找结果独立保存；允许生成前端查找报告，报告投影与远端发布是不同步骤。
- “高质量”是对材料中的需求适配与说明质量的判断；未经执行不能声称通过功能实测，不能用名称、星数或模型分数宣称全网最佳。

### 12.2 需求计划与发现

保留原始需求，运行开始时固定计划，所有候选按同一标准比较。计划包含 `intent`、最多 8 个 `queries` 和带唯一 `id`、`kind`、`description` 的 `criteria`。

只有用户明确要求的能力属于 `required`；说明中的优点属于 `quality_signal`。不能把质量观察项升级为硬条件，也不默认指定模型、平台或编程语言。以“生成高质量 Prompt”为例，生成提示词是必需能力；澄清信息、组织输出格式、优化迭代可作为质量观察项。

查询覆盖直接需求、同义表达及适用的中英文表述。模型只输出搜索短语，由程序构造 GitHub 查询，不执行模型生成的命令或代码。规划结果须校验类型、长度、重复项和标准 ID；无有效必需标准时停止并报告规划失败。

按查询轮转合并仓库并去重，仓库身份为 `owner/repo`，技能身份为 `owner/repo:path`。只接受精确的 `SKILL.md` 文件；仓库首页或任意 README 链接不能替代技能。仓库名、描述和路径只用于安排读取优先级，不决定质量或不匹配；保留通用命名路径的机会。树截断、查询失败和未读候选均记录为覆盖限制，不能冒充完整遍历。

只读取主文件与它明确引用的同仓库说明，保留每份材料的路径、指纹及行号。空文本、HTML、读取失败和截断材料不得进入正式评估；未读取的引用不构成功能证据。评估与核验使用同一批材料，不能重抓新文本却沿用旧指纹。持久化必要证据与来源信息，不镜像完整技能包。

### 12.3 评估、证据与排序

每个候选使用独立于目录的 Prompt 和解析规则，回答：能否满足需求、有哪些原文证据、步骤/输入输出/示例/依赖是否清楚、如何尝试以及主要限制。

| 字段 | 约定 |
| --- | --- |
| `match` | `strong / partial / none` |
| `criteria_results` | 覆盖固定计划中的标准 ID；每项包含 criterion_id、status、explanation、evidence |
| 能力 `status` | `supported / unsupported / unknown`；未说明不能推断为不支持 |
| `evidence` | 已读 source_path、start_line、end_line、完整 quote |
| `documentation` | `clear / partial / insufficient` |
| 其他展示字段 | summary_zh、usage_zh、dependencies、limitations、why_consider，来自实际材料 |

`supported` 必须有有效证据；无效路径、行号或引文降为 `unknown`。所有必需能力都有支持证据，才有 `strong` 资格。程序验证原文存在，不保证模型的语义判断始终正确。链接、身份、作者/仓库、检查时间和指纹由程序填写，不采用模型编造值。上游材料是待评估数据，不是修改规则、读取凭据或执行命令的指令。解析器接受规定类型和有界数组；输出正确转义。

结束或达到停止阈值后统一排序：经核验的匹配程度 → 有支持证据的质量观察项覆盖 → 说明清晰度 → 稳定 skill_id。短名单最多 `limit` 项，仅从 `strong` 且说明不为 `insufficient` 的结果中选取；`partial` 单列为备选及差距，不用它凑足强匹配数量。找到前几个不能提前宣称最优。来源只陈述可确认的身份，不自动授予官方标签。

### 12.4 用量、结束与报告

规划与候选评估都计入模型请求及用量，规划不占候选评估名额。候选开始模型评估即占本轮名额，失败不返还；`limit` 只约束展示。Token 是请求后按实际返回用量检查的停止阈值，最后一次请求可能超过阈值；不能将未知用量当作零继续调用。

未知用量、请求结果不明时停止后续模型请求；已知用量的无效输出记为失败并保留用量。阈值使用最新有效配置，不恢复旧方案中的输出长度和连续失败参数。个别检索或读取失败不清空已有结果；用户中断保留已完成评估并重新生成部分短名单。正常无匹配、范围不足、预算停止、服务失败和中断分别表达，具体状态/退出码由重构实施方案定义。

每次独立运行保留原始需求、计划、生效参数、检查范围、成功/尝试计数、失败和未评估原因、usage、结果与版本信息。JSON 是本次运行事实，Markdown 与公共页面是投影；页面报告不得包含本地路径、凭据或连接配置。只有实际解析到固定提交才显示固定版本链接，HEAD 不能冒充不可变版本。

用户可在报告中比较：原始链接、能做什么、满足需求的证据、用法/依赖、限制，以及备选与需求的差距。无足够结果时如实说明范围和原因。实际验收场景仍为“生成高质量 Prompt”，其离线反例、排序和有界真实验收要求纳入重构实施方案。
