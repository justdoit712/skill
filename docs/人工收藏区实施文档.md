# 人工收藏区 实施文档

依据：`docs/Skills导航目录二开需求.md` §7.4（`config/overrides.json`）、§10.1（人工覆盖不能被静默覆盖）、§6（不建设管理后台）。
状态：**方案已定，尚未实施**。本文只规定做法，不代表代码已改。
面向：实施者（改代码的人）；也供用户核对是否符合预期。

---

## 1. 需求（用户已确认的四条决定）

| # | 决定 | 含义 |
|---|---|---|
| 1 | **三区并列** | 推荐区、候选区、人工收藏区是三个平级分区，人工区不是推荐区的子集 |
| 2 | **互斥** | 一个技能进了人工收藏区，就不再出现在推荐区或候选区 |
| 3 | **两个区都能收录** | 推荐区和候选区的条目都可以被人工收进人工收藏区 |
| 4 | **不自动移走 + 给出删除接口** | 上游内容变化、自动结论降级、甚至被判成硬性排除项，都不自动把它移出人工区；由用户通过删除接口自己移除 |

补充约定（本文档提出，实施前请一并确认）：

- 人工收藏**不受重复审查影响**：程序照常检查内容有没有更新，但**绝不因为更新而自动重新评估、自动降级或自动改写它的结论**。
- 人工收藏**不消耗模型额度**：只多花几次抓取（不调用模型），用来如实记录"上游是否变了"。
- 索引里的人工收藏条目**不得出现假数据**：内容指纹、最近检查时间照常刷新，不做"冻结"。

## 2. 术语与命名

| 名词 | 含义 |
|---|---|
| 人工收藏 | 用户手工指定、长期保留的条目 |
| 自动结论 | 程序按 §5.2 六项检查得出的 `recommended` / `candidate` / `excluded` / `processing_failure` |
| 人工层 | 覆盖在自动结论之上的标记，**不修改**自动结论本身 |
| 冻结区 | 本文**不采用**的做法：进区后停止检查、指纹与时间原地不动 |

页面用词统一为「**收藏区**」（比"人工区"更像用户语言）；文档与配置里用「人工收藏（manual pick）」。三处措辞必须一致，避免页面、文档、配置各叫一个名字。

## 3. 数据契约：`config/overrides.json`

新建文件，随 git 提交，**不含任何凭据**（§7.4）。

```json
{
  "overrides_version": "1.0.0",
  "source": "docs/人工收藏区实施文档.md",
  "note": "人工收藏名单：这里列出的技能只由用户手工维护。程序不得自动增删、不得自动降级、不得因此重新调用模型。删除条目即等效于用户主动移出收藏区。",
  "manual_picks": [
    {
      "skill_id": "anthropics/skills:skills/skill-creator/SKILL.md",
      "name": "skill-creator",
      "from": "candidate",
      "added_at": "2026-09-21",
      "reason": "自己试过，生成技能骨架的结构合我习惯"
    },
    {
      "skill_id": "vercel-labs/agent-skills:skills/react-best-practices/SKILL.md",
      "name": "react-best-practices",
      "from": "recommended",
      "added_at": "2026-09-21",
      "reason": "推荐区里讲依赖版本最清楚的，先收着"
    }
  ]
}
```

### 3.1 字段

| 字段 | 必填 | 说明 |
|---|---|---|
| `skill_id` | ✅ | 必须与索引中的 `skill_id` **完全一致**（稳定 ID，格式 `owner/repo:path`） |
| `name` | — | 仅供人阅读；与索引不一致时以索引为准，并在校验里给出提示 |
| `from` | — | 收录时的来源分区（`recommended` / `candidate`），仅作记录，不影响行为 |
| `added_at` | ✅ | ISO 日期（`YYYY-MM-DD`），用于排序与审计 |
| `reason` | ✅ | 收录理由。§10.1 要求覆盖配置保留理由，**空缺即校验失败** |

### 3.2 校验规则（预检阶段执行，失败即中止运行）

1. `skill_id` 非空、格式合法（含 `owner/repo`，允许带 `:path`）。
2. `skill_id` 必须在**当前索引或本轮候选中存在**；否则报错并列出该 ID，提示"拼写错误或该技能尚未被收录"。
3. `added_at` 可被解析为日期；`reason` 非空字符串。
4. 同一 `skill_id` 不得重复出现。
5. `overrides_version` 缺失时按 `1.0.0` 处理并给出警告；未知字段忽略但记录警告。
6. 校验失败**不降级为警告**：宁可停下让人修，也不能带着坏名单跑一轮付费评估。

## 4. 行为规则（实施的核心）

### 4.1 人工层不改自动结论

判断只做一件事：条目是否在 `manual_picks` 里。在，就给它打上标记；**不在，一切照旧**。

- `decide.py` **不改**：它是纯函数，仍然是"六项检查 → 自动结论"，保持可单测。
- 新增一个"读 overrides → 返回 `skill_id` 集合"的函数，由 `pipeline.py` / `local_run.py` 在生成条目时把标记写进条目。

### 4.2 条目新增字段

索引条目（`data/catalog.json`）与页面数据各增加：

```json
"manual_pick": true,
"manual_note": {
  "added_at": "2026-09-21",
  "reason": "自己试过，生成技能骨架的结构合我习惯",
  "from": "recommended",
  "auto_status": "candidate"
}
```

- `manual_pick`：是否人工收藏。
- `manual_note.auto_status`：**被覆盖掉的自动结论**。这样"删除收藏"后能立刻回到原本该在的分区，也让页面能如实说明"程序本来把它判为候选区"。
- 自动结论字段（`status`、`reason_codes` 等）**保持原值不动**，页面只是优先按人工层归区。

### 4.3 分区归属（互斥）

页面数据生成时按以下顺序判定，**命中即停**，保证一条只进一个区：

```
1. manual_pick == true            → 收藏区
2. status == "recommended"        → 推荐区
3. status == "candidate"          → 候选区
4. status == "pending"            → 不计入三区（未评估，只进统计）
5. status == "excluded" / "processing_failure" → 不计入三区（只进统计）
```

推论（必须实现并测试）：

- 收藏区的条目**不出现在**推荐区、候选区。
- 计数互斥：`recommended` / `candidate` 两个计数**不含**收藏条目；新增 `manual` 计数。
- 页脚统计行显示为：`推荐 N · 候选 M · 收藏 K · 未评估 X · 处理失败 Y`。

### 4.4 内容变化：只提示，不自动处理

人工收藏条目的内容指纹照常计算与更新，`content_changed_at` 在**首次检测到变化时**写入（沿用现有语义，不刷新）。

- **不重新评估**：即使评估 ID 变了，也不为它调用模型。
- **不改状态**：不因内容变化把它降级成候选，也不清除它的人工标记。
- **不覆盖人工纠正**（§10.1）：`needs_review` 的自动标记对它**不生效**，改为在页面上显示一条中性提示："上游内容已变化（日期），尚未复核；本条为人工收藏，程序不会自动重评。"
- 抓取失败时**保留上一次的指纹与提示**，不写"已检查无变化"（避免假数据）。

### 4.5 自动结论变差也不移走

| 自动侧发生什么 | 人工收藏条目怎么办 |
|---|---|
| 被自动判为候选区 | 仍留在收藏区，`manual_note.auto_status` 更新为 `candidate` |
| 被自动判为硬性排除项（如 DSH_PLUGIN、LIVE_TRADING） | **仍留在收藏区**，但页面必须显示醒目警告条："程序判定为排除项（原因码），本条为人工收藏，请自行确认风险" |
| 评估处理失败 | 仍留在收藏区，页面显示"评估未完成"，不隐藏、不伪造简述 |
| 上游仓库删了/404 | 仍留在收藏区，显示"上游不可访问（日期）"，不自动删除 |

### 4.6 抽查：抓取名额的分配

收藏条目要能发现"上游变了"，就必须被周期性抓取。抓取**不占模型额度**（§7.3），但要有上限。

- 新增配置项（建议放 `config/rules.json` 的 `run_limits`）：`max_manual_checks_per_run`，默认 **10**。
- 排序优先级：**收藏条目优先于普通抽查**（它变化与否是用户最关心的），但仍排在"已知内容变化待复核"的条目之后。
- 名额不足时不抓，下轮再来；不得把没抓当成"没变化"。

## 5. 删除接口（三个层级）

用户明确要求"给出删除接口"。不做管理后台（§6），因此接口是"改文件 + 校验 + 生效"，三层递进：

### 5.1 删一条（日常使用）

1. 打开 `config/overrides.json`；
2. 删掉对应的那个对象；
3. 下次运行（或直接跑页面数据生成）后，该条目**立即回到自动结论所在的分区**（推荐区或候选区），`manual_pick` 变为 `false`；
4. 若它当时对应的自动结论是被排除项，它会回到"不计入三区"的状态，只出现在统计里。

### 5.2 清空（重置）

把 `manual_picks` 置为 `[]`。全部条目回到自动分区。

### 5.3 软删除记录（可选，防止反复误收）

如需保留"曾经收过又删掉"的历史，可给对象加：

```json
"retired_at": "2026-09-22",
"retired_reason": "上游脚本权限过大"
```

带 `retired_at` 的条目**不再出现在收藏区**，且**不再自动补回**。是否实施由用户决定；不实施也不影响前两层。

### 5.4 页面上的删除提示

收藏区每个卡片显示一行小字（只作为提示，不做按钮、不写文件）：

> 移出收藏区：删除 `config/overrides.json` 中该条目的对象。

这是"给出删除接口"的最小可用形式。**不做**网页上的删除按钮：静态页没有后端，写了也无法真正落盘，反而误导。

## 7. 测试要求

`tests/test_overrides.py` 至少覆盖：

| 用例 | 断言 |
|---|---|
| 名单校验 | `skill_id` 不存在 / `reason` 为空 / `added_at` 非法 / 重复条目 → 校验失败且给出可定位报错 |
| 互斥 | 同一技能在收藏区出现后，`recommended` 与 `candidates` 两个数组里**都不含**它；三区计数之和 + 未评估 + 排除 + 处理失败 = 条目总数 |
| 覆盖候选区 | 自动结论为 `candidate` 的技能被收入收藏区后，只出现在收藏区 |
| 覆盖排除项 | 自动结论为 `excluded` 的技能被收入收藏区后，仍在收藏区，并带风险提示字段 |
| 内容变化 | 上游内容变化：`content_changed_at` 有值、**模型调用次数为 0**、`status` 未变、`manual_pick` 仍为 `true` |
| 不降级 | 自动结论从 `recommended` 变为 `candidate` 时，条目仍在收藏区，`manual_note.auto_status` 更新 |
| 删除 | 从名单移除后，条目回到自动分区，`manual_pick` 为 `false` |
| 抓取上限 | `max_manual_checks_per_run` 生效；未抓到的条目不写"无变化" |
| 假数据 | 收藏条目的 `content_fingerprint` 与 `last_checked` 随检查更新，不被冻结 |

沿用现有做法：用固定评估输出、替身抓取函数，不联网、不调用模型。

## 8. 验收标准

1. 页面出现三个并列标签页：推荐区、候选区、收藏区；默认仍显示推荐区。
2. 同一技能**只出现一个区**，三区计数互不重复。
3. 从推荐区、候选区都能人工收入收藏区（改配置即生效，无需改代码）。
4. 收藏条目的上游内容变化后：页面显示变化提示，**本轮模型调用数为 0**，条目仍在收藏区。
5. 收藏条目被自动判为排除项后：仍留在收藏区，页面显示风险警告。
6. 删除配置中的条目后，它立即回到自动结论所在分区。
7. `config/overrides.json` 无凭据、随 git 提交、每条都有理由与日期。
8. 现有测试全绿；新增测试覆盖 §7 全部用例。

## 10. 实施顺序建议

1. `config/overrides.json` + `src/overrides.py` + 校验测试（不碰页面，先保证名单可信）
2. `src/index.py` 三区拆分 + 互斥 + 计数（此时页面还看不到收藏区，测试先绿）
3. `src/pipeline.py` / `src/local_run.py` 注入人工标记 + 抽查名额
4. `public/index.html` + `styles.css` 第三个标签页与提示条
5. `src/report.py` 周报口径
6. 文档与 README 同步（含 `tests/test_docs.py` 的文件名断言）
7. 端到端核对：把 `data/catalog.json` 里两个技能加进收藏区，跑一次运行（或只重生成页面数据），确认三区互斥、模型调用为 0
