# 重复从 #108 开始检查：根因与修复方案

日期：2026-09-26  
状态：问题已核实，本文为待实施方案；不代表下述修复、迁移或恢复命令已经完成。  
范围：本地目录批处理 `tools/run_local.py` 的候选池、评估账本与断点续跑。

## 1. 结论

每次从“检查 #108”开始，是因为候选池仍把该条目标记为 `pending`，而评估账本已经把对应评估标记为失败且不可重试。程序每轮都会取出它，抓取材料后查到账本阻止调用，再直接返回，没有推进候选池状态。

这会反复检查旧条目，但不等于反复调用模型。用户日志中，首次运行直到 #147 才出现“评估 #1”，当时累计用量仍为 0 Token。重复检查仍消耗网络请求和时间，也使待处理数量包含实际上不会继续评估的条目。

此前新增的 `LENGTH_EXCEEDED` 已解决新发生截断的持久化跳过；尚未解决旧版 `MODEL_ERROR` 记录，以及其他不可自动重试记录与候选池的状态同步。

## 3. 代码根因

相关文件：

| 文件 | 作用 |
| --- | --- |
| `src/catalog/pool.py` | `get_pending_candidates()` 只按 `status == pending` 选择候选 |
| `src/catalog/local.py` | `process_candidate()` 抓取材料、构造评估身份、读取账本、决定是否调用模型 |
| `src/catalog/evaluation.py` | `evaluation_id()` 生成评估身份 |
| `src/catalog/budget.py` | 保留尝试次数、失败状态、用量记录与结果未知状态 |

当前关键分支可以概括为：

```python
if record.status in {failed, in_progress, needs_recovery} and not resumable_failure:
    report.blocked_records += 1
    return True
```

这里没有更新并保存候选池状态。由此形成循环：

```text
pool: pending
    → 本轮选中并打印“检查”
    → 抓取材料、计算评估 ID
    → ledger: 不允许自动重试
    → 返回，pool 仍为 pending
    → 下次运行再次选中
```

阻止重复付费的账本保护本身应该保留。问题在于“无法继续自动处理”没有反映到候选池，也没有打印明确的阻止原因。

### 3.1 为什么不能把旧 HTTP 200 全部改成超长跳过

HTTP 200 只说明收到成功 HTTP 响应，不能单独证明输出截断。空正文等响应异常也可能被旧版归类为 `MODEL_ERROR`。

排查到的旧错误摘要只保留错误码、HTTP 状态和耗时，没有足够证据把这些记录全部认定为 `finish_reason=length`。必须区分“确定截断”和“旧版原因不明的失败”。

### 3.2 为什么切换模型不一定解除阻止

目前评估 ID 为：

```text
skill_id | content_fingerprint | rules_version | model_config_version
```

其中没有直接包含模型名称或端点。不同模型配置如果都使用同一个 `model_config_version`，切换模型后仍可能命中旧评估记录。排查到的上述记录使用版本 `1.0.0`。

这属于恢复策略的相关边界，不能通过随意删除账本或修改版本号来掩盖；否则可能绕开历史尝试次数与重复调用保护。

## 4. 目标行为

1. 已确定无法自动重试的候选不再保持 `pending`，后续启动不重复抓取。
2. 确定截断使用 `length_exceeded`；其他被阻止的候选使用独立 `blocked` 状态。
3. `blocked` 表示“需要明确恢复操作”，不表示技能质量不合格，也不等于永久拒绝。
4. 仍可安全重试的网络/临时 HTTP 失败保持现有重试策略，不误标为终态。
5. 历史用量、尝试次数和结果未知标记完整保留，不自动重新调用模型。
6. 报告区分本轮新阻止数量、池内累计阻止数量、可执行候选数量与超长跳过数量。
7. 增量补水、自动过期重建和普通刷新不能悄悄解除阻止状态。

## 5. 修复设计

### 5.1 扩展候选池状态与阻止元数据

在 `src/catalog/pool.py` 新增 `STATUS_BLOCKED = "blocked"`，加入合法状态、统计、序列化和反序列化。

为条目增加可选的 `block_info`，旧池缺少字段时按空值读取。建议字段：

```json
{
  "evaluation_id": "对应的完整评估ID",
  "reason": "NON_RETRYABLE_FAILURE",
  "reason_code": "MODEL_ERROR",
  "http_status": 403,
  "blocked_at": "带时区的时间",
  "source": "local_ledger"
}
```

`reason` 至少区分：不可重试失败、重试次数耗尽、结果未知、旧记录原因不明。HTTP 状态等字段只保存有明确来源的值；不得从信息不足的旧记录中猜测。

只记录安全诊断字段，不复制 API Key、认证头或完整服务端正文。

### 5.2 统一账本到候选池的状态映射

提取纯判断函数，输入评估记录及有效重试额度，输出动作和原因。在线运行与历史对账共用它，避免各自判断不一致。

| 账本事实 | 候选池动作 | 本轮动作 |
| --- | --- | --- |
| `completed` | 复用并发布成功后设为 `done` | 不调用模型 |
| 确定 `LENGTH_EXCEEDED` | `length_exceeded` | 不重试、不累计服务失败 |
| 本地失败可重试且未达到尝试上限 | 保持 `pending` | 按既有规则继续 |
| 不可重试失败 | `blocked` | 明确记录并跳过 |
| 已耗尽重试额度 | `blocked` | 等待明确恢复 |
| 遗留 `in_progress` / `needs_recovery` | `blocked`，原因是结果未知 | 不自动重发 |
| 无匹配记录 | 保持 `pending` | 正常处理 |

首次产生不可继续处理的失败时，也应立即保存对应池状态；不能只修复“下次遇到旧记录”的分支。本轮的故障熔断和用量未知停止条件仍按原策略执行。

打印明确日志，例如：

```text
[阻止] #108 writing-lean-proofs：存在旧版不可重试评估记录，已持久化为 blocked，本次未调用模型。
```

禁止把 `blocked` 简单替换成 `done`：后者会错误表示已经完成正常处理。

### 5.3 对旧数据进行离线对账

建议增加独立离线对账入口，并提供“预览”和“应用”两种模式。具体命令名在实现时确定，当前尚无该入口。

对账步骤：

1. 获取与采集相同的目录任务锁，确保没有正在写入的批处理。
2. 读取候选池、本地账本与可用的 Actions 评估记录。
3. 为 `pending` 条目匹配明确的评估身份；本地精确记录优先，保持与运行器一致。
4. 生成拟迁移清单，包含技能 ID、序号、旧状态、新状态、依据和源记录。
5. 应用时保存候选池备份，通过原子写入更新池；不修改历史账本和 Token 记录。
6. 保存迁移报告，重复执行应无额外变更。

身份匹配必须谨慎：不能仅按技能名称或“最近一条记录”关联。应核对 `skill_id`、内容指纹、规则版本及模型配置版本。

如果池中缺少内容指纹，或存在多个无法判定的身份，则列入“待核实”，不强行迁移。它可以在下一次正常抓取、得到精确评估 ID 后自动落为 `blocked`；若要求完全离线消除首次重复抓取，则需要人工明确指定应关联的评估记录。

有明确截断证据的旧记录才迁移为 `length_exceeded`；只有 `MODEL_ERROR + HTTP 200` 的记录应归为原因未明的 `blocked`。

### 5.4 在候选池重建时保留阻止状态

沿用超长跳过标记的保留方式，把旧池的 `blocked` 与 `block_info` 合并到重建结果中。按稳定技能 ID 匹配，不依赖可能变化的 `seq`。

未被本轮搜索发现的阻止条目也应保留其记录，防止后续搜索重新发现后又进入 `pending`。普通 `--refresh-pool` 只刷新发现结果，不代表用户授权重新评估被阻止项。

这样会使内容已更新的阻止项也继续等待恢复，这是本期明确的保守策略；如需自动检测上游变化，应单独设计，不在此处偷偷恢复付费调用。

### 5.5 明确恢复路径

为 `blocked` 条目设计按技能 ID 或评估 ID 指定的恢复操作，先预览影响，再应用。不要用“清空整个候选池/账本”作为恢复手段。

恢复必须同时满足两层要求：

- 池状态允许进入处理队列。
- 账本允许执行相应评估尝试。

仅把 `blocked` 改回 `pending` 会再次被旧账本阻止；直接清空尝试次数又会丢失费用控制依据。因此恢复应保留原始记录，并追加显式恢复事件，记录原因、时间及新授予的尝试额度。

HTTP 403 应先解决访问或权限问题；网络重试耗尽应先确认服务恢复；结果未知的调用不得默认为未计费。更换模型后重新评估，也应明确记录新评估身份或恢复授权，不依赖版本号碰巧不同。

模型身份是否纳入提供方、端点与模型名，应作为单独的身份版本设计处理，避免直接修改 ID 算法导致所有历史评估失去缓存命中。

### 5.6 报告与可观察性

建议报告同时展示：

- 全池 `blocked` 累计数量。
- 本轮新增阻止数量及按原因分组。
- 本轮超长跳过数量与池内超长跳过累计数量。
- 可进入处理队列的数量，并与人工排除、冷冻、已收录等策略过滤后的数量区分。
- 阻止条目的清单或本地详情链接。

在打印“检查”之后如果不进入评估，应有明确的复用、排除或阻止说明，避免出现几十行只有“检查”的无解释输出。

## 6. 验收用例

全部使用临时目录和模拟响应，不需要真实模型调用。

| 用例 | 预期 |
| --- | --- |
| #108 为 pending，精确账本为不可重试失败 | 首次处理落为 blocked；再次运行不抓取、不调用模型 |
| 历史 MODEL_ERROR + HTTP 200，无截断证据 | 标为 blocked，不推断为 length_exceeded |
| 明确 LENGTH_EXCEEDED | 保留 length_exceeded，不影响服务失败计数 |
| 本轮首次收到不可重试失败 | 当轮保存 blocked，同时遵守原有停止条件 |
| 网络失败仍有重试额度 | 不被提前 blocked，继续按既有上限重试 |
| 重试额度耗尽 | 保存 blocked，保留 attempts 和既有用量 |
| 结果未知 / 遗留 in_progress | 不自动重发，保留需要恢复的原因 |
| 离线对账重复执行 | 幂等；第二次无新增迁移 |
| 缺指纹或身份冲突 | 报告待核实，不误关联、不调用网络 |
| 池过期、强制刷新、补水 | blocked 及其原因保留，不自动重新评估 |
| 原 blocked 本轮未被发现，下轮重新发现 | 仍为 blocked |
| 相同技能多个规则或模型版本记录 | 只处理明确匹配的记录，不按时间随意选取 |
| 采集正在运行时申请迁移 | 锁冲突并清晰退出，不写部分数据 |
| 中途写入失败后再次对账 | 可以重试，不重复计费、不破坏原始账本 |
| 显式恢复 | 历史 attempts、usage 和恢复事件可追溯，只有授权的条目可重新尝试 |

## 7. 实施顺序与回滚

1. 扩展池状态与元数据，完成序列化兼容测试。
2. 提取共同判断函数，修复本轮失败和历史失败两个状态推进分支。
3. 补齐报告、日志及重建保留逻辑。
4. 提供离线对账预览，检查 #108 等历史条目的拟迁移依据。
5. 在批处理结束或正常停止、确认锁已释放后，备份并应用迁移。
6. 验证下一次从真正可执行候选开始，而非固定回到 #108；再完善显式恢复入口。

迁移只改候选池，不删除账本。需要回滚时，在没有运行任务且持有同一任务锁的条件下恢复备份，并记录回滚操作；不要覆盖迁移之后新产生的候选池进度。若迁移后已有新进度，应逐条撤销本次迁移，而非整文件回滚。

本次任务仅形成文档，没有执行迁移、重置失败记录、停止运行进程或调用模型。
