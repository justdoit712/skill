# 样本异常隔离与批处理容错完整方案

日期：2026-09-26  
状态：待实施设计；本文中的新配置、命令和字段均为提案，不代表已经可用。  
范围：本地普通目录批处理 `tools/run_local.py`。共享传输层可新增诊断事实，但本期不改变定向查找和 Actions 的调度、配额策略。

## 1. 目标和边界

目标是让单条输出截断和偶发格式异常不会被当成服务宕机，也不会因池状态未推进而反复抓取；同时保留费用控制、异常停止与可恢复性。

必须满足：

1. 明确 `finish_reason=length` 时，拒绝采用不完整输出，标记 `length_exceeded`，继续处理其他候选。
2. 偶发输出 JSON/结构异常时，标记 `blocked` 并说明原因；持续输出无效时，使用独立格式异常保护，不无限消耗预算。
3. 模型是否成功响应、响应是否符合业务契约、是否计量完整，分别判断。HTTP 200 不等于结果可用，更不等于用量已知。
4. 所有发出请求的处理路径都经过统一收尾；任何跳过动作不得绕过 `usage_unknown`、预算、写入错误或中断保护。
5. 已发生的请求全部保留，输入/输出/推理用量透明；未知用量不得填成零。
6. 阻止与超长跳过在重启、补水、过期重建和普通刷新后保持；只有明确恢复操作才能解除。
7. 不保证达到目标推荐数，也不承诺毫秒级处理。目标、预算、候选耗尽、评估次数、用户中断和系统异常均可结束运行。

不在本期范围：自动提高单条输出上限、自动压缩原文、自动更换模型、修改质量筛选标准，以及对所有历史数据重新评估。

## 3. 错误分类：保留事实，再决定动作

### 3.1 传输层

`src/infra/llm.py` 只负责网络及模型接口事实：

- `http_status`、`error_type`、`finish_reason`、`usage`、`attempts`、`latency_ms`。
- `LENGTH_EXCEEDED`、`NETWORK_ERROR` 及既有模型调用错误码。
- 只有明确 `finish_reason=length` 才认定输出截断；空字符串、非法 JSON、HTTP 200 都不能代替该证据。

不在传输层校验目录业务字段，不增加用一个 `is_service_failure` 布尔值控制所有行为的机制。可保留现有 `is_sample_error` 作为诊断信息，最终动作仍由分类器结合完整事实决定。

### 3.2 评估层

为业务校验增加有稳定代码的异常类型，禁止通过匹配中文错误文本判断类型。

| 建议错误类型 | 含义 | 是否必然发出模型请求 |
| --- | --- | --- |
| `OUTPUT_JSON_INVALID` | 实际模型输出不是合法 JSON | 是 |
| `OUTPUT_SCHEMA_INVALID` | 字段缺失、类型/枚举/质量结构非法 | 是 |
| `RESUME_STATE_INVALID` | 待复核初评与材料或规则不匹配、恢复快照损坏 | 否 |
| `RESPONSE_EMPTY` | 正常结束但未提供正文，且非 length | 是 |
| `LEGACY_PARSE_UNKNOWN` | 旧 `PARSE_ERROR` 无法确定具体子类 | 未知 |

为兼容现有调用者，JSON 和结构异常第一阶段仍可返回 `reason_code=PARSE_ERROR`，同时增加 `error_kind`；本地新分类器使用 `error_kind`。恢复状态错误使用独立 `RESUME_STATE_INVALID`，不再冒充模型解析错误。

错误结果还应保留 `stage`（assessment/review/resume）、实际 `calls` 列表以及安全诊断。初评和复核执行同一分类规则。旧测试适配器只有 `call` 时可以兼容，但必须明确“本次未发送请求”与“发送后没有 usage”的区别。

现有 `pending_evaluation` 应在发送请求之前验证。未发送请求的本地错误不能调用 `usage.add(None)` 来凭空增加未知请求。

### 3.3 本地运行器决策表

| 结果 | 当前候选动作 | 批处理动作 |
| --- | --- | --- |
| 有效评估，达到或未达到推荐标准 | 发布后 `done` | 公共停止检查后继续 |
| 明确 `LENGTH_EXCEEDED` | `length_exceeded` | 不计服务失败；公共停止检查后继续 |
| `OUTPUT_JSON_INVALID` / `OUTPUT_SCHEMA_INVALID` | `blocked`，记录格式错误 | 增加独立格式异常计数；未到阈值则继续 |
| `RESUME_STATE_INVALID` | `blocked`，记录恢复状态冲突 | 停止，要求处理本地状态，不调用模型 |
| 401 / 403 | `blocked`，记录访问错误和评估配置上下文 | 立即停止，不依次污染后续候选 |
| 408 / 429 / 可重试 5xx / 网络异常 | 保存真实请求记录 | 在现有费用保护允许下退避重试；耗尽后停止 |
| 非可重试 4xx 或明确请求配置错误 | `blocked`，记录 HTTP 及配置错误 | 停止检查配置，不假定只是样本异常 |
| 正常结束却无正文 / 未分类模型异常 | `blocked` | 沿用通用连续失败阈值，达到后停止 |
| 输出有效，但质量检查不通过 | `done`，保存候选结论 | 属于有效评估，不计技术失败 |
| 已发出请求但最终用量未知 | 保存已有候选处理结果 | 无条件停止后续付费调用 |
| 写账本/池/报告失败 | 保留可恢复事实 | 停止，不能继续调用模型 |

服务重试耗尽后终止本轮，保留原记录及用量，候选转为带恢复原因的 blocked。对 401/403 的 blocked 应理解为“当前评估上下文不可执行”，不代表技能永久不可用。

网络异常或错误响应常常没有 usage；本期不放宽现有未知用量保护。如果最终用量不能确定，则 `usage_unknown` 比“服务重试”更优先。不能仅凭 HTTP 状态推断本次零费用。

## 4. 计数器与停止条件

### 4.1 三类计数分开

- `consecutive_failures`：保留给无有效结果的通用模型响应异常，不再包含明确截断和已细分的格式异常。
- `format_failures_without_valid_result`：自最近一次有效业务评估后发生的格式异常候选数量，每候选最多增加一次。
- 请求重试计数：继续由账本 `attempts` 与请求明细管理；不与候选级异常计数混用。

计数规则：

| 事件 | 通用连续失败 | 格式异常计数 |
| --- | --- | --- |
| 得到有效业务评估，无论推荐与否 | 清零 | 清零 |
| 明确 length 响应 | 清零 | 保持原值 |
| 已确认由模型输出产生的格式错误 | 清零 | 加一 |
| 网络/HTTP 故障 | 按服务重试策略处理 | 保持原值 |
| 缓存复用、预筛排除、已收录或冷冻跳过 | 保持原值 | 保持原值 |
| 历史 blocked/截断记录对账 | 保持原值 | 保持原值 |

格式异常计数不被 length 清零，避免“格式错误—截断”交替时永远绕开保护。不能从历史失败记录推断当前服务恢复，因此历史对账也不重置计数。

### 4.2 建议配置

在 `config/runners/local-run.json` 增加：

```json
{
  "max_format_failures_without_valid_result": 10
}
```

默认 10 是产品保护阈值，不是对故障原因的证明。选择它是为了允许连续 5 条偶发格式异常后继续寻找正常候选，同时避免数百次无效输出持续消耗预算。读取旧配置时使用默认值，验证必须为正整数；不提供默认关闭保护的选项。

本期不增加同一样本的自动“修复 JSON”请求，也不自动扩大输出额度。每次格式异常保存后直接进入下一候选或停止；后续恢复是显式操作。

### 4.3 停止原因

保留既有 `token_limit`、`usage_unknown`、`retry_exhausted`、`model_failures`、目标/候选/次数限制及中断原因；新增：

- `format_failures`：格式异常达到阈值。
- `access_denied`：401/403。
- `request_config_error`：不适合自动重试的请求配置错误。
- `resume_state_invalid`：恢复数据冲突。

若同一次处理满足多个停止原因，全部记入 `stop_causes`，主原因按确定优先级选择：中断/持久化失败 → 用量未知 → 恢复状态冲突 → 访问/配置错误 → 总预算 → 重试耗尽 → 格式异常阈值 → 通用失败阈值 → 正常目标/次数/候选结束。不得由最后执行的赋值覆盖更重要原因。

## 5. 统一请求生命周期和收尾

### 5.1 写入顺序

```text
调用前检查停止条件
    → 保存请求开始记录
    → 调用模型
    → 保存响应事实与用量
    → 解析并生成最终业务结果
    → 分类，更新账本最终状态和错误明细
    → 保存候选池状态与 block_info
    → 更新本轮统计并保存报告
    → 清理活动请求上下文
    → 计算停止原因
    → 允许进入下一候选或停止
```

初评成功后，如果需要复核，复核发出前再检查预算和用量；每个实际请求单独落账。初评和复核的用量不得只保留最后一次，也不能重复相加。推理 Token 是输出 Token 的子集，单独展示但不再加到总量中。

### 5.2 伪代码

```python
result = evaluate_with_accounting(...)
decision = classify_result(result, policy)

persist_final_evaluation_record(result, decision)
apply_pool_transition(item, decision)  # 复用 _update_blocked
update_failure_counters(result, decision)
update_run_report(result, decision)
persist_pool_and_report()
clear_active_context()

stop = determine_stop_state(state)
return not stop.should_stop
```

这是职责示意，不是可直接替换现有函数的代码。异常分支必须由外层异常收尾记录失败并停止，不能借 `finally` 提前清理尚未持久化的活动请求。

任何已发出请求的分支禁止直接 `return True` 跳过上述收尾。在候选入口及每次模型请求前再加一层停止状态守卫，防止上层遗漏传播已设置的停止条件。

### 5.3 原子性与中断恢复

账本、候选池和报告是多个文件，原子写单文件不等于多文件事务。使用目录任务锁与顺序落盘，并实现幂等对账：

- 账本有明确失败结果、池仍 pending：按精确评估身份修复池，不重发模型请求。
- 池已落终态、报告未完成：可从本轮请求/处理事件重建报告，不再次增加统计。
- 仅有请求开始而无最终结果：保留结果未知状态，禁止自动重发。
- 池指向的账本记录缺失或冲突：报告不一致，要求恢复，不猜测成功或免费。

若现有请求回调只保存 HTTP 完成事实，业务解析失败后还应补上最终 `error_kind` 和阶段，避免请求明细显示 completed 而评估失败原因丢失。

## 6. 候选池和 block_info

沿用已有池状态，不新增与 blocked 含义重复的 `parse_failed`。

建议 `block_info` 结构：

```json
{
  "evaluation_id": "完整评估ID",
  "reason": "OUTPUT_FORMAT_INVALID",
  "reason_code": "PARSE_ERROR",
  "error_kind": "OUTPUT_SCHEMA_INVALID",
  "stage": "review",
  "http_status": 200,
  "blocked_at": "带时区的时间",
  "source": "local_ledger",
  "model": "实际模型名称",
  "model_config_version": "实际配置版本"
}
```

模型名称是诊断上下文，不改变现有评估 ID。API Key、认证头、完整响应正文和私人字段不进入该结构。旧记录没有的字段可空，不能补造。

跳过不应改变技能原有推荐/候选结论：技术失败无法证明技能质量不合格。初评通过但复核格式无效，也不能把未完成复核的结果发布成推荐。

`length_exceeded` 与 `blocked` 的刷新保留规则使用当前实现并补测。普通刷新不会授予额外付费尝试。

## 7. 历史对账与显式恢复

### 7.1 离线对账

建议新增工具 `tools/manage_pool.py`，以下命令为计划接口：

```powershell
python tools/manage_pool.py reconcile --dry-run
python tools/manage_pool.py reconcile --apply
```

默认只预览；应用时持有目录任务锁、保存迁移前备份与迁移清单。对账不联网、不调用模型、不修改用量或删除账本。

精确匹配技能 ID、内容指纹、规则版本、模型配置版本，来源选择与现有运行器一致。本地记录和 Actions 记录均可供读取，但本地迁移不能改写 Actions 周账本。

只有明确 `LENGTH_EXCEEDED` 或结构化 `finish_reason=length` 证据才迁移为超长跳过。旧 `MODEL_ERROR + HTTP 200` 不自动推断截断；旧 `PARSE_ERROR` 没有子类时按 `LEGACY_PARSE_UNKNOWN` 记录。

缺少指纹、多身份冲突或缺少来源记录的条目列为待核实；不能仅按名称或最近时间选记录。必要时允许下一次正常抓取后得到精确身份，再落 blocked，之后便不再重复检查。

对账产生的是历史状态同步，不计作本轮新模型失败，不重置实时计数。

### 7.2 恢复接口

计划接口：

```powershell
python tools/manage_pool.py resume --evaluation-id "精确ID" --reason "已修正输出格式配置" --dry-run
python tools/manage_pool.py resume --evaluation-id "精确ID" --reason "已修正输出格式配置" --apply
```

恢复默认不立即调用模型，只准备下一次运行。应检查阻止原因、当前配置和对应记录，明确展示恢复将允许额外付费尝试。

恢复事件应追加到本地账本，保留历史请求、错误、attempts 和 usage；记录操作者原因、时间及额外授予额度。若采用原评估 ID 恢复，允许尝试总上限只增加显式授权的数量，不能把 attempts 清零。运行器不得在启动时把授权上限无条件重写成默认值。

池状态只有在恢复授权已持久化后才能改回 pending；中途失败可根据授权事件幂等补齐。结果未知必须额外确认其历史处理方式，不能把未知用量转成零。

恢复 Actions 来源的失败应在本地创建带来源关联的恢复记录，不修改远端额度历史。若不存在可信来源或所需评估材料，应拒绝应用并说明缺少什么。

更换模型名称但仍使用相同 `model_config_version` 不一定生成新 ID。本期不直接修改全库 ID 算法；恢复时记录新模型上下文，后续如需升级身份规则，单独设计缓存兼容迁移。

## 8. 日志和报告

建议日志：

```text
[自动跳过] #148 expo-overview：输出达到 8000 Token 上限，已保存 length_exceeded。
[格式异常] #152 example-skill：复核输出字段不合法，已保存 blocked（距上次有效结果累计 2/10）。
[停止] 输出格式异常达到阈值，请检查模型与评估输出契约；后续候选未调用。
[停止] 当前响应用量未知；本条状态已保存，后续付费调用已停止。
```

日志不把 length 必然解释为“输入文档太长”，因为推理消耗或输出结构也可能耗尽输出额度。

报告保留既有用量字段，并增加：

- `skipped_output_format`：本轮格式异常隔离的候选数。
- `format_failures_without_valid_result`：当前独立异常计数。
- `blocked_new`、`blocked_total`：本轮新增和池内累计阻止数量。
- `reconciled_blocked`：本轮通过历史记录补齐的阻止数量。
- `stop_causes`：本轮停止原因集合。
- 每次请求的 `stage`、传输状态、业务结果及对应错误子类。

明确统计口径：length 和格式异常不计入“服务失败请求”；全部实际请求仍计入请求总数和 Token。保留旧 `failed_requests` 字段时需同步文档说明口径，必要时增加分项字段，避免旧报表误读。无任何请求的恢复错误不增加请求总数。

| `docs/运行说明.md` | 错误口径、停止条件、历史对账和恢复操作 |

共享模块变化后，定向查找和 Actions 测试必须通过；不得因本地策略调整改变其重试或配额含义。

## 10. 测试与验收

### 10.1 必测场景

| 场景 | 核心断言 |
| --- | --- |
| 连续 5 条 length 后正常候选 | 无服务熔断，继续达到可实现的目标，5 条持久化跳过 |
| 连续 5 条格式异常后有效评估 | 默认阈值 10 下继续，有效评估清零格式计数 |
| 连续 10 条格式异常 | 第 10 条落盘后停止，第 11 条不调用 |
| 格式异常与 length 交替 | length 不清空格式计数，达到阈值时仍停止 |
| 有效但未推荐的评估 | 重置格式计数，不误算失败 |
| 任一样本异常伴随未知 usage | 状态保存，但下一候选不调用 |
| 请求后达到总预算 | 完整记账，下一请求不发出 |
| 初评有效、复核截断或格式失败 | 两轮用量准确，不发布未完成复核的推荐 |
| 恢复初评版本冲突且没有调用 | RESUME_STATE_INVALID，请求与用量不凭空增加 |
| 401/403 | 当前条目阻止，本轮停止，其余候选保持原状态 |
| 429/5xx/网络失败 | 既有重试和未知用量保护均不被放宽 |
| 旧 HTTP 200 通用失败 | 不误迁移为 length，不自动重新付费 |
| 重启/补水/过期/刷新 | 阻止和超长标记保留，元数据不丢失 |
| 账本成功后池写入失败 | 下次精确对账恢复，不重复调用 |
| 池成功后报告写入失败 | 可重建，统计不重复 |
| 显式恢复后重启 | 授权尝试额度保留，旧次数与费用不清零 |
| 迁移重复执行或锁冲突 | 幂等，锁冲突无部分写入 |

使用临时目录、假时钟和假响应；故障测试明确记录真实发出次数，不能只断言最终状态。增加状态序列测试，覆盖失败、成功、截断交替的计数变化。

### 10.2 执行顺序

先跑新增聚焦测试，再跑全量 Python 测试和架构守卫：

```powershell
python -m unittest discover -s tests -q
```

离线测试完成后才做可选真实冒烟，使用当前已有参数限制规模，例如：

```powershell
python tools/run_local.py --target 1 --max-evaluations 2 --max-tokens 100000 --max-retries 0
```

该预算仍是请求后的停止阈值，不是服务端硬性费用上限；最后一次请求可能超出阈值。真实冒烟还会使用当前候选池和模型配置，执行前应明确目标。不能通过直接运行默认 100M Token 任务代替故障覆盖测试。

## 11. 实施和交付顺序

1. 固化当前已实现能力的回归测试，先覆盖已知 early-return 和 PARSE_ERROR 误分类问题。
2. 实现有类型的错误与无 I/O 分类器；保持共享调用者兼容。
3. 接入统一收尾和格式异常保护，补齐账本、候选池、报告一致性。
4. 实现离线对账与显式恢复，补测权限来源、身份冲突、额外尝试授权及中断窗口。
5. 完成全量离线验证并更新运行说明。
6. 停止或等待现有批处理结束；在任务锁保护下预览历史迁移，再应用明确可判定的记录。
7. 可选执行小规模真实冒烟；确认账单、状态、日志和恢复链路后再恢复日常批处理。

交付条件：本方案必测场景通过，历史迁移可预览且幂等，恢复不会绕开付费记录，普通刷新不会复活终态条目，文档中的新命令与实际帮助输出一致。

## 12. 回滚

代码回滚与数据回滚分开。新增字段应尽量保持旧读取器兼容；不能回滚到不理解 blocked 状态的版本后继续运行。

迁移前保存备份和逐条变更清单。没有后续进度时可在锁内恢复备份；已经产生新评估时，只撤销本次迁移涉及的条目，不覆盖新的运行结果。不删除历史账本、请求明细或恢复事件来伪造“未运行”状态。

任何恢复或迁移失败都应报告明确原因。默认保留现状并停止，不以继续消耗模型额度来掩盖不一致。
