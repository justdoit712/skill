# 异常恢复、Finder 增强与评估成本优化综合实施方案

日期：2026-09-28  
状态：待实施。本文为执行计划，不代表相关功能已经实现或验收通过。  
范围：Windows 本地运行，以 `tools/run_local.py` 和 `tools/find_skill.py` 为主要入口，兼容既有两阶段评估入口。

## 1. 依据与目标

本方案整合以下三份文档，统一实施顺序、依赖和验收要求；具体业务边界仍参考原方案：

- [样本异常隔离后续待办](样本异常隔离后续待办.md)
- [定向查找搜索召回与证据核验增强方案](2026-09-27-定向查找搜索召回与证据核验增强方案.md)
- [LLM 评估流水线与 Token 成本优化方案](2026-09-27-LLM评估流水线与Token成本优化方案.md)

长期架构约束见[架构约定](../架构约定.md)，实际操作入口及用量规则见[运行说明](../运行说明.md)。

目标按优先级排序：

1. 保证异常恢复可追溯、可重复执行，不重复授权、计费或统计。
2. 在既有预算内改善 Finder 查询覆盖，减少真实引文因行号漂移被拒绝的情况。
3. 通过静态分级、输出契约和受限缓存复用减少无效模型调用。
4. 用固定样本和可检查的运行事实证明正确性及收益。

“召回翻倍”“节省 15%～30% Token”均为未经验证的假设，不作为交付承诺。

## 2. 当前基础与实施边界

本轮只读核查确认，代码已有精确内容缓存、Finder 结构化证据核验结果、查询游标、离线恢复入口和请求用量记录。因此以下工作均按增量扩展实施，不重建整条流水线。

普通目录 `catalog/quality.py` 已支持完整连续行引用的重定位；Finder 采用指定区间内完整引文核验，两者规则不同，不直接互相导入或统一为宽松规则。catalog 与 finder 保持业务隔离，infra 不包含业务 Prompt，shared 保持中性且不执行 I/O。

统一边界：

- 保留原始材料、精确指纹、模型原始输出、历史 attempts 和用量事实。
- 新功能默认关闭或处于观察模式，通过对应验收后再启用。
- 恢复、缓存复用及报告重建不得重复发出已确认完成的模型请求。
- 未知用量不视为零；沿用当前有界重试与估算预留规则，不恢复旧方案中“一律停止”的要求。
- 离线开发使用固定材料、临时目录和模拟接口；真实搜索与模型调用单独安排。
- 本计划不要求迁移全部历史记录，不自动修改模型配置，不执行部署。

## 3. 阶段依赖与交付顺序

| 阶段 | 内容 | 前置条件 | 交付门槛 |
| --- | --- | --- | --- |
| P0 | 异常恢复与审计闭环 | 固定恢复故障样本 | 多文件中断可恢复，授权和事件幂等 |
| P1 | 样本基线、统计及版本契约 | 可与 P0 的设计工作交错推进 | 指标可复算，旧数据兼容策略明确 |
| P2 | Finder 查询和证据增强 | P1 | 查询、核验、排序、报告及续跑完整链路通过 |
| P3 | 静态分级和严格输出契约 | P1；改变持久化和调度行为前完成 P0 | 观察结果可解释，兼容入口和恢复逻辑通过 |
| P4 | 规范化缓存 | P0、P1、稳定的输出契约 | 身份、证据、用量和复用审计全部通过 |
| P5 | 集成与真实效果验证 | 对应功能离线验收完成 | 正确性先通过，收益按实测报告 |

推荐执行顺序为 P0 → P1 → P2 → P3 → P4 → P5。P2 与成本优化不存在直接业务依赖；规范化缓存启用必须后置于恢复闭环和输出契约确定。

## 4. P0：异常恢复与审计闭环

### 4.1 实施任务

| 工作项 | 实施内容 | 主要模块 |
| --- | --- | --- |
| 迁移清单 | 独立保存操作身份、记录身份、变更依据、前后状态、未确认项、备份位置及完成状态 | `src/catalog/maintenance.py` |
| 恢复授权幂等 | 为单次授权建立稳定事件 ID；中断重放沿用该事件，不再次增加尝试额度；新的显式授权使用新事件 | `maintenance.py`、`budget.py` |
| 多文件恢复 | 根据已保存的账本事实补齐池状态和派生报告 | `local.py`、`pool.py`、报告模块 |
| 未知结果约束 | 明确 completed、failed、needs_recovery、身份冲突和材料冲突的处理分支 | 恢复入口、账本模块 |
| 来源审计 | 保存 Actions 来源关联及恢复所需材料身份；缺少可信依据时拒绝恢复 | `maintenance.py` |

使用现有会话锁和原子文件写入。需要跨文件推进的操作采用“持久化操作记录 → 写入业务状态 → 补齐派生状态 → 标记完成”的可重放流程，不引入数据库或宣称具有多文件事务。

未知结果恢复只在既有显式授权范围内增加尝试机会，保留此前请求、费用未知状态及预算预留，不能将旧请求改写为未发送。

### 4.2 验收

通过故障注入覆盖：

1. 账本完成、池尚未保存。
2. 池已保存、报告尚未生成。
3. 恢复授权已保存、池尚未改回 pending。
4. 迁移清单已保存、部分后续写入失败。
5. 锁冲突、身份歧义、材料冲突和历史原因缺失。

重复执行恢复后不重复调用、不重复授权、不重复统计事件；历史 attempts、用量和 Actions 原记录保持完整。清单保留可检查的操作结果，未确认记录不得强行迁移。

## 5. P1：样本基线、统计与版本契约

### 5.1 固定离线样本

- 查询：中文、英文、技术别名、歧义词、明确技术约束和无术语表命中的需求。
- 证据：正常跨行、合法行号漂移、重复段落、否定句、数字变化、代码、表格及跨文件拼接。
- 目录：短而有效、无 Frontmatter、明确占位、正文含 TODO、模板型技能和依赖参考材料的文档。
- 持久化：正常记录、缺字段旧记录、身份冲突、材料变化及各写入阶段中断。

保存输入、模拟响应及预期业务结果，测试调用生产规则和公开入口。复用已有 fixture，并补齐缺口，不以测试文件存在代替本轮执行结果。

### 5.2 统计口径

| 类型 | 必须区分的事实 |
| --- | --- |
| 搜索 | 实际请求、重试、去重后新增仓库、新增 Skill、有效材料、合格结果 |
| 模型 | 请求阶段、尝试次数、完成评估数、已知 Token、未知用量、格式失败、截断 |
| 缓存 | 精确命中、规范化潜在命中、实际复用、拒绝原因 |
| 静态规则 | 规则版本、命中信号、建议动作、实际跳过及抽样误拦截 |

报告保留计算指标的分子分母。分母为零时标记不可计算；缺失历史字段标记未知，不补造事实。没有相关技能标注集合时报告新增有效候选，不称为完整召回率。

### 5.3 版本设计

确定报告 Schema、输出契约、术语表、核验器和规范化算法的版本字段及兼容规则。输出契约变化纳入新缓存身份或兼容判断，不重写旧 evaluation_id，也不因新增字段自动触发全量重评。

P1 验收要求：关闭优化时保持已有业务行为；统计可由保存的运行事实复算；旧记录能够读取且缺失信息明确显示为未知。

## 6. P2：Finder 查询与证据增强

### 6.1 查询统一及术语补全

主要模块：`src/finder/plan.py`、新增术语纯函数模块、`search.py`、`refill.py`、`run.py`、`report.py`。

1. 初始、交互和反思路径共用空白规范化、大小写去重及操作符校验。
2. 新增小型版本化术语表，记录概念、别名和适用边界。
3. 先接入观察模式，记录覆盖缺口及拟补词，不增加搜索请求。
4. 启用后在现有查询上限内合并补词，不改变意图、required 或 quality_signal。
5. 保存模型原始查询、最终查询、补全来源、术语表版本及稳定查询身份。
6. 沿用现有分页、反思、游标、预算和停止条件；续跑复用保存的最终计划，不因术语版本更新重新扩展旧计划。
7. 保存查询到仓库、Skill 的全部发现来源；边际新增计数仅计算首次发现，并注明受执行顺序影响。

首版保持当前搜索附加条件。扩大搜索范围作为独立实验，避免与术语扩展、分页调整同时改变。

### 6.2 证据邻近定位

主要模块：`src/finder/evidence.py`、`evaluation.py`、`report.py`，必要时同步公开投影及前端读取逻辑。

- 扩展现有结构化结果，保存模型原始引用、实际位置、原文片段、匹配方式、核验器版本和稳定失败码。
- 指定区间已经匹配时沿用现有行为。
- 失败后仅在同文件合法行号附近寻找完整连续引文，初始配置为原起止行前后各不超过 3 行。
- 唯一性按实际文本出现位置判断，不按包含同一引文的重叠窗口数量判断。
- 非法行号、未读取文件、重复位置歧义、文字删改及跨文件拼接继续拒绝。
- 不删除否定词、标点或代码符号来制造匹配；新增容错不扩大代码和空白敏感内容的放行范围。
- 报告展示实际位置，原始评估对象保持不变；Prompt 要求足够完整的句子和必要上下文。

### 6.3 验收

查询补全与证据修复使用独立开关。完整验证“原始 JSON → 解析 → 核验 → 降级 → 排序 → 报告”，并覆盖续跑、预算停止及来源去重。

真实引文的唯一邻近位置可以恢复；高重合度伪造引文不能通过；一个必需项证据无效时不能进入强匹配短名单。报告明确原文存在不等于能力已实测或语义判断完全可靠。

## 7. P3：静态分级与严格输出契约

### 7.1 静态分级

主要模块：`src/catalog/prescreen.py`、`local.py`、`queue.py`、`sync_reserve.py`、`sync_evaluate.py`。

按三个步骤推进：

1. **观察模式**：输出档位、启发式版本、命中信号、建议动作和原因，不改变调用行为。
2. **明确空壳跳过**：仅处理具有充分依据的占位材料；跳过事实与模型评估分开记录，内容或规则变化后可重新检查。
3. **批内排序**：准备有上限的小批次材料，在兼容业务优先级内调整顺序，保留等待时间或轮转机会。

评估使用准备阶段的同一份材料快照。空文件、HTML 和截断沿用材料无效或抓取失败分类；缺 Frontmatter、短文本或出现 TODO 不单独构成淘汰依据。引用入口尚未读取时保持待判断，不能假定其内容有效。

验收覆盖有效短文误拦截、人工及复核优先级、公平性、批次中断和两个评估入口的行为一致性。观察、跳过与排序分开控制，便于定位影响。

### 7.2 严格输出契约

主要模块：`src/infra/llm.py`、各业务阶段的调用入口、输出契约及解析器。

- 兼容旧字符串配置，支持受校验的完整格式对象。
- 后端能力声明与本次业务 Schema 分离，不在全局模型配置中固定一份业务 Schema。
- 普通目录初评、复核，以及 Finder 规划、澄清、反思和候选评估使用各自契约。
- Schema 与本地解析器共享字段、枚举和版本定义，保留业务及证据校验。
- 后端不支持格式参数时明确失败；如配置回退，应在运行开始前确定并记录，不逐候选隐式重发。
- 格式错误、截断、网络错误和未知用量继续分别分类和记账。

先使用模拟接口验证载荷及旧配置兼容性。不能根据模型名称推断真实后端支持严格 Schema，真实能力确认归入 P5。

## 8. P4：受限规范化缓存

主要模块：`src/shared/identity.py`、`materials.py`、新增规范化纯函数模块、`src/catalog/local.py`、质量核验及账本模块。

### 8.1 数据与材料

新增辅助指纹、规范化版本、来源评估 ID 和复用审计；精确指纹含义不变。

当前材料 manifest 不包含全文，实施时必须先确定新材料快照的保存、完整性校验及引用方式。没有可信旧材料时继续使用精确缓存或正常评估，不反推历史辅助指纹。

首版仅允许经过明确验证的换行编码规范化。不自动合并空行、清理缩进、删除注释、改变链接或使用 AST 相同推断语义等价。“增加空行”用例在首版验证安全回退，不要求缓存命中。

### 8.2 复用流程

1. 获取并验证当前材料，优先查询精确缓存。
2. 未命中时查找同技能的规范化候选记录。
3. 核对实际材料集合、规则版本、模型配置版本、输出契约及规范化版本。
4. 核对记录完整性；未完成、待复核、用量未知记录不作为完整结果复用。
5. 在新原文中重新核验初评及独立复核所需证据；缺失、歧义或不兼容时回退。
6. 成功后保存独立复用审计，关联当前材料和历史评估；保留原始评估时间与来源记录。

先运行观察模式记录潜在命中及拒绝原因，再启用复用。缓存命中不伪造模型调用或 Token，也不直接等同于新增推荐。

### 8.3 验收

允许的转换能够命中；缩进、硬换行、链接目标、标题、YAML、注释指令等变化不错误复用。版本变化、材料不足和证据不明均正常回退。复用落盘中断后可重放，不重复计费或统计。

## 9. P5：集成与真实效果验证

每个提交先执行相关模块回归，集成时在 Windows PowerShell 中执行：

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -q
npm test
git diff --check
```

本次文档整理未执行上述测试。实施时将命令、结果、失败原因和未覆盖事项记录到验收文档；离线测试通过不能推导真实后端、搜索效果或旧机器迁移已通过。

真实验证单独明确调用预算、样本、配置和停止条件：

- 缓存及静态规则使用固定材料、规则和模型配置对照。
- 搜索增强固定预算和执行顺序，在相近时间运行并保存返回结果，说明远端结果变化的影响。
- 每次只改变一个因素：查询补全、证据修复、静态跳过、排序、输出模式或缓存。
- 同时报告质量、覆盖、成本和时延；格式失败与截断分开，未知用量单列。
- 没有价格依据时只报告 Token；估算避免的成本必须标明假设。

发现错误复用、有效材料误拦截、证据误放行或用量失真时，关闭对应功能并重新验收。关闭功能后保留已有审计字段和历史记录，不通过删除数据回退。
