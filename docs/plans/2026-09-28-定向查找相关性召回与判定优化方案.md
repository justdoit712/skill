# 定向查找相关性召回与判定优化方案

日期：2026-09-28  
状态：待实施（设计与执行方案）  
范围：定向查找子系统（`src/finder/`），以 `tools/find_skill.py` 为主要入口。  
定位：独立于主目录评估（`catalog`），围绕“这次需求最值得看哪些技能”进行专项优化。

---

## 1. 背景与核心目标

当前定向查找在落地过程中，存在“有价值的备选被判定断崖误杀”、“中文需求难以匹配英文仓库路径”、“大合集在首轮耗尽评估配额”等问题。

本次优化围绕**提高相关候选命中率、把匹配之处与差距说清楚**展开，确立以下原则：
1. **备选不误杀**：满足部分核心需求且有客观证据的条目必须保留为备选（`partial`），严禁降级为 `none` 导致结果消失。
2. **需求优先排队**：根据多语言查询词、技能名称、简介与路径综合打分排序，高相关候选优先评估，保留少量探索配额。
3. **小步快跑与动态检索**：按 10～15 个候选分批评估，根据收敛效果及时调整搜索或反思，避免首轮被大合集垄断。
4. **聚焦核心需求，减少形式主义审查**：文档只要足以理解做法即可，重点回答“满足哪些、证据在第几行、还缺什么、如何尝试”。
5. **受控并发与渐进呈现**：抓取预取与有限并发（2 并发），缩短输出耗时，产出结果即时呈现。

---

## 2. 现状问题与技术改造方案

### 2.1 修正“部分匹配被当成不相关”的判定断崖
- **问题现状**（[`src/finder/evaluation.py`](../../src/finder/evaluation.py#L305-L316)）：
  当模型初评为 `strong` 时，只要任一必需准则被判定为 `unsupported`（哪怕其他核心能力与加分项有确凿证据支持），程序就将其强制重算为 `match = "none"`：
  ```python
  if original_match == MATCH_STRONG:
      if not all_required_supported:
          res["match"] = MATCH_NONE if (any_required_unsupported or supported_count == 0) else MATCH_PARTIAL
  ```
  在后续排序筛选中，`shortlist` 取 `strong`，`alternatives`（备选）取 `partial`，而 `none` 条目被完全丢弃，导致许多有参考价值的候选彻底消失。
- **改造方案**：
  1. 只要存在确凿证据支持的能力（`supported_count > 0`），统一保留为 `MATCH_PARTIAL`，进入备选清单（`alternatives`）。
  2. 仅当所有准则皆无证据支持（`supported_count == 0`）或完全无关时，才归为 `MATCH_NONE`。
  3. 在 `limitations` 中明确记录所缺少的具体必需准则名称或描述，并在 `why_consider` 中点明“已具备哪些部分能力，适合作为备选参考”。

### 2.2 候选按需求相关性优先评估
- **问题现状**（[`src/finder/refill.py`](../../src/finder/refill.py#L231)、[`src/finder/search.py`](../../src/finder/search.py#L194)）：
  1. 路径匹配关键词仅通过 `re.findall(r"[\w]+", topic.lower())` 从原始用户需求提取。对于中文需求，切词往往是一整段中文，无法匹配 GitHub 仓库中的英文路径（如 `skills/emotional-support/`）。
  2. 候选调度（`schedule_candidates_fairly`）仅按仓库轮转，未综合考虑与本轮需求的语义/词法相关度。
- **改造方案**：
  1. **多源关键词融合**：合并 `plan["queries"]`（规划阶段产出的中英文拓词）、用户原始需求核心词及预设领域词库。
  2. **综合相关度粗排**：综合“技能名称（权重大） > 仓库/技能简介 > 路径关键词”进行快速词法打分。
  3. **双轨调度**：将候选池分为“高相关优先队列”（占 80%～85%）与“探索轮转队列”（占 15%～20%），优先评估高潜力候选，同时保留探索配额防遗漏。

### 2.3 小批评估与动态搜索调整
- **问题现状**（[`src/finder/refill.py`](../../src/finder/refill.py#L348-L366)）：
  当前采用“耗尽当前所有候选才开启下一轮”的策略（`max_total=None`）。若第一轮遇到含数十个技能的大型集合仓库（Awesome List），会一口气串行评估完所有文件，直接耗尽 `max_evaluations` 配额，使反思拓词（`_reflect`）和后续查询完全没有机会执行。
- **改造方案**：
  1. **批次窗口（Batch Size = 10～15）**：每轮次处理候选限制在小批次窗口内。
  2. **动态调整**：完成一批评估后，检查短名单集齐度与命中率；若连续无有效产出，立即推进到下一检索词或触发反思拓词。
  3. **队列保留**：未评估的剩余候选留在 `candidate_queue`，在后续轮次按优先级再次参与调度，不直接丢弃。

### 2.4 需求驱动的轻量审查与场景特异性
- **问题现状**：
  提示词与审查项中残留了部分偏向通用大型工程的形式要求（如缺少参数表、缺少独立教程或验收文件等），容易误伤 Prompt 类或指引类技能。
- **改造方案**：
  1. **保留核心门槛**：严格区分“必需能力”（`required`）与“加分项”（`quality_signal`），用户明确要求的核心能力绝不擅自降级。
  2. **轻量可用性判断**：重点关注“满足哪些需求、确凿证据在哪、缺少什么、如何调用或尝试”。只要说明能指导使用，不因缺乏格式化教程而否定。
  3. **针对“情感陪伴”等体感型场景的判定界线**：
     - **客观可验证机制**：材料中必须具备具体交互规则（如倾听复述、情绪确认、去说教/去评判约束、共情示范等）；
     - **杜绝口号宣称**：仅作者自述“具备深度共情”、“超强情感连接”而无具体 Prompt/交互规则的，判定为缺乏证据；
     - **真实试用提示**：材料具备具体机制即可判定“值得尝试”，但对话是否足够自然温暖需由试用确认，在报告中清晰提示。

### 2.5 抓取预取、两并发评估与渐进呈现
- **问题现状**（[`src/finder/run.py`](../../src/finder/run.py#L286-L307)）：
  抓取材料与模型评估完全串行，单技能耗时较长；且必须全部执行完才最终输出。
- **改造方案**：
  1. **流水线预取**：在当前候选执行模型评估时，后台异步预取后续候选的材料文本。
  2. **有限受控并发**：评估阶段支持 2 个候选并发调用，保持记账原子性（`UsageTotals`）与连续失败熔断机制。
  3. **渐进落盘与展示**：每完成一个候选或产生新的推荐项时，即时增量更新 `report.json`，提升用户等待体验。

## 4. 边界约束与验证要求

1. **架构隔离**：修改严格限制在 `src/finder/` 内部，严禁引入 `src/catalog/` 的特化逻辑，保持子系统独立性。
2. **预算与账本安全**：所有并发和预取操作必须严格尊重 `max_tokens`、`max_evaluations` 和未知用量熔断，严禁超额调用。
3. **断点续跑幂等**：任何分批与队列调度状态必须在 `report.json` 中保持原子化序列化，保证 `--resume` 能够无损恢复。
