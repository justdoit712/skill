# Skill 评估推荐策略与模型适配优化方案

**文档版本**：v1.0.0  
**生成日期**：2026-09-26  
**对应需求**：解决本地运行中“连续数十次评估 0 推荐”、“DeepSeek 模型输出频繁截断（8000 Token 上限）”以及“Qwen 3.7 模型大面积出现格式异常（OUTPUT_SCHEMA_INVALID）”的核心策略与工程瓶颈。

---

## 一、 现状问题深度剖析（问题事实与根因）

在近期本地批量运行（Run `20260926-154017-865e21` 与 `20260926-165037-f6eec9`）中，系统暴露出了严重阻碍候选收录的三大核心问题：

```
运行现状：
┌───────────────────────────────┬────────────────────────────────────────────────────────┐
│ 运行现象                       │ 核心指标与诊断数据                                      │
├───────────────────────────────┼────────────────────────────────────────────────────────┤
│ DeepSeek-V4-Flash 评估        │ 16 个候选中有 14 个触发 [自动跳过: 输出达到 8000 Token 上限] │
│ Qwen 3.7-Flash 评估           │ 56 个候选中有 40 个报 [格式异常: OUTPUT_SCHEMA_INVALID]      │
│ 两款模型跑完评估的 16+ 个样本  │ 新增推荐数 0 / 50（全部归入普通候选区，0 推荐）          │
│ 1.1.0 规则全库历史统计        │ 累计评估 216 条，成功推荐仅 1 条（推荐率仅 0.46%）      │
└───────────────────────────────┴────────────────────────────────────────────────────────┘
```

### 1.1 根因一：DeepSeek 模型配置中的 Token 上限严重偏小
- **现象**：几乎所有样本在刚好耗费 8,000 Token 输出时被服务端截断并触发程序跳过。
- **原因**：
  1. `config/models/bailian-deepseek-v4-flash-0731.local.json` 中配置的 `"max_output_tokens": 8000` 严重偏低；
  2. DeepSeek 作为高智能推理模型，其返回的 `completion_tokens` 包含了大量的深度思考链（`reasoning_tokens`）；
  3. 系统 Prompt 要求的条目繁多，模型在深度推演数千 Token 后，正文 JSON 尚未写完即触发了百炼服务端的 8,000 Token 强行截断（`finish_reason="length"`），被安全机制标记为 `length_exceeded` 自动跳过。

### 1.2 根因二：Qwen 3.7-Flash 对多层嵌套 Schema 遵守度不足导致误伤
- **现象**：40 个候选被标记为 `blocked` 并报 `OUTPUT_SCHEMA_INVALID`。
- **原因**：
  1. 规则 1.1.0 引入了深度质量评估，要求必须在顶层返回 `quality_checks` 对象（且必须完整包含 `practical_value`、`actionability`、`verification` 以及原文 citations 数组）；
  2. `qwen3.7-flash-2026-07-15` 模型版本较早，在面对上百行的复杂 Prompt 时，经常遗漏 `quality_checks` 中的某个字段；
  3. 代码层 `check_quality()` 抛出 `ValueError` 时，直接被当成单样本不可恢复的格式损坏（`OUTPUT_SCHEMA_INVALID`）并进行阻断隔离。

### 1.3 根因三（最致命）：原文逐行核验（`verified_citations`）过于死板，一票否决
- **现象**：即使模型认为技能质量极高、全项通过（`pass`），最终结果也必定变成 `candidate`，绝不可能被推荐。
- **原因**：
  1. **机械死板的比对逻辑**：`src/catalog/quality.py` 要求模型返回 `start_line`、`end_line` 与 `quote`，并用 Python 严格执行 `quote == "\n".join(lines[start - 1:end])`，且硬性规定单次引用不得超过 20 行；
  2. **模型行号天生容易微偏**：大模型生成文本时，在 200 行的长文档中极易将行号估偏 1~2 行，或者引用的代码块跨度达到 25 行；
  3. **强制降级连锁反应**：代码只要比对失败，就会无情地将原本由模型给出的 `pass` 强行篡改为 `unknown`（附带理由“程序未能核实所引原文与行号”）；
  4. **决策一票否决**：`decide.py` 规定必须全部项为 `pass` 才能推荐。只要有 1 项被篡改成 `unknown`，全盘降级到普通候选区，导致 216 条评估里 215 条被误杀。

## 二、 优化方案与设计规范

针对以上三大症结，设计以下具体改进方案：

```
优化架构：
┌────────────────────────┐      ┌────────────────────────┐      ┌────────────────────────┐
│  DeepSeek 配额调整     │      │   Prompt / Schema 健壮性 │      │  原文引用弹性核验改造   │
│  - max_tokens: 32000   │  +   │  - 补齐示例 JSON       │  +   │  - 去除死板行号强绑定   │
│  - 释放推理思维链空间  │      │  - 缺失字段优雅默认值   │      │  - 基于原文子串真实存在 │
└────────────────────────┘      └────────────────────────┘      └────────────────────────┘
                                            │
                                            ▼
                           大幅提高合理推荐率，彻底消除误杀阻断
```

### 2.1 优化点 1：原文引用核验改造（弹性核验，消除机械误杀）
- **改造位置**：`src/catalog/quality.py` -> `verified_citations` 与 `check_quality`。
- **调整规则**：
  1. **放宽行号强绑定**：大模型定位行号存在天然漂移。核验算法改为：
     - **优先行号窗口比对**：允许起止行号在 `[start - 3, end + 3]` 的窗口范围内寻找该段文字；
     - **兜底原文子串包含**：只要 `quote` 去除前后空白后的主要内容（如 >15 字符的有效片段）在 `text` 原文中真实存在，即认可该证据真实可查，不予篡改；
  2. **放宽单次引用行数**：将单次最大行数从 20 行放宽至 **60 行**（便于引用完整代码段或流程列表）；
  3. **不因引用格式微瑕否定基础判断**：对于 `scope_match`、`purpose_clarity`、`dependency_transparency` 等宏观逻辑维度，如果模型已经给出清晰的 `evidence` 说明，即使 citations 数组格式不规范，也**保留模型的原始判断（pass）**，仅在质量复核审计字段中做软性记录，不再强制篡改为 `unknown`。

### 2.2 优化点 2：优化模型配置参数（彻底解决 DeepSeek 截断）
- **改造位置**：`config/models/bailian-deepseek-v4-flash-0731.local.json`。
- **调整规则**：
  1. 将 `"max_output_tokens"` 由 `8000` 提高到 **`16000` 或 `32000`**；
  2. 百炼平台的 DeepSeek-V4-Flash / R1 系列支持最大 32,768 Token 输出，足够同时容纳 4,000~8,000 Token 的推理思维链与完整的结构化 JSON，杜绝 `length_exceeded`。

### 2.3 优化点 3：增强 Prompt 与 Schema 的容错健壮性
- **改造位置**：`src/catalog/evaluation.py` -> `build_prompt()` 与 `parse_evaluation()`。
- **调整规则**：
  1. **修正 Prompt 示例矛盾**：当前 `build_prompt()` 文本要求输出 `quality_checks`，但文末的示例 JSON 对象却遗漏了 `quality_checks` 的结构范例，导致部分模型（如 Qwen 3.7）出现幻觉或遗漏。在示例 JSON 中显式展示 `quality_checks` 的三个子对象结构；
  2. **Schema 优雅降级与补齐**：如果模型返回了合法 JSON，且包含基础的 6 项检查，但个别扩展字段（如 `quality_checks` 或非必选 tags）缺失，程序应自动根据已有判定赋予合理默认值，而不是直接抛出 `OutputSchemaError` 将条目标记为永久损坏（`blocked`）。

### 2.4 优化点 4：历史误伤条目一键恢复机制
- 此前被 Qwen 3.7 误伤标记为 `blocked` 的 40+ 个候选，以及被 DeepSeek 误伤跳过的 14 个候选，其本身内容并无问题。
- 在优化策略生效后，通过执行批处理恢复脚本或重置池状态，将这些候选恢复为 `pending`，无需重新消耗大量网络请求去 GitHub 重新搜索。

## 五、 预期收益与效果评估

1. **推荐产出率恢复正常**：合格技能不再因机械性的行号偏差被一票否决，能够顺利进入推荐区，实现“新增 50 个推荐”的目标；
2. **DeepSeek 全力发挥**：DeepSeek 的强大推理思维链不再被 8,000 Token 截断，能够完整输出高水平评测；
3. **模型兼容性大幅提升**：无论使用 Qwen 系列还是 DeepSeek 系列，都能稳定输出合规格式，不再出现大面积 `OUTPUT_SCHEMA_INVALID` 阻断。
