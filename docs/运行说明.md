## 普通查找的导航价值筛选（2026-09-28）

`tools/run_local.py` 和目录 Actions 共用规则 1.3.0，默认在 `config/standards/rules.json` 启用 `quality_review.enabled`。该开关控制质量检查；不再发起第二轮独立模型复核。独立定向查找 `tools/find_skill.py` 不受此次修改影响。

流程：原有预筛 → 六项基础评估 → 核验核心引用 → 根据导航价值判断推荐或候选。实际价值并入用途明确，可操作性并入说明完整；材料足以理解做法与价值即可。`verification_note` 只说明有无示例、验收或验证方法，不作为额外门槛；不再请求三项 `quality_checks`。

六项均须有简短判定理由，核心功能引用集中在 `evidence_traceability.citations`；其他基础项不必重复引文，程序只验证原文存在，介绍与内容是否一致仍由模型判断。适用领域专项的通过项仍须有证据；不适用条件无需为缺少引文而失败。对“所读材料未见明显风险”不强求不存在风险的引文证明。

依赖一般信息缺口使用 `unknown`、`blocking=false` 并说明原因，仅在页面提示；关键运行条件不明用 `unknown`、`blocking=true`，缺必要依赖用 `fail`，均留候选。遗漏标记不放行，`fail` 不能用 `blocking=false` 绕过。材料未声明依赖不得解读为无依赖或全平台兼容。原有硬性排除与金融、健康专项保留。

每次请求前保存阶段状态，响应后立即保存用量；预算在下一次请求前检查，最后一次请求仍可能超过总上限。达到预算或响应用量缺失时，保存已完成的有效评估并停止后续请求，不再等待第二轮。运行中断且请求结果不明时仍进入既有恢复机制，不自动重复付费。调用记录保留在账本 `requests`，新评估阶段为 `assessment`。恢复快照仍需校验材料和规则版本；一致时直接核验并使用已有评估，不追加模型请求，不一致时拒绝复用。

规则版本已更新以隔离旧评估缓存；已有目录和本地池中 `done` 的条目不会被本次代码修改自动重评。需要重新发现并检查已有池条目时可用 `tools/run_local.py --refresh-pool`，仍按目标数、预算和发现范围处理，不代表全目录已完成重评。变更质量开关或判据时也应更新 `rules_version`，避免复用不同规则下的缓存。

运行入口保持不变：`.\.venv\Scripts\python.exe tools/run_local.py`。页面“筛选依据”展示检查理由，不显示评估轮数；历史两轮评估记录保留原状态。完整结论及引文留在本地或 Actions 评估账本。真实推荐质量仍需实际模型抽样校准，离线测试验证的是程序行为。

### 百炼模型队列自动轮换

普通查找与定向查找支持同一百炼账户、同一 endpoint 的文本模型队列。在 `config/models/model.local.json` 保留原有 endpoint、auth 及任务配置，将顶层 `model` 替换为非空 `models` 数组，例如：

```json
"models": [
  "<第一个实际模型 ID>",
  {"model": "<第二个实际模型 ID>", "limits": {"max_output_tokens": 4000}}
]
```

这些 ID 是占位符，必须换成自己的可用模型。不要同时保留 `model` 与 `models`，也不要同时保留新路径和旧平铺路径的 `model.local.json`。模型级参数仅支持 `request`、单请求 `limits` 和 `capabilities.json_schema`，任务预算不随模型改变。环境变量凭据优先。

在云端开启相关模型“用完即停”后，程序仅对结构化错误码 `AllocationQuota.FreeTierOnly` 自动记录耗尽并轮换。普通 403、欠费或其他错误不会误标耗尽；额度拒绝同时返回非零用量时先记账再停止。材料超过某模型输入上限时，本次调用跳过它，继续寻找能接收完整材料的模型，不删减材料。切换模型重置临时错误重试次数，但请求数、消耗与任务预算累计不重置。

耗尽状态存放在 `data/local/model-pool-state.json`，两入口通过文件锁共享。状态不自动过期，不探测额度恢复，更换账户也不会自动清空。损坏状态或遗留锁会明确停止；遗留锁必须确认旧进程已退出后由用户处理。

全池耗尽会保留未完成任务。编辑队列、追加模型后重启：普通查找继续执行 `tools/run_local.py`；Finder 使用 `tools/find_skill.py --resume`（多个历史任务可指定运行目录）。普通查找没有 `--resume` 参数。已完成结果保留原模型归属，不因队列调整重做；队列模式暂不复用缺乏明确模型身份的跨任务规范化缓存。

`tools/switch_model.py --show`、`--list`、`--check` 只读展示/校验队列与状态，不写文件、不联网；队列模式下切换写操作会拒绝覆盖配置。真实测试需显式运行 `tools/test_model_call.py --model <队列中的精确模型 ID>`，仅测试该模型，不自动遍历队列。

**候选池持久化与断点续跑（pool.json）**：
- 初次运行或候选池过期时，完整执行搜索与展开，将发现的全部候选及初始序号（`seq`）固化在 `data/local/pool.json` 中；
- 每处理一条候选（评估通过、预筛排除、抓取失败或非技能文件），立即原子持久化该条目状态（`pending` / `done` / `excluded` / `fetch_failed` / `not_skill` / `length_exceeded` / `blocked`）；
- 若进程中断（或中途达到 Token / 目标限额停止），下次运行**自动从断点继续**，跳过所有已处理候选，绝不从头原地打转；
- 当池中待处理候选充足（>= `pool_watermark`）时，**完全跳过网络搜索**（免去十余分钟耗时与上百次 GitHub API 调用，秒级启动）；低于水位线时自动增量搜索补水并追加到池尾；
- 命令行支持 `--refresh-pool`（重新搜索并重建候选池，保留超长跳过标记）与 `--pool-watermark <N>`（临时调整补水阈值）。

**单条样本异常隔离与容错（超长截断与格式损坏）**：

迁移清单、恢复授权幂等与中断恢复的历史验收记录见 [2026-09-28 实施方案验收与对照记录](audit/2026-09-28-实施方案验收与对照记录.md)。当前操作与预算规则以本说明为准。

- **超长截断（LENGTH_EXCEEDED）**：本地目录评估返回 `finish_reason=length` 时，按样本级 `LENGTH_EXCEEDED` 处理，不重试、不累加服务连续失败计数，并重置该计数。候选池持久化为 `length_exceeded`，续跑、补水、过期重建和 `--refresh-pool` 均保留跳过状态，不自动重评。截断只表明输出额度不足（可能包含推理 Token），不代表服务不可用，也不代表技能质量不合格；已有目录结论保持不变。
- **输出格式异常（PARSE_ERROR / blocked）**：模型返回非合法 JSON 或必要字段结构不合法时，认定为单样本格式损坏，直接标记候选为 `blocked` 并记录到账本，不发起无意义重试，不累加服务连续失败计数，而是平滑跳至下一个候选继续评估。只有在累计 10 次格式异常且中途未产出任何有效结果时，才会按 `format_failures` 机制停止。正常结束但没有正文按通用模型失败计数处理；缺失可补齐的质量项按第 11 节处理。
- **离线维护工具（manage_pool.py）**：
  - 对账一致性核验：`python tools/manage_pool.py reconcile`（支持 `--dry-run` 预览与 `--apply` 写入修复）。自动将账本已确认超长或不可重试格式损坏的候选同步至候选池 `length_exceeded` / `blocked` 状态。
  - 人工解除阻断：`python tools/manage_pool.py resume --evaluation-id <ID> --reason <说明> [--extra-attempts N] [--event-id <事件ID>]`（支持 `--dry-run` 与 `--apply`）。显式重置指定评估的不可重试状态并同步将池条目恢复为 `pending`。重放同一次授权时沿用事件 ID，不重复增加额度；未指定时会优先恢复该评估尚未完成的操作。事件 ID 仅允许字母、数字、下划线和连字符，最长 128 字符。
  - 对账及恢复清单保存在 `data/local/state/migrations/`。写入中断后可重新执行原操作，核对当前身份与状态后补齐清单；冲突会明确报错，不能直接套用旧决定。`--dry-run` 不补写清单。池读写失败会向调用方报告，不再静默忽略。
  - 离线恢复已完成结果时，只有材料指纹、规则及模型配置对应的完整评估身份匹配，且有有效完成账本，才将池条目标记为 `done`；同一技能的旧结果不会使新版本候选跳过评估。

本次输入、输出及推理用量正常记账，推理 Token 已包含在输出用量内，不重复相加。`report.json` 的 `skipped_length_exceeded` 与 `skipped_output_format` 分别统计本轮超长跳过与格式损坏跳过数，不计入基础设施失败；请求明细保留专属错误码。总预算耗尽、用量未知、候选耗尽等停止条件仍然有效，不能保证一定收满目标数量。

### 本地目录流水线优化与安全开关（2026-09-28 综合升级）

为在控制 Token 成本的同时保证评估严谨性，普通目录本地运行新增了两项优化功能，统一采用“**默认观察模式（只记审计不改行为），显式命令行开关主动启用**”策略：

1. **静态空壳过滤与批内防饥饿排序（`--enable-static-skip`）**：
   - **默认行为（观察模式）**：对抓取到的候选正文进行快速静态分级（`A` 高质量结构、`B` 普通有效正文、`C_PLACEHOLDER` 明确空壳模板、`UNASSESSED` 待定），并在账本请求记录中记录 `static_signal` 与 `suggested_action`，不改变实际模型调用。
   - **启用方式**：在命令行传入 `--enable-static-skip`。
   - **执行效果**：仅针对确认包含明显 TODO 占位且无实质内容的 `C_PLACEHOLDER` 项进行安全跳过（标记 `skipped_static`），不调用模型，避免无效支出。有效短文本技能绝不被简单长度规则机械误杀。
   - **防饥饿机制**：批内调度时根据评级微调评估顺序，优先评估高质量候选，同时保留至少 20% 配额给低评级或新候选，防止低星或非标准格式技能被永久饥饿阻塞。

2. **受限规范化缓存与原文证据重验（`--enable-normalized-cache`）**：
   - **默认行为（观察模式）**：计算当前材料的受限换行规范化辅助指纹（`sha256:norm:v1:...`）。若发现仅存在跨平台换行差异（CRLF/LF）或行尾空白差异的已完成历史评估，记录 `cache_observation` 审计信息，但不跳过模型调用。
   - **启用方式**：在命令行传入 `--enable-normalized-cache`。
   - **执行效果**：在精确缓存未命中、且同技能历史评估的规则版本、模型配置版本和严格输出契约版本均完全一致时，将历史候选的原文引文在当前新材料中执行重新核验（`verify_citations_in_document`）。核验全部通过后直接复用历史结论（标记 `cached_normalized`），记录来源评估 ID 与复用审计，不产生额外 Token 开销；若新材料中证据缺失、位置无法定位或有修改，安全回退至模型正常评估。

## 4. 队列与复核（§5.2、§5.3、§7.2）

`data/queue.json` 是**跨轮累积**的待处理队列，不是本轮快照。它保证超出每周额度的候选
会在后续运行中依次得到评估，而不是每轮被同一批条目反复跳过。

- 排序：已知内容变化或待复核的条目插队；其余按"先补齐从未处理过的、再按上次检查时间
  从早到晚"公平轮转；同组内官方来源优先。
- 已评估且内容未变的条目**不在队列主体里**：它们只在有多余抓取名额时被抽查
  （`MAX_RECHECKS_PER_RUN`，默认 10 条），用于发现"已推荐内容发生变化"。
  抽查条目在未真正处理时会退回队列，下轮重新排队。
- 队列项记录 `content_fingerprint`（上次抓取到的内容）、`baseline_fingerprint`
  （上次评估到的版本）、`last_attempted_at` 与 `first_queued_at`。
  索引里的指纹优先于队列自己的记录。
- 条目出队条件：这份内容已有完成的评估记录、已达尝试上限，或结果不明需人工确认。
- 建议在运行后确认积压：`--json` 输出的 `queue_pending`（队列长度）、
  `carried_over`（遗留条目数）、`needs_review_backlog`（内容变化积压）。

内容变化后的处理规则见 §5.2：保留推荐状态并醒目标记"内容已变化，待复核"，
同时展示原评估对应的版本与评估时间；复核通过才更新依据并清除标记，
复核不通过降级至候选区。

## 5. 故障处理（§7、§7.3）

| 情况 | 处置 |
| --- | --- |
| 来源不可达 | 保留上次有效数据，**不做**批量删除或虚假下架 |
| 模型调用失败 | 保留待处理状态，**不伪造**中文简介与评估结论 |
| 预留额度后崩溃 | 已预留名额**不释放**；下周重新排队并占用新周名额 |
| 手动重跑 | **不重置**尝试计数；设计上每个名额最多 2 次调用尝试 |
| push 冲突 | 停止后续付费调用、重新加载状态；使用非强制提交，不覆盖他人提交 |
| 提交成功但部署失败 | 只重试部署该产物，**不重新评估**技能 |

## 9. 人工干预区（收藏与排除黑名单）维护

依据 [产品规范](产品规范.md) §7.4 与 §10.1，所有人工干预统一收敛在 [config/overrides.json](../config/governance/overrides.json)：

### 9.1 人工收藏区（manual_picks）
- **收录条目**：在 `config/governance/overrides.json` 的 `manual_picks` 数组中添加条目对象，包含 `skill_id`（稳定 ID）、`reason`（非空理由）、`added_at`（`YYYY-MM-DD`）以及可选的 `from`（`recommended`/`candidate`）。
- **三区互斥**：收藏条目独立进入「收藏区」，不出现在推荐区与候选区，统计互斥。
- **免自动重评保护**：收藏条目的上游内容变化时更新指纹与检查时间，但**不调用模型重评（0 模型调用）**，程序绝不自动降级或移出。
- **移出收藏**：从 `manual_picks` 数组中删掉对应对象（或清空为 `[]`），该条目立即回到其原始自动结论分区（推荐区或候选区）。

### 9.2 人工排除黑名单（manual_exclusions）
- **永久跳过**：在 `config/governance/overrides.json` 的 `manual_exclusions` 数组中记录被屏蔽的条目对象（包含 `skill_id`、`reason`、`added_at`）。
- **预筛拦截**：预筛阶段直接判定为 `excluded`（原因码 `MANUAL_EXCLUDED`），流水线在发现或爬取到该条目时**完全跳过，0 模型调用、不消耗任何 API Token 额度**，且不出现在推荐区或候选区。

### 9.3 网页端交互与一键同步
无论在本地预览还是 GitHub Pages 线上预览环境：
1. 页面卡片右上角提供 **【★ 收藏】** 与 **【🚫 屏蔽】** 按钮，点击即时在当前页面生效；
2. 页面底部浮动同步栏实时统计未提交的变更项；
3. 点击 **【查看并同步到仓库】**，可直接一键复制最新配置并自动跳转到 GitHub 网页在线编辑页（`https://github.com/justdoit712/skill/edit/main/config/overrides.json`），粘贴后提交即可触发线上自动更新。

### 9.4 已收录名单（owned-skills.json）维护与变更包同步
依据 [已收录名单契约](产品规范.md#13-已收录名单契约)，用于将用户已掌握或私有托管的技能从推荐、候选、收藏及定向查找中隐藏：
- **全局过滤与候选评估跳过**：标记为已收录后，网页立即从推荐、候选、收藏和定向查找中隐藏条目，不再提供「已收录」分区及数量徽标。同步名单到仓库后，主目录与定向查找在识别具体技能后跳过其正文抓取与候选模型评估；前置规划、搜索和仓库展开仍可能产生请求及用量。误操作可通过标记后的提示撤销；已同步名单通过仓库配置或 CLI 维护。
- **白名单配置与存储隔离**：公共仓库名单维护在 [config/governance/owned-skills.json](../config/governance/owned-skills.json)，仅包含 `skill_id`、`name`、`added_at` 与可选 `source_url`；历史管理链接（`managed_url`）与私人备注（`note`）仍仅保留在当前浏览器 LocalStorage 中，严禁同步到公共仓库或部署产物。移除已收录分区后，页面不再提供私人详情与备份管理入口。
- **CLI 变更包合并与同步**：使用独立工具 [tools/manage_owned.py](../tools/manage_owned.py) 检查与合入变更包：
  ```powershell
  # 校验网页导出的变更包是否合法、是否有前置冲突（不写文件）
  .\.venv\Scripts\python.exe tools/manage_owned.py --check-changes <patch_file>

  # 加锁合入变更包并离线更新主索引与页面（0 Token 消耗）
  .\.venv\Scripts\python.exe tools/manage_owned.py --apply-changes <patch_file>

  # 查看当前已收录条目
  .\.venv\Scripts\python.exe tools/manage_owned.py --list
  ```
- **工作流自动触发**：向 `main` 分支提交 `config/governance/owned-skills.json` 时，自动触发 `.github/workflows/sync-config-deploy.yml` 运行离线同步与 GitHub Pages 发布。

### 9.5 页面暂存与同步业务场景边界
- **静态部署与单向手动同步**：本站部署于 GitHub Pages 静态环境，无服务端与后台数据库，不支持亦无需自动双向同步。业务同步闭环为：网页浏览 → LocalStorage 本地暂存 → 手动导出变更包或复制 JSON → 提交合入仓库。
- **单页面操作闭环**：单页面内的标记、放弃/清空、导出构成完整闭环。用户点击“清空”即可将当前页面的本地缓存与内存暂存完全清零。
- **杜绝过度设计**：项目不维护脆弱的浏览器跨标签页 Storage 广播实时联动机制；多标签页并发修改或跨页清空属于脱离实际业务形态的边缘用例，所有状态均以当前页面加载与用户显式操作为准。

## 10. 定向查找特定需求 Skill（find_skill.py）

产品约束见 [产品规范](产品规范.md) 第 12 节；实现与验收见 [修复验收记录](audit/2026-09-23-分层重构修复验收.md)。下面描述当前入口和源码行为，不能把目标规范当成已完成保证。

### 10.1 适用场景与运行边界

`tools/find_skill.py` 用于按具体需求比较相关 Skill，例如“生成高质量 Prompt”。它跳过主目录的领域、人工屏蔽与冷冻规则，不修改目录主索引、候选池、队列或周额度账本。它会读取上游材料并调用配置的模型，不安装或执行上游技能。

本地报告保存于独立运行目录，当前也会更新 `public/data/find-report.json`，供页面“定向查找”标签展示。命令本身不提交或发布；后续部署整个 `public/` 时，该报告可能随页面一起上线。

### 10.2 常用命令与参数

```powershell
# 使用配置中的默认需求；配置也未提供 topic 时才交互输入
.\.venv\Scripts\python.exe tools/find_skill.py

# 命令行直传需求与自定义限制
.\.venv\Scripts\python.exe tools/find_skill.py "生成高质量 Prompt" --limit 5 --max-evaluations 20 --max-tokens 200000
```

配置优先级为显式命令行参数 > `config/runners/find-skill.local.json` > [config/find-skill.json](../config/runners/find-skill.json) > 代码兜底值。未提供命令行 topic 时使用配置；两者都为空，仅在交互终端询问输入，非交互环境返回用法错误。

| 参数 | 当前仓库配置 | 代码兜底值 | 含义 |
| --- | --- | --- | --- |
| `topic` | 以 `config/runners/find-skill.json` 为准 | 无 | 本次查找需求 |
| `--limit` | `5` | `5` | 合格短名单目标，达到即停止 |
| `--max-rounds` | `3` | `3` | 首轮搜索与补水合计轮数 |
| `--max-evaluations` | `200` | `200` | 累计候选评估尝试数，失败也计入 |
| `--max-tokens` | `20,000,000` | `20,000,000` | 澄清、规划、评估和反思的累计停止阈值；最后一次请求可能超过阈值 |

模型连接优先使用 `config/models/model.local.json`，缺失时使用 example；凭据优先从对应环境变量读取。当前规划最大输出 4,000 Token，单技能评估 10,000 Token，连续评估失败停止阈值为 20。读取参数为主文件最多 64 KiB、主文件和最多 2 个引用文件合计 96 KiB。

数值请使用整数；配置中可用空格、逗号或下划线分隔，不要使用 `20m` 等单位缩写。非法格式会报错；要求 limit >= 1、max_evaluations >= limit、max_tokens >= 1000、max_rounds >= 1。

### 10.3 报告与当前限制

每次运行输出 `data/local/find-skills/<运行编号>/report.json` 和 `report.md`；JSON 保存需求、固定计划、生效参数、搜索与覆盖信息、请求事实、评估结果及用量。Markdown 为派生报告，公共快照仅在统一收尾按发布条件生成白名单投影，运行开始不覆盖旧快照。

未知用量会停止后续模型调用；当前有效结果仍保留。候选尝试数与成功评估数分别统计，失败尝试占名额。证据须通过严格类型、路径、行号和完整引文核验，但原文匹配不能保证模型的语义判断正确。

搜索、展开或材料全部失败与正常无匹配分别记录；中断收尾保留已有结果。部分查询、仓库或材料可能受读取上限影响，报告会标识覆盖不足，不能将结果称为全网最优。页面不把缺失用量或次数显示为零。

离线恢复命令、旧记录限制及本轮验证结果见 [修复验收记录](audit/2026-09-23-分层重构修复验收.md)，长期接口约束见 [架构约定](架构约定.md)。未执行技能不标记为已通过实测；真实模型语义、远端 Actions 与部署没有因离线回归通过而自动完成验收。

## 11. 评估与定向查找运行细则

### 范围与执行顺序

本节记录已实现的评估与查找行为，包括 Prompt 对齐、即时早停、引用重新定位、缺失字段处理、预算保护、检查点、分页补水及反思拓词。普通目录与 Finder 的引用核验分别实现；下述完整行重新定位仅适用于普通目录。

旧机器运行记录缺失，不复用文档中的失败率作为已验证事实，不批量恢复旧候选。当前模型为本机配置选择的模型，不自动切换或联网校准。服务端输出能力未经核实，保留私有配置中的输出额度；不能承诺提高额度后不会截断。

### 普通目录评估

- 规则版本升为 `1.1.1`，防止将旧规则缓存当作新规则结果。
- 开启质量评估时，JSON 示例集中输出 `evidence_traceability.citations`，并提供 `verification_note` 提示；六项保留简短理由，不再输出三个质量子项。
- 未提供 `verification_note` 时补充中性说明，不影响推荐。非法核心检查、非布尔 `blocking` 或非文本验证说明仍是结构错误。新评估不采用历史三项质量字段作门槛；历史记录保持原有展示。
- 质量缺口不覆盖已有的 `instruction_completeness=fail`、原始理由和引用；缺口单独保留在质量项及审计记录中。
- 引用必须是原文的完整连续行。依次接受精确定位、起止行号偏差不超过 3 行且唯一的定位、全文中唯一的完整匹配。不接受片段相似匹配，也不凭模型解释跳过核验。
- 每项最多 3 条引用，每条最多 60 行。优先短引用；原模型输出不改写，实际行号及匹配方式保存到审计字段。
- 核心引用或适用领域证据无法核实仍转为 `unknown`；其他基础项不要求重复引文，但主动提供的引文也须真实。普通信息缺口仅提示，关键缺口留候选；不再进行第二轮独立复核。

### 定向查找边界

| 参数 | 默认值 | 含义 |
| --- | --- | --- |
| `limit` | 5 | 经证据核验和排序后合格的短名单目标 |
| `max_rounds` | 3 | 首轮检索加最多两轮补水，空结果也计轮次 |
| `max_evaluations` | 200 | 累计候选评估尝试数，失败尝试也计入 |
| `max_tokens` | 20,000,000 | 累计用量停止阈值，包含澄清、规划、评估和反思 |

每次有效评估后立即检查目标，续跑开始也检查。用量未知优先停止；用量已知时，目标达成优先于同一次调用触及 Token 或次数上限。预算在下一次搜索、展开、抓取或模型调用前检查。

Finder 的澄清、规划、评估和反思请求均在发送前统一预留预算，串行与双并发采用相同规则。预留按提示词与响应 Schema 的 UTF-8 字节数、256 Token 消息余量及完整最大输出 Token 计算，属于针对常见字节分词器的保守估算，不是已计费用量。已知消耗加在途预留再加本次预留超过 `max_tokens` 时不会发送请求；在途请求结算后可以释放剩余额度。因此即使实际累计消耗低于阈值，也可能因不足以容纳下一次请求而以 `token_limit` 停止。若后端使用不同分词或额外计费规则，仍需验证估算适用性。

每条请求保存独立 `request_id`、`reserved_tokens` 和 `reservation_state`。已知用量响应按实际值记账并释放预留；用量未知保留预留并停止新请求。`usage_audit` 每次更新为最新对账状态，在途请求不被当成已结算的未知用量。双并发通过 `--concurrency 2` 启用，默认仍为串行。

所有定向查找模型请求禁用底层隐藏重试。仓库搜索每个查询的同一页最多尝试三次（含首次），调度层持久化计数，底层每次只发一个请求；其他 GitHub 接口仍沿用原有有界重试。连续模型失败阈值跨轮次与续跑保留。

失败搜索页采用指数退避，并遵守 `Retry-After` / GitHub 限流重置时间；等待按不超过 60 秒分段，可中断续跑。请求发送前记录尝试，跨轮次与续跑不清零；仅成功才推进页码。到达上限或收到不可重试的 HTTP 错误后跳过该查询，继续其他查询，记录未完成页和覆盖缺口；当前查询全部失败时以 `search_failed` 停止。

网络恢复后，可用 `--resume --retry-failed-searches` 显式重置未完成页计数，重用原规划、成功搜索和评估结果，保留失败历史及服务端冷却时间。全局轮数、模型次数和 Token 限制仍生效。旧报告没有逐次计数时，将已失败页视为原底层三次尝试已耗尽，须显式重试。

### 定向查找证据判定

存在必需能力准则时，强匹配要求全部必需能力有核验通过的支持证据；部分匹配至少要有一项必需能力得到支持，仅满足质量准则不能作为备选。文档严重不足会将强匹配降为部分匹配。模型原判为 `none` 时，即使发现部分支持证据，也只记录审计冲突，不自动升级。

缺少支持的必需能力写入限制说明，报告保留模型原始判定与核验后判定。每条引用最多 1200 字符，超限作为格式错误处理，不截断后参与核验。

### 补水与检查点

1. 已保存候选分批评估，每批最多 12 个；批次间穿插展开最多 5 个待处理仓库。候选队列为空时，先展开最多 20 个待处理仓库。存量耗尽后进入下一轮搜索；启用主动反思时也可在批次间拓词搜索。
2. 每个关键词保存下一页及耗尽标记。每页 20 个仓库；不足一页表示耗尽。仓库使用规范化 `owner/repo` 去重，技能使用 `skill_id` 去重。
3. 待展开仓库按相关性排序；候选调度按约 80% 相关性优先、20% 探索分配。每批优先限制单仓库最多 2 个候选，无其他候选可填满批次时放宽此限制。展开保留返回树内的所有技能路径，其余候选留队，模型尝试数仍由全局预算约束。
4. 常规补水先翻页，没有新仓库时反思；连续两轮有有效评估且全部为 `none` 时，下一轮优先反思。仓库运行配置已启用主动反思：连续两批有评估结果但均无 `strong` / `partial`，且尚未达到轮数上限时，可在当前轮提前反思拓词。
5. 每个补水轮最多反思一次。模型只能返回 3–5 个短语，程序去重并拒绝搜索操作符、额外字段；原始需求、意图、评估准则保持不变。候选反馈最多五例，按不可信资料处理。
6. 报告保存轮次阶段、搜索页、仓库队列、候选队列、处理过的技能、连续失败数和反思结果。读取失败和格式失败也记录为本次运行已处理，不自动反复请求。
7. 已收到的模型响应与评估材料检查点保存到本地事实报告。续跑按 `pending_evaluations` 中每个检查点的请求 ID 补录已返回但尚未形成评估的结果，兼容旧单检查点，不重新抓取材料或发送模型请求；重复恢复不重复计数。发送后尚未确认的请求视作用量未知，保留预留并停止自动重试。
8. 旧报告缺少队列时，重新发现候选并跳过已有结果及已记录尝试；无法保证从缺失的旧游标精确接续。续跑不能更改原始需求。

| 原因 | 状态 | 退出码 |
| --- | --- | --- |
| `target_reached` | `completed` | 0 |
| `candidates_exhausted`（反思无新词） | `completed` | 0 |

| `usage_unknown` / `model_failures` | `stopped` | 2 |

### 查询观察与报告统计（第 2、3 单元修复）

- Finder 新报告使用 `schema_version=1.1.0`；前端和离线重建继续兼容 `1.0.0` 及未声明版本的旧报告。离线重建旧报告不会改写其原版本。
- 术语观察保留模型原始查询、清洗去重后的查询及完全未覆盖的概念。正常规划与已返回规划响应的中断恢复共用审计解析，不额外请求模型，也不执行拟补充查询。
- Finder 与本地目录报告的 `metrics` 从保存的调用、搜索、用量和结果事实重算；重复保存或重建不累加计数。公共 Finder 投影只输出固定统计字段，不复制内部诊断。
- 缺失历史字段、未采集的规范化缓存或抽样核查信息使用 `null` 表示未知。搜索请求在未能确认是否发出时也保持未知，不能用预留尝试冒充已确认 HTTP 请求。
- 抽样误拦截率以实际抽查数量为分母，不以全部跳过数量为分母。版本复用检查要求指定的规则、模型配置和输出契约版本齐全且相等；不凭相同主版本假定评估结果可复用。该校验不迁移旧记录或触发全量重评。

### 术语有界补全与邻近证据恢复（第 4、5 单元）

针对 Finder“一直没有推荐结果”及检索词语言覆盖不全的问题：

- **邻近证据漂移恢复（两层核验）**：Finder 评估候选时，采用两层核验机制：
  1. 首层精确匹配起止行区间。
  2. 若模型输出的行号出现 $\pm 3$ 行以内的轻微偏差或换行不一致，核验器自动在上下 3 行滑动窗口内执行空白与换行标准化匹配。匹配成功后标记恢复状态（`evidence_recovered=True`）并记录实际所在行区间（`recovered_line_start`, `recovered_line_end`），保留有效推荐评级。
  3. 若原文中不存在该内容或引文被篡改，依然坚决判定不通过并降级为 `none`，杜绝伪造证据。
- **术语有界补全（`--enable-terminology-completion`）**：
  - 默认采用观察模式：仅记录未覆盖的概念到 `terminology_observations`，不增加 GitHub 搜索。
  - 显式传入 `--enable-terminology-completion` 时，系统在总查询数不超过 8 条的前提下，最多补充 2 条英文技术术语检索式。补充查询在报告中明确溯源（`origin="terminology_completion"`），并单独记录边际召回与 Token 统计。
